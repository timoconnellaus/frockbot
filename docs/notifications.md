# Messages, unread state and Android notifications

Every explicit `send_to_user` message advances the Bot's cloud-owned message cursor as part of the transaction that persists that send. A Turn can send several messages, and its settlement adds no unread count. Text, approvals, widgets and Routine messages use the same notification preference. Private model text never becomes an alert, and neither does a Turn's `reply/to-caller` answer: it is addressed to the caller that asked for the Turn — the account's voice session, which reads it out itself, or another of the User's Bots, which reads it as its tool result — so it mints no message, advances no cursor and wakes no device (see [voice](voice.md)). A `send_to_user` message from a Turn with a `voice` origin is still an ordinary message that counts as unread, but it creates no push: the person asked on the call.

Clients mark the latest displayed message read only while the app/window is focused, the conversation is visible and the latest message is on screen — any part of its row inside the viewport, rather than the thread being pinned to its end, so a thread nudged up a line is still being read. A background app, another open Bot or a viewport in older history does not mark new messages read. Explicit Mark as read is a separate action. Read cursors only move forwards and name real messages; an older device cannot undo another device's read. Manual unread is a reminder and creates no push.

The same definition of focused — the open chat, on a window that holds focus, with nothing covering it — decides both the read receipt and what the sidebar draws. Covering is read per tier: the dual tier is the only one that draws the right panel as a drawer over the conversation, so only there does an open panel cover it. At the widest tier the panel and the run view are a third column beside the conversation and cover nothing, and on a phone they are pushed pages the route already accounts for — and an open run is never a covering of its own, since it reaches the screen as that column, through that drawer, or as one of those pages. The cloud count stays honest, because the Bot cannot know which chat is on screen and the receipt that clears the count is a round trip behind the message that raised it; the client suppresses the focused Bot's badge, bold name and contribution to a group total at render time instead, so a reply settling into the chat the User is reading never flashes a badge. A Bot marked unread by hand is the exception: it keeps its bold dot while open, because that flag is intent rather than arithmetic, and only opening it again clears it — but the count beside the dot is arithmetic, so it is suppressed like any other. Suppression is cosmetic and local to the device that knows what is on screen; the durable receipt is what makes the badge stay gone on the next launch and the next device.

Android uses Firebase Cloud Messaging's native Android SDK and `NotificationCompat.MessagingStyle`. New messages update the Bot's existing expandable notification; other Bots have their own notifications. Swiping away the notification leaves the conversation unread. Tapping opens that Bot. Read updates remove the corresponding messages from notifications on other devices. Notification permission, sound, vibration, lock-screen visibility and launcher badges use Android's controls. The in-app unread count does not depend on launcher behavior.

A chat Turn that ends `failed` is told the same way: the settling transaction commits one ordinary message carrying the product's sentence for the failure, named `<runId>:failed`, which is the line the conversation draws for that run — so the Bot's row badges and previews it, a device is alerted, and opening the conversation clears it. A run settled `failed` again by recovery adds no second message.

A Routine whose Turn broke is told the same way: the firing commits one ordinary message through the same index, unread cursor and outbox, keyed by the firing so a settlement retry adds no second message. That message is drawn in the conversation on the firing's own run, at the next send ordinal the run had reached, so the identity the device renders is the one the unread record names and opening the conversation clears it. A muted Bot still counts it unread and raises no alert. A firing refused before any Turn was admitted records no run of its own, so the terminal record admission never wrote is written in its place — failed, with no journal — and the message is read in the conversation exactly like every other one.

Because only a Routine Turn that contributed a message belongs in the transcript, that fact is recorded beside the message it committed. The transcript scan filters a silent firing off its run record and that marker, without opening its journal, and reads that same marker for the message a broken firing's journal cannot carry.

A Bot hidden from the sidebar is muted. The Bot's configuration transaction enforces it for every writer — the settings surface, another client, or the Bot's own `bot_update`: the write that hides a Bot turns `notifications.enabled` off with it, and turning notifications on while the Bot is hidden is refused with a stored `rejected` receipt that moves no revision. Showing the Bot again leaves notifications off until the User turns them on. Hiding changes alert eligibility only; the Bot's messages still count unread and roll into the sidebar's "Show N hidden" entry. On the native settings surface, hiding a Bot that notifies asks for confirmation first, and confirming draws both switches at once and sends a single `bot/set-profile`; while hidden, the Notifications switch is disabled and says why.

Every state a row can show — read, pinned, muted, labelled, hidden, archived — can be flipped from the row itself, without opening the Bot (`apps/native/lib/shell/bot_actions.dart`). The same list of actions is reached the way each tier reaches a row: a phone long-presses it for a sheet, and a desktop secondary-clicks it for a menu at the pointer or presses the control the row grows under the pointer and on focus. On a phone each row is a card a shade lighter than the list's ground, so what a thumb slides is visibly the thing that moves; the ground is the app's ordinary page surface, so the list is no lighter than any other screen, and a swipe reveals a recessed track beneath the card rather than a second card. A phone also swipes, through `flutter_slidable`, which carries the swipe rows have had since Mail: the action slides in with the row and stretches as the swipe goes on (`StretchMotion`), never fades. Towards the trailing edge a swipe past a third of the row marks the Bot read, or unread when nothing is, and the row springs back (a `DismissiblePane` whose confirmation performs the action and vetoes the dismissal). Towards the leading edge a short swipe rests on a Hide button for a tap, and a long swipe past most of the row hides without the tap, the button changing colour before the finger lets go so the commit is never a surprise. Each line crossed ticks under the thumb, one row is open at a time (`SlidableAutoCloseBehavior`), and a scroll closes it. Each action is one command — `bot/mark-read` or `bot/mark-unread` through the activity controller, one-field `bot/set-profile` patches for pin, label and hidden, `bot/update-notifications` for mute — fenced on the revision read just before it and drawn on the list before the answer, then put back if the authority refuses. Hiding from the row does not ask first: it offers Undo instead, and Undo puts the notifications back too, because hiding turned them off. Archiving asks with the same dialog as the Bot's page, and delete is not offered from the row at all.

A short-lived device presence record can defer a push while another device is reading. Only a durable read receipt can discard the alert. If presence becomes stale without a read, the Bot's durable outbox retries delivery. The outbox shares the Bot's alarm and also drains immediately after messages and read commands. Alarm retry can take up to roughly 30 seconds after a stale presence lease.

Each User holds a bounded device registry. Tokens rotate under a stable installation ID; logout unregisters the device and clears local notification state. Read signals have a 24-hour delivery lifetime, and app resume reconciles read state again. Push messages carry stable message cursors; Android ignores duplicates and already-read messages and does not re-alert for an older out-of-order message.

The server records an external attempt before calling FCM. A known service rejection is retried with backoff. An ambiguous network outcome or interrupted attempt is recorded as uncertain and is not blindly repeated; the message remains available in the conversation. Delivery receipt cursors are bounded to one per Bot/device/update kind. Push is an alert transport, never message history authority.

## Application icon badge

The app icon shows the account's unread messages: the sum of the unread counts of every non-archived Bot whose Notifications setting is on. Each view in `/api/bots/unread`, and the view a read receipt returns, carries `notificationsEnabled`, which the Bot Durable Object reads from its current settings; the cloud stays the only authority on both the count and the eligibility. A muted Bot still counts on its sidebar row and adds nothing to the icon. A Bot marked unread by hand with no unread messages adds nothing either, because the manual flag is a reminder rather than a count. The focused conversation is suppressed exactly as the sidebar suppresses it, so a reply settling into the chat being read does not flash on the icon while its read receipt is in flight.

`apps/native/lib/activity/badge.dart` holds the counting rule. At startup, the shell preserves the existing icon badge until both the cloud unread fan-out and the network Bot directory with its lifecycle/archived state have loaded. A cached directory can populate the sidebar but cannot authorize a badge update. If the directory or lifecycle read fails, polling and app resume retry it without overlapping directory reads or discarding the cached UI. With Beta focused and Alpha holding two unread messages, the first authoritative Dock reconciliation shows 2.

After that, unread refreshes, read predictions or receipts, focus changes and the refresh after a Bot settings save reconcile the badge. Unchanged values are deduplicated, except when the native push channel first becomes ready or native notifications change. Notification delivery and completed native read effects reapply focused suppression even when the cloud count stays unchanged.

On macOS the dock tile's `badgeLabel` shows the total, saturating at `99+` when the sum passes 99 or any contributing Bot's count is capped, the same saturation the sidebar uses. Zero removes the label, and sign-out or the signed-in shell being torn down clears it.

Android launchers badge from active notifications, and some draw only a dot, so badge reconciliation never creates a tray notification. For eligible Bots, it refreshes only existing notifications, using the greater of the cloud count and the retained message count (a capped cloud count is reported as 100, the least the real count can be). Muting or archiving a Bot cancels its notification and forgets its retained messages and stored count. Focusing an eligible Bot with a positive cloud count cancels only its active notification, preserving its stored messages and count; leaving focus does not recreate that notification. Neither suppression nor swiping marks the conversation read, and reconciliation does not restore a swiped notification.

A true cloud zero, including for the focused Bot, removes the stored cloud count before refreshing any retained active notification from its remaining messages; an active notification with no retained messages is cancelled. This prevents stale stored counts from inflating later alerts while read cursors still determine which message entries remain. Sign-out or an account change cancels the account's notifications and clears its stored notification state.

## Configuration

The Android configuration is `apps/native/android/app/google-services.json`, for Firebase project `frock-bot` and package `com.frockbot.mobile`. It contains Firebase's public app configuration. Gradle applies it only to a build that opts into that production identity (`apps/native/README.md`, Android upgrade); the isolated `.dev` package every other build produces carries no Firebase registration and receives no push. The release workflow requires `FCM_SERVICE_ACCOUNT` in GitHub Actions and forwards it to the production Worker. The server's dedicated `frockbot-push` service account has the Firebase Cloud Messaging role. Its private JSON credential belongs only in the Cloudflare Worker secret `FCM_SERVICE_ACCOUNT`, never in the APK or repository.

The authenticated `/api/push/device` endpoint registers tokens, renews focused-viewer presence, and removes an installation. The User identity comes from gateway authentication, not request JSON.

## Release verification

The one-time, repeatable `notification-state-cleanup.ts` cleanup removes disposable old Turn-based unread state and pending notification projections when each Bot is loaded. It retains conversations and settings. The one-time `hidden-bot-notifications-cleanup.ts` cleanup, also run as each Bot is loaded, turns notifications off for a Bot that was hidden before hiding muted it, moving its settings revision. A release must visit the unread directory to load existing Bots and verify a fresh conversation before declaring the change ready.

Android native Firebase changes require a full Shorebird release through `scripts/native-update.py release`, followed by publishing and `adb install -r`; they cannot ship as a Dart-only patch. Deploy the backend before installing the message-cursor client.

Read cursors are message cursors, which the `1.1.0` build cannot decode, so this release raises both the app version and `minimumNativeVersion` to `1.2.0`: an install that is not upgraded is told to update rather than left with a broken sidebar. The release name comes from `apps/native/pubspec.yaml`, so the APK and the gate cannot disagree. A read command an older build left behind is discarded on load instead of retried.

The app icon badge adds `notificationsEnabled` to the unread view, and the view refuses unknown and missing fields, so a native build without it cannot decode `/api/bots/unread`. This release raises the native app version and `minimumNativeVersion` together to `1.4.0`, and ships the Android half as a full release because it changes Kotlin. Deploy the backend before installing the new native clients. Check the dock badge with the focused chat receiving a reply, a muted Bot, 100 or more unread, and sign-out; check an Android launcher with a muted Bot's notification present, a swiped notification, and a read on another device.

Check real-device delivery with the conversation focused, another Bot selected, the app backgrounded, and the process stopped normally. Verify bursts, notification navigation, mute, notification permission denied, read-on-another-device, logout, and offline catch-up. Android force-stop is a separate OS state: FCM delivery resumes after the user opens the app again.
