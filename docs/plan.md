# The re-orientation

FrockBot grew a distributed capability operating system around a product that needed a well-built app. Every capability became a Package, the app itself became a 51k-line "plugin", the client split across Vue, Flutter and a third UI language, and the agent loop braided provider I/O together with durable resumption in one 1,785-line function.

This document is the plan to reach the architecture described in [`architecture.md`](architecture.md). It replaces the ADR set, which recorded how the previous shape was reached and is available in git history. A landed step records the decision it settled and what it removed; the current shape of anything it built is [`architecture.md`](architecture.md)'s to state, and the reasoning behind a decision lives in its [ADR](adr/).

## Target

|                  | Before                                           | After                                   |
| ---------------- | ------------------------------------------------ | --------------------------------------- |
| Packages         | 74, of which 44 plugins                          | ~7 modules                              |
| Clients          | Vue + Flutter + a third UI language              | Flutter, plus web sign-in and marketing |
| Agent loop       | 1,785 lines, provider I/O and durability braided | ~300-line durable loop over the AI SDK  |
| Plugin runtime   | cordis, 158 import sites                         | frock-compose                           |
| Applet authoring | on the User's Computer, via Miniflare            | a cloud build service                   |
| Untrusted code   | every package treated as untrusted               | Bot-authored code and Applets only      |

The seven modules: `core`, `app`, `frock-compose`, `providers`, `computer`, `applets`, `native`.

## Decisions

Settled, and not to be relitigated without a reason that is new:

- **Bot-authored packages stay.** Self-modification is the product, so the loader, generations and grants survive — scoped to untrusted code rather than applied to everything.
- **A tenant is a User.** One Plugin worker per account. A Bot authoring a Plugin installs it for that User; which Bots run it is the Bot's own enable map ([ADR 0026](adr/0026-plugins.md)).
- **The base has no DI container.** Ordinary imports. This is what stops the collapse from quietly undoing itself.
- **The Computer stays, as a Package.** One provider-neutral `ComputerHost` interface with Fly behind it, so another host can be substituted. It leaves the Applet authoring path entirely. The chosen next host is the five-User DigitalOcean Kubernetes pilot in [`kubernetes-computer-host-plan.md`](kubernetes-computer-host-plan.md), with a gated Hetzner expansion path.
- **Applets follow cloudflare-os.** Source in object storage, built by a cloud service, mounted from an immutable artifact into a Durable Object facet. The runtime is already correct; only authoring moves.
- **Providers go through the AI SDK.** Request translation, streaming, tool-call accumulation and usage reporting are bought, not written, behind one narrow `ModelProvider` interface.
- **At-most-once by idempotency key.** Forensic reconciliation of dispatched effects is removed.
- **Multi-bot stays.** A single default avatar for now; the wearable system is deferred, not deleted.
- **Vue is deleted per surface**, in the same change that lands its Flutter replacement, so `main` always ships a working product.
- **Frock Compose is ours.** `frock-compose/` carries no upstream provenance and is not tracked against another repository. It is free to diverge — which is what makes the Flutter `ViewNode` renderer a first-class part of it rather than a fork.

## Order

Each step leaves `main` shippable.

**1. Documentation reset.** _Done._ One page of principles, one architecture document, this plan. The ADR set, the slice plans and the superseded research are removed.

**2. Cut what is dead.** _Done._ The Electron and WebView shells, their capability packages, the architecture checks and two prototypes: 11 packages, 14,548 lines.

**3. Park the deferred features.** _Done._ MCP and Composio came out first — roughly 11.4k lines, no owned Durable Object class and no owned tables. MCP returns later as a plugin over the `http` grant. Composio came back as first-party app code instead (step 11): it is the deployment's own connection backend, not untrusted code, and the `http` grant is how a plugin reaches an account through it.

The same ruling cleared two leftovers from that cut: Bot templates carried an `mcpServers` field and Routines a connection-trigger kind whose only provider was Composio, both kept only because changing a stored shape looked like a migration. Both are gone, along with the trigger path they served.

`plugin-voice` and `plugin-billing` are out too, in their own tag. Voice owned the `VoiceSession` Durable Object class; a `deleted_classes` migration retires it, because a `new_sqlite_classes` entry is immutable once applied.

**4. Providers onto the AI SDK.** _Done._ One interface over `ai` + `@ai-sdk/*` replaces the hand-written provider stack, and an Anthropic provider proves the seam is open — the provider set had been a hardcoded two-entry map. What the SDK could not take stayed: request mapping, failure classification and the deadlines, because the Frock AI gateway and Ollama's native endpoint reach that seam with a stream and no URL. The 2,526-line Ollama connection file was left untouched by this step: durable-record ceremony, not transport. That ceremony is one provider-neutral lifecycle now, `providers/model-connections/user.ts`, which Ollama Cloud and every catalog provider configure. Shape: [`architecture.md` §7](architecture.md#7-model-providers).

**5. Split the agent loop.** _Done._ `index.ts` is 853 lines beside `model-request.ts`, `resume.ts`, `tool-execution.ts`, `errors.ts` and `runtime.ts`. The extraction changed no test, which is what proved it changed no behaviour.

Forensic reconciliation is gone. Every external effect that matters carries an idempotency key — a model call's `requestId`, a tool call's `occurrenceId` — and is re-issued under that key rather than investigated afterwards. No Turn parks waiting for a person to resolve it. `admitEffect` and Stop fencing survive and now run before every dispatch, re-issues included.

The seam that retrieved a lost response from the provider is deleted outright: `LlmReconciliationCapability`, `ctx.llm.reconcile`, and all four provider implementations. It was declared, implemented everywhere and called by nobody. Shape: [`architecture.md` §4](architecture.md#4-agent-loop--coreagent-loop).

**6. Frock Compose replaces cordis.** _Done, in three cuts that each left `main` shippable._ Wired the extension points named in `AGENTS.md` — and only those — and deleted `kernel-composition`, the manifest system, `plugin-authoring`, `plugin-package-catalog` and `plugin-package-publisher`.

- _6a, done._ The three packages, with the seams that existed only for them: the Bot authoring quota and artifact store, the Catalog install path, the publisher's User revisions, and `apps/cloudflare-bundler`, whose one caller was authoring. 14,900 lines. Authoring returned with the step 8 build service; until then nothing else produced an artifact-bearing member, so the only isolate member was the Applets Package.
- _6b, done._ cordis is gone. The registries are plain classes built by ordinary imports; every first-party plugin is a feature function the app lists in order; the loop takes one typed hook list (`LoopHooksV1`) that replaces the waterfall and emit bus, and the isolate host appends a Bot-authored package's hooks to the same list after the app's. The resident runtime, the desktop shell contracts and the two `@cordisjs/plugin-webui` entries went with it: none had a live caller.
- _6c, done._ Frock Compose hosts the untrusted layer only. The Package Catalog went first — first-party code ships with the deploy, so it had nothing to distribute — and then the manifests: a first-party plugin is a `PackageDefinitionV1` the foundation lists, and an untrusted member carries a `PluginDescriptorV1` naming its tools, the loop seams it wraps, the grants, the slots and the three context keys, and nothing else. Generations list untrusted members only and live in `core/durable`; `kernel-composition` is deleted. Shape: [`architecture.md` §5](architecture.md#5-composition).

**7. Collapse the plugins into the app.** _Done._ The 21 first-party plugins are directories under `app/`, and the seven modules are what is on disk: `core`, `app`, `frock-compose`, `providers`, `computer`, `applets` and `native`. `applications/` is gone, and the eight per-plugin vite builds went with it — nothing read their output, and the app's own build bundles the clients from source.

The shell backend is now a state object and feature modules: `ShellBotStateV1` is what every feature function takes as its first argument, and each group is an ordinary exported function the Bot Durable Object calls directly. `app/shell/backend.ts` went from 6,111 lines to 204: the state construction, a hook table of one-line lambdas, and the forwards the recovery tests still drive.

Frock Compose was the last module to be cut. `frock-compose/` is one flat workspace holding the isolate host and its wrapper; the framework-agnostic Compose kernel beside it — which nothing had imported since cordis went — is deleted, and the core-to-compose cycle went with it. What an untrusted member declares about itself is a contract, so `PluginDescriptorV1` and the four vocabularies it names live in `core`, the failure phases live beside the activation that records them, and `core` imports `@frockbot/core/` and nothing else. The app builds the host `activateCompositionV1` mounts through (`app/shell/backend-composition.ts`).

**8. Applets off the Computer.** _Done._ `apps/applet-build` is a fifth deployable: no routes, an `APPLET_BUILD` service binding, a `node:24-slim` container with no egress running the SDK's own five-stage pipeline over source posted inline, answering with diagnostics or with a content-addressed artifact the app Worker hash-verifies and stores. The Bot authors through `applet_*` tools, and `applet_publish` builds from the Workspace prefix rather than from a Sprite.

The Computer is out of the loop entirely. Applets declares no durable root to it, so nothing is mirrored onto a Sprite; the `applets` provisioning phase, the `applet` PATH shim, the unpinned `@frockbot/applet-sdk@latest` install, the two doctor checks and the `applet dev` preview-tab branch are gone, and provisioning is five phases. The SDK lost its CLI and its `bin` with them — the service is the only thing that builds an Applet — and the end-to-end Workspace seed door went the same way, its last caller having been the `dist/` seeding a publish no longer reads. The last cut was 488 insertions against 1,807 deletions; the step as a whole is 7,354 insertions against 2,543 deletions, and what it bought was a build service and a Computer with no Applet-shaped operation left in it. Shape: [`architecture.md` §9](architecture.md#9-applets).

**9. Flutter to parity, Vue out.** _Done._ The long pole. One Flutter client, on the phone and on the web — `bot.frockbot.com` is an app behind sign-in, so Flutter Web's first-load cost buys one codebase instead of two. Each surface ported, then its Vue original deleted in the same change. Includes the ViewNode renderer — six node types — which replaces the third UI language as the way a plugin renders.

The flip served the Flutter web build at `/` and took the Vue client out in the same change: 216 files and 42,949 lines, `packages/` with them, so the repository holds one client and no client libraries beside it. What a plugin renders is the ViewNode document the server projects, not a second UI language. The one thing the browser cost is the app origin's Content-Security-Policy: `script-src` gains `'wasm-unsafe-eval'` and `style-src` gains `'unsafe-inline'`, which is what CanvasKit and the engine's injected styles need. The artifact origin's policy is untouched, which is the one that matters — it is where untrusted code runs. Shape: [`architecture.md` §6](architecture.md#6-clients).

- _PR 1, done._ The Flutter app compiles for the web. `dart:io` leaves `lib/` except inside `*_io.dart`, and a test keeps it there; four seams pick an implementation by conditional import.
- _PR 3, done._ The shell: the Bot list, the conversation and the right panel, three responsive tiers, and a slot registry that is the Flutter analogue of `<k-slot>`, with `Semantics(identifier:)` on every interactive widget from one file — which is what a Playwright spec can select on a canvas. No Vue is deleted yet: Flutter Web is not what the site serves until the flip.
- _PR 4, done._ `ViewNode` and `ViewDocument` are in the client wire schema and rendered by `apps/native/lib/view/`, six node types. The third UI language went out in the same change: its two Flutter packages, the vendored spec, the catalog adapter, `FormPreview` and the wire types beneath them — 2,065 lines.
- _PRs 5 and 6, done._ Settings, as a host over the `SettingsFrame` projected as a `ViewDocument` rather than a second renderer of typed fields, and Bot settings as a surface of its own.
- _PR 7, done._ Connectors and Plugins, two more projections in the settings-document family. `SettingField` gains a `secret` kind: the document seeds it null, the widget never shows a value, and the typed characters go out on the action input and are dropped from the controller the moment it is answered. Admin was a small surface of its own over `/api/admin/policy`; it is gone, along with those routes — administration is the [admin portal](../README.md#the-admin-portal) ([ADR 0028](adr/0028-open-deployment.md)).
- _PR 8, done._ Routines, Audit, Search and conversations. Neither frame carries a shared revision counter, because a Routine is its own durable record and an audit page is a projection: each projection derives one from its own bytes, so the host adopts a fresh controller exactly when what it is showing has changed. The Bot has one continuous, automatically compacting chat, whose Session announcements are system lines in the thread.
- _PR 9, done._ Flock, templates, machines and the Routine editor. Creating a Bot is the sidebar's own gesture, with the avatar art bundled; archiving, restoring and deleting are one retained lifecycle command per account, surfaced in Bot settings' Advanced. Three more projections in the document family, and the Routines document grows an editor — one form, seeded by the read, for a new Routine or for the one `?edit=` names, because a form per Routine would be a second copy of every prompt in the document. One rule arrived with all three: **a secret the authority minted once is never in a document.** A webhook key and a pairing code exist on a receipt and nowhere else, and the host holds each in a banner for as long as the person is looking at it.
- _PR 10a, done._ Applets, the Computer and Package pages, all framed web pages through one seam, `lib/view/host_frame.dart`, and all host chrome rather than projections, because each holds a credential minted per reader and a document can be read twice. The `/native-fallback` path is gone whole, `FallbackBootstrap` from the wire schema with it.

**10. Narrow the Computer.** _Done._ `ComputerHostV1` is the interface everything above the Computer speaks, Fly is one implementation of it behind a single deployment chooser, and an in-memory host proves the substitution by running the same contract suite. Step 8 had already left the host generic — no Applet-shaped operation was left in it — so nothing here was a rewrite. The three cuts are 3,051 insertions against 3,987 deletions across 106 files. Shape: [`architecture.md` §10](architecture.md#10-computer).

- _Cut 1, done._ The two callerless seams, before the interface work touches them: the sanctioned one-root Workspace sync, and the superseded v0 single-effect journal that nothing in production ever populated — migration `v5` retires its Durable Object class with the route and the bindings that served it. 78 insertions against 2,211 deletions.
- _Cut 2, done._ The interface, and Fly as its one implementation: `ComputerHostV1` and `ComputerHostSessionV1` with a capabilities block that says what a host _is_ — its scratch path, its GUI refusal, its desktop's shape, its viewer origins — hanging off both the host and its sessions, because every reader needs it before there is a session. The 2,549-line on-Sprite runtime moved into the implementation, and the import gate gained its second rule.
- _Cut 3, done._ A second implementation that proves the first is one: `computer/fake`, an in-memory host, run against Fly by one contract suite asserting the interface's behaviour and nothing either host's own. Fly is chosen in one file, `apps/cloudflare/src/computer-host.ts`, beside the bindings the choice depends on: the app is handed a factory and registers whatever it is given. The gate grew its last two rules, which is what took one vendor's vocabulary out of forty files that had only ever been describing it. 1,735 insertions against 826 deletions.

**11. Connected apps.** _In progress, in cuts that each leave `main` shippable._ One integration layer for the services a User connects FrockBot to, as `app/connect`, the provider behind it invisible plumbing, each app its own Connectors row, and connecting once giving every Bot the app. Shape: [`architecture.md` §8](architecture.md#8-connected-apps).

- _Cut 1, done._ Connections. A `connect` Package with one hosted-grant Connection Type per curated app. Connect is the existing `authorize` press and disconnect revokes upstream; `COMPOSIO_API_KEY` is an optional production secret, and absent, nothing connects and the deploy says so.
- _Cut 1b, done._ Connectors, designed. The generic document renderer gave the page text and buttons; Connectors is host chrome over the frame now, and the Connectors document projection is deleted with the renderer that read it.
- _Cut 2, done._ Tools. One Tool Namespace per ready Connection, named for the app, pinned per Turn. Nothing is in the prompt for an app nobody connected; execution carries the deployment key and the account id, so no credential is leased or logged, and a failure after dispatch is reported as an unknown outcome rather than retried.
- _Cut 3, done._ Triggers. A third Routine trigger beside schedule and webhook — `{ kind: "connection", connectionId, triggerType, config }` — whose instance is created at the provider when the Routine is, under an effect id, and deleted with it. One deployment-wide `POST /api/connect/events` door, HMAC-verified with `COMPOSIO_WEBHOOK_SECRET`, routes a `trigger.message` to the owning Bot as a firing keyed by the event id, marks a Routine unavailable on `trigger.disabled`, and marks a Connection failed on `connected_account.expired`. `routine_manage` gains the trigger and a `list_triggers` that offers only connected apps' events. The Routine editor offers those events beside Plugin triggers, as `connection:<connectionId>:<triggerType>`.
- _Cut 4, done._ Conversation authors Routines; the editor goes; Jev may skip a clearly unrelated connected-app event before the conversational model. Four cuts of its own: [`routines-conversation-plan.md`](routines-conversation-plan.md), [ADR 0033](adr/0033-conversation-authored-routines.md).

**12. Plugins.** _Done, in nine steps that each left `main` shippable ([ADR 0026](adr/0026-plugins.md))._ A User customises a Bot by talking to it, and the way a Bot changes is by adding Plugins. Two layers: the deploy holds the loop, the first-party features behind per-Bot flags, the loopbacks and the hook contract; one Dynamic Worker per User holds every Plugin the deployment seeded or a Bot wrote. Storage, network, model and settings are loopback capabilities masked per Bot per Turn; declared hosts and open network access are approved by the User on the Plugin's card, which is the one path by which a Plugin gains reach. The User Durable Object owns the Composition — the installed set, its generations, last known good and the quarantine; the Bot owns its own enable map, approvals and settings. Seeded Plugins are locked, default-on, default-off, admin-gated or installable, and a Plugin may be a Routine trigger source. Shape: [`architecture.md` §5](architecture.md#5-composition).

- _Step 1, done._ The ADR, the terms in `CONTEXT.md`, and the amendments to `AGENTS.md`: the sixth hook, the shape of the `http` grant, provides and consumes, triggers, settings, the per-Bot exception to account-shaped configuration, and the one path by which a Plugin gains reach.

- _Step 2, done._ The descriptor and the Plugin worker contract, decoders and tests only. `PluginDescriptorV1` names loop hooks directly — the action vocabulary and the action-to-hook map are deleted — and carries the `contractVersion` it was built against, `network` (declared hosts or open access, present exactly when the `http` grant is), a bounded settings schema, typed `provides` and `consumes`, and `triggers`. The sixth hook opens to Plugins, and may shape a request but never change `requestId`, `provider`, `model` or the model binding the credential lease hangs off. `core/contracts/plugin-worker.ts` is the boundary of the per-User worker step 3 implements.

- _Step 3, done._ The per-User Plugin worker host. Every Plugin a generation names mounts into one Dynamic Worker per User, behind a generated index that narrows the capability stub into the `ctx` a Plugin author writes against and runs an open hook over every enabled Plugin that declared it — in mount order, each seeing the value the one before it left, and naming any it skipped for the Durable Object to record. Providers mount before consumers. A descriptor mismatch, a retired contract, an unopened grant or a slot refuses one Plugin at `resolve`; a module that does not parse fails the whole worker at `mount`; a health report that differs from its descriptor fails that Plugin alone.

- _Step 4, done._ The generation store moved to the User (`DurableCompositionStore`): the installed Plugin set, its generations, the last known good and the quarantine, reached through the composition RPCs, with pinning as compare-and-swap and a lost race re-read and re-derived. A Bot admits a Turn inside its own storage transaction, which cannot call another object, so every admission goes through `admitTurnV1`, which reads the User's pin and adopts it into the Bot's own mirror. Which of the installed Plugins a Bot runs is its own revisioned enable map, read at every mount.

- _Step 5, done._ Loopback capabilities. `BotCapabilities` is minted once per User, and every call carries an `IsolateScopeV1` that the wrapper takes from the invocation it is serving; the Bot resolves that Turn's authority when called and refuses a scope that is not the Turn it is running, so nothing in the stub can go stale. `storage` and `settings` ship as grants. Network is a loopback `globalOutbound` minted with the union of the enabled Plugins' declared hosts or open access; a host outside the policy is a rejection the Plugin's `fetch` sees, and a worker whose Plugins declared no network has no outbound at all.

- _Step 6, done._ The catalog, seed states, the Plugins page and per-Bot switches. A seeded Plugin is one the deployment ships into every User's Composition with a seed state — `locked`, `default-on`, `default-off` or `admin-gated` — reconciled against the deployment catalog on every read. A Bot's enable map follows the seed rule and also switches off the first-party features a User may turn off per Bot, with the account-wide installation still the precondition; a Bot with Routines off has its occurrences consumed without a Turn, so its clock still advances.

- _Step 6a, done._ The Marketplace is one searchable catalog of models and connectors. Add a model there first; Models lists only what has been added. DeepSeek stays Plugin-served; compiled catalog providers use the same Add command without becoming artifacts.

- _Step 7, done._ Bot authoring, and the approval that makes a Plugin live. The Applet build service gained a Plugin mode that type-checks a module against the SDK, bundles the one file and reads its exports by running it in Miniflare, and ten `plugin_*` tools mount for a Turn only behind the account's admin-held Plugin-authoring feature, with the managed `plugins` Skill going exactly where they go. A publish decodes `plugin.json` with the kernel's own descriptor decoder and refuses a descriptor that disagrees with the built module about tools, hooks, services or triggers. A publish never runs anything: `plugin_publish` and `plugin_enable` write an intent keyed by the Turn's effect id and put an approval card on the Turn's own log, and the settlement settles the intent in the transaction that records the decision. A Plugin a Bot wrote is off for every Bot until a person switches it on, which is what "self-modification never widens authority by itself" means here.

- _Step 8, done._ Plugin triggers. `RoutineTriggerV1` gains `{ kind: "plugin", pluginId, trigger }` beside the webhook kind, and both enter through the same signed webhook door — the same key, digest and replay guard — so every triggered Routine is keyed at creation. The delivery is handed to the Plugin outside any transaction, and the receipt records the drop and its reason, which a replay answers with; two copies of one delivery in flight at once join rather than ask the Plugin twice. The Plugin mounts for that delivery alone under a synthetic Turn identity naming the Routine, and a Plugin that is not in the Composition, is off for this Bot, declares no such trigger or does not mount is a drop with that reason, never a throw. `routine_manage` takes a `pluginTrigger`, and the Routine editor offers an enabled Plugin's triggers by name rather than by id. A template carries a Plugin-triggered Routine as a webhook one — it lands disabled and unkeyed either way.

- _Step 9, done._ The settings slot, failure notices, Work-view itemisation and the contract's current-and-previous rule: `settings.sections` is the one open slot, a failing Plugin is skipped and noticed and turned off at three, a Plugin's model calls are itemised on the Work view, and the app serves the current and the previous hook contract. Shape: [`architecture.md` §5](architecture.md#5-composition).

## Planned: Group Chats replace Projects

Agreed in the Group Chat design walkthrough, and built in the stages at the end of this section. Voice is designed separately, later.

A Group Chat is a conversation between the User and several of their Bots. It replaces **Project** entirely. The Project catalogue and per-Bot membership in the User Durable Object, the `project_create`, `project_join` and `project_leave` tools, the `project` memory scope, the `project-memory` Workspace root and voice's `recall_project` are deleted, not renamed, and existing Project state is discarded as disposable. The Memory engine's `groupChat` scope stays and becomes each Group Chat's shared memory.

**Conversation.**

- **Every message reaches every member.** Each member Bot has the whole thread in its context, whether or not it was asked to reply, so it can follow the conversation.
- **Jev decides who replies.** For every message, Jev chooses which members are triggered: none, one, several or all. There is no post that skips Jev. Its choice is not drawn in the thread; the triggered Bot's Work view records why it ran.
- **The User's @mention always triggers** the Bot named. Jev still decides whether anyone else joins in.
- **Bots address each other in the thread.** A Bot writes `@Name`; the mention is resolved against the members when the message is posted and stored by Bot id, so a rename does not break it. The asking Bot does not wait: its Turn ends when it posts, and the answer is the next message in the thread. There is no fixed cap on Bot-to-Bot Turns. Jev checks every Bot-triggered Turn and stops loops and drift.
- **Bots outside the group** are reached with `bot_message`, which from a Group Chat accepts only non-members. The Exchange marker and its view-only Exchange are drawn in the group thread. `bot_message` in one-to-one chats is unchanged.
- **A Bot may @mention the User**, which sends a push notification. Every other message only counts as unread.

**Steering replaces Supersede, everywhere.** A message sent while a Bot is working waits, and the Bot reads it at its next step boundary. The running chat Turn finishes its model response and every tool call it made, then ends `completed`; the message runs next, with that work in its context and a note that it was unfinished. Nothing already sent to the model is re-issued and nothing in flight is cut off, so the model sees what injecting the message into the running Turn would have shown it. The message does not redirect the work by itself; the Bot decides what to do with it. A message that arrives while the Turn is producing its final answer simply runs next. `/stop` is the only cancel. This applies to one-to-one chats too: Supersede, its drain state and the `superseded` terminal state are removed. A Turn that is not the person's own — answering another Bot, the voice session or a Routine — does not yield; the message runs once it finishes. In a Group Chat, a member's running Turn yields the same way to a new group message and continues its unfinished work in its next group Turn, whether or not Jev triggered it for that message.

**A Bot in a Group Chat.**

- It brings its whole self: its tools, Computer and connected apps, and its Bot, User and Group Chat memory. It sees the group's thread, not its one-to-one history, which it can search on demand.
- It does one thing at a time. A group Turn waits behind the Bot's other work, and the Bot is not drawn as working in the group until its group Turn starts.
- A member Bot may post into a Group Chat from outside it — from its one-to-one chat or a Routine. The post goes through Jev like any other message.
- Its group activity is not marked in its one-to-one thread.

**Membership and lifecycle.**

- The User and their Bots may create a Group Chat, rename it, and add or remove members. Every change is a line in the thread and can be undone. A group has 2 to 8 member Bots.
- A new group is shown as its members' names ("General, Xero Books & Codex") until the User or a Bot names it. A Bot that creates a group names it for its purpose.
- A Bot may archive a Group Chat, and the User may restore it. Only the User deletes one, which removes the thread and the group's memory.
- A Bot that leaves loses access to the group's memory.

**Interface.**

- Every Bot message starts with a badge: a pill filled with the Bot's avatar colour (`avatarCatalog` in `app/flock/shared.ts`) and its name, with black or white text chosen for contrast and a hairline outline on the near-white and near-black colours. Cards a Bot posts carry the same badge. Two Bots of the same character share a colour and are told apart by name.
- A mention is drawn as a chip in the mentioned Bot's colour. The composer's `@` opens a member picker, and the empty composer is addressed to the group by name. The User's messages are drawn as today.
- The working indicator is the one-to-one chat's: each member whose group Turn is running stands at the end of the thread under the sheen, side by side, and leaves when its Turn ends. A queued Bot is not drawn. A Bot a member asked with `bot_message` stands beside that member, smaller, as it does in a one-to-one chat.
- `/stop` stops every member Turn running for this group, and `/stop @Name` stops one. A Bot's work in other chats is untouched. A stop that produced nothing is a marker naming the Bot.
- A member Turn that did not finish is the one-to-one chat's muted line with Retry, on that Bot's side and under its badge. Retry runs that Bot again.
- Group Chats sit in the sidebar among the Bot rows, and are labelled, pinned, ordered and hidden the same way.
- The multiple-avatar component is a row of up to three overlapping avatar stills followed by `+N`. It serves the sidebar row, the pinned tile and the thread header.

**Architecture.**

- Each Group Chat is a `GroupChat` Durable Object holding the ordered message log, its client publication channel, Jev's decisions and the User's read cursor.
- The User Durable Object holds membership, which Memory already checks there, and the list of the User's Group Chats with their sidebar arrangement.
- A member's Turn runs in its own Bot Durable Object, under a Session per group, on the `agent` lane.
- The Channels implementation removed on 2026-09-01 (`ac7870294`, removed in `c2922891c`) is prior art for fan-out with idempotent per-recipient delivery. Its log lived in the User Durable Object; this design gives each group its own object.

**Still open.** Group Chats in voice: a call stays with one Bot until that design. Whether Group Chats later replace `bot_message` and Exchanges in one-to-one chats.

**Build stages.** Each leaves `main` shippable and production Bots able to reply.

- _Stage 1, steering, done._ Supersede is gone from every chat. A user-lane message joins a FIFO user queue (`pending-user-run:`, 32 deep); the loop asks `userMessageWaiting` after every step that would otherwise continue, and a chat Turn on the person's own lane ends there `completed`. Its settlement leaves a `yielded-turn` pending input when it still owed its reply. `supersede-cleanup.ts` rewrote the stored `superseded` runs, rows and replay updates as `cancelled` and removed the retired inputs and single waiting slot. Installed apps still send `supersedes`; it is accepted and dropped until they have updated.
- _Stage 2, the Group Chat core, server only, done._ `app/groups/` and the `GroupChat` Durable Object (`apps/cloudflare/src/group-chat.ts`, migration `v9`). The User object holds the group list, members and sidebar arrangement with receipted commands; the group's object holds the thread, read cursor and each member's Turn, and reads the group from the User object before it acts. Routes: `GET`/`POST /api/groups`, `POST /api/groups/:id/commands` (rename, add and remove members, archive, restore, delete, arrange), `GET /api/groups/:id`, `GET`/`POST /api/groups/:id/messages`, `POST /api/groups/:id/read`, `/stop`, `/retry`, and the `/channel` WebSocket. A member's Turn is admitted with `admitGroupTurn` on the `agent` lane under `group:<id>`, carrying the thread since it last took part and a `group` origin; it is kept out of the member's one-to-one thread, and the group reads it back by id when the Bot nudges it or its alarm fires. A newer message makes a running member Turn yield at its next step boundary; one that yielded unanswered is asked again. Mentions are resolved to Bot ids when posted. Until stage 3 only an @mention asks a member, and a run of Bots asking Bots ends after eight Turns. The routes' wire schemas are in `client-wire.schema.json`.
- _Stage 3, Jev decides who replies, done._ `core/contracts/group-reply-judge.ts`, the labelled eval `app/evals/group-reply.ts` (nine fixtures, all passing against `jev-1.13.0`; run with `bun app/evals/group-reply-run.ts`), and the hosted adapter `app/supervision/group-reply.ts`. Every message is judged once, after it is written: one yes/no per free member who is not the author and not already mentioned, one question whether the message needs anyone besides the members it mentions — so a question to the group is never left unanswered — and, for a member's message that mentions others, whether asking them continues the conversation, loops or drifts. The person's @mentions run at once; a member's run only when Jev says they continue. The judgment is kept in the Group Chat (`group:judgement:<seq>`) and a member Jev asks carries the reason `jev` on its run's origin, which is what its Work view shows. Unavailable — no `JEV_API_KEY`, a failure or a timeout — asks nobody extra and lets a member's mentions run under the bound of eight Bot-started Turns; with Jev there is no fixed cap. A judgment lost to an eviction is written down first and the alarm asks again.
- _Stage 4, the app, done._ `apps/native/lib/groups/`. The group's channel sends one `group/state` frame on connect and on every change; the client reads the thread after the last message it holds, and reads the group again after a rename or membership line. A send is kept before it posts and is sent again under its own command id; a pin, label, order or hide shows at once and is put back if the group refuses it. The sidebar draws groups among the Bot rows under the entry id `group:<id>`, so order, labels and drops are planned over one list, and a group's share of a drop is `group/arrange`. The pane opens with the members' overlapping stills under the header; every Bot message carries its badge, a mention is a chip, the members working stand under the sheen, a member Turn that did not finish has its Retry, an Exchange line opens the view-only Exchange from the Bot that was asked, and a membership or name line can be undone. The composer's `@` offers the members, `/stop` stops every member and `/stop @Name` one. The header's name opens the members sheet: rename, add, remove, archive, restore, delete. Search's Group Chats tab finds a group by name or member, and an archived one opens read-only with Restore. A push carrying `groupId` opens `?group=<id>`, and Android keys its notifications by the group. A Bot a member asked with `bot_message` is not drawn beside it: the group's state frame names only its members.
- _Stage 5, Bots act on groups, done._ `app/groups/agent.ts` gives a Bot, in its own chat and its Routines, `group_list`, `group_create`, `group_update` (rename, add and remove members), `group_archive` and `group_post`, and a `<group_chats>` prompt section naming its groups. Each command's id is derived from the User, Bot, run and call, so a replay after eviction commits once; a post from outside the group is `postFromBot` on the Group Chat, idempotent by its own `o-` message id, and asks members exactly as a member's message does. Inside a group Turn, `bot_message` (Flock's `group-bot-messaging` capability, agent lane) refuses members and asks only Bots outside; the group reads each call back and writes an Exchange line (`bot-message`). A member's `@User` marks its message `mentionsUser`, and the group sends one push per message through the User object's `deliverGroupPush`, whose receipt, presence and FCM payload carry `groupId`.
- _Stage 6, Projects out and group memory in, done._ The Project catalogue and membership, the `project_*` tools and their session events, the `project` scope, the `project-memory` root, voice's `recall_project` and the Plugin memory grant's `project` scope are deleted. `project-events-cleanup.ts` rewrites each Bot's stored Memory events in place (`project` → `group`, `projectId` → `groupId`, the two membership events kept as the Memory Package's call and result), and `project-cleanup.ts` deletes the User object's Project keys, their ledger records and R2 objects, and every `groupChat` scope not keyed by a Group Chat id. The `group` scope is keyed by Group Chat id and authorized by Group Chat membership; a group's Turns inject that group's prepared core and capture their thread for extraction into it, and deleting a group purges its scope. Extraction itself and the outbox that carries a Bot's capture to the User object are still unwired in production, as for every scope, and come with the Memory plan.

## Planned: shared long-term Memory following Hindsight

Agreed during the startup and memory review; implementation is specified in the handoff and has not started.

Use **Hindsight as the reference design for FrockBot's long-term Memory engine**, implemented on our existing Cloudflare architecture with Durable Objects, SQLite and Vectorize. The decision is to build this behaviour into FrockBot; adopting Hindsight's hosted service or PostgreSQL stack is not the selected direction. The [provider comparison](research/hermes-memory-alternatives.md) records the prior art and rationale: evidence-backed consolidation, several complementary recall methods, token budgets and generated topic pages.

Chat and voice use the same logical Memory engine. Scope and kind are separate dimensions:

| Scope      | Ownership and visibility                                                      |
| ---------- | ----------------------------------------------------------------------------- |
| User       | User-wide knowledge available across that User's Bots.                        |
| Bot        | Knowledge belonging to one Bot, including its private conversation decisions. |
| Group Chat | Knowledge shared within that Group Chat, by its members.                      |

Each scope supports facts and experiences with dates and source references, consolidated observations that capture the current understanding and its changes, and browsable topic pages generated from that knowledge. Keep authoritative evidence and the derivation links: topic pages, chronological views and the prepared core are projections, not independently maintained copies of facts. Corrections and forgetting must invalidate dependent views and prevent stale search results from reintroducing obsolete knowledge.

Enforce scope during capture, consolidation, page generation and retrieval. Derived knowledge must not widen access to its sources. Promoting a Bot or Group Chat memory into User scope is an explicit operation; summarising it never grants broader visibility.

Recall follows Hindsight's combination of semantic, keyword, relationship and temporal retrieval, with source expansion when a concise memory is insufficient. Bound retrieval effort separately from the tokens returned. Keep automatic recall and explicit memory tools available throughout a Turn, including when later model steps or tool results reveal a new need. The specific Jev gate and assessment placement remain for design.

Startup loads a small prepared core from the permitted scopes. Extraction, consolidation, topic-page generation and optional reasoning over memories run outside the chat/voice startup path, with durable scheduling for required background work. Prepared views and recalled context need freshness and scope checks, and a bounded shared context budget.

This replaces the long-term Memory design, not the whole conversation system. Working context remains recent messages and tool results; compaction maintains a rolling summary plus the recent tail; original conversation history remains separately recoverable as evidence. The prepared core and recalled memories draw from the same long-term engine for both text and voice.

The [Memory packet](startup-implementation/memory.md) selects the existing Bot DO for Bot scope and existing User DO for User/shared scope, and specifies canonical records, transactions, source invalidation, projections, retrieval budgets and staged cutover. Gemini uses supported blocking Memory tools and transcript-triggered prefetch; guaranteed automatic recall before every relevant voice answer still needs a turn-control decision, because receiving a transcript does not pause generation. The Jev recall gate remains deferred. Shared Memory is each Group Chat's, authorized by Group Chat membership.

The [existing Memory diagrams](research/memory-proposal/README.md) predate this decision and illustrate the earlier recall/write proposal; they are not yet a complete diagram of the selected Hindsight-based design. Its behaviour on our architecture must be verified during implementation; upstream evaluation results do not establish equivalent performance for a port.

## Planned: bounded conversation context with prompt-cache preservation

Agreed during the startup review; implementation is specified in the handoff and has not started. This is the working-conversation counterpart to the [long-term Memory plan](#planned-shared-long-term-memory-following-hindsight); it addresses the history-loading paths identified in the [startup assessment](research/chat-voice-startup.md#conversation-history-loading-walkthrough-findings).

Maintain a durable, directly readable working-context projection for each conversation: the current compaction summary, recent messages and tool results within the context budget, and references to original history. Update it as the conversation progresses so a new Turn can load the required context without reconstructing the full retained journal and all historical model requests. The projection is derived from authoritative conversation records, with explicit version and sequence tracking; it must remain usable and consistent after eviction.

Keep original history independently available for transcript browsing, search, source expansion and audit. Active execution, effect admission and exact recovery records retain their own guarantees. A context read must not depend on unrelated execution recovery or historical maintenance.

Voice obtains its permitted recent-conversation excerpt through a dedicated bounded read instead of fetching a general transcript page and truncating it afterwards. Index voice turns by call and sequence, and unfinished continuity jobs by state/order, so opening and handover read only the required context. Preserve visible-message attribution and the existing boundary around private model/tool scratch. Preserve Gemini Live sessions and their resumption handles; loading context differently must not unnecessarily restart a resumable session.

**Prompt-cache reuse and conversation fidelity are requirements of this change:**

- Keep the compaction summary unchanged between compactions. Append new messages while the context remains within budget; do not introduce a fixed last-N window that drops an old message on every Turn.
- Preserve model-facing message content, roles, order, tool calls/results and their identifiers, provider-specific replay data, system instructions, tool definitions and applicable cache/session settings. The storage optimisation must reproduce the existing assembled context for the same history and policy; changes to pruning or compaction policy require a separate explicit decision.
- Keep stable content at the beginning of the prompt. Add newly recalled memories near the current work rather than repeatedly rewriting an early system-prompt section. Corrections, forgetting and permission changes still take precedence over retaining cached content.
- At compaction, deliberately replace the covered history with the new summary. The changed portion may need processing again; preserve the unchanged prefix before it. Cache availability remains provider-controlled, so correctness never depends on a cache hit.

Verify equivalent model-facing context before and after the storage change, including tool/replay data, long histories, multiple compactions, eviction and recovery. Verify bounded storage reads independently of retained archive size, and preserve voice resumption behaviour. [S2](startup-implementation/context-and-recovery.md#s2-working-context) specifies the projection, absolute Session cursor, separate recovery journal and preservation of existing context budgets; the recovery boundary is agreed below.

## Planned: fast startup with durable background recovery

Agreed during the startup review; implementation is specified in the handoff and has not started. The [wake-up assessment](research/chat-voice-startup.md#wake-up-recovery-walkthrough-findings) records the current paths and the transcript-delivery reliability gap.

Track active/in-flight and pending records directly so those safeguards do not require scanning the archive. Recovery must distinguish work from the previous activation from newly admitted work.

Preserve the rejoin behavior now on main: live drops have a 60-second window; paused/backgrounded calls have a rolling 24-hour window based on the record's `lastSeenAt`. Abandonment uses the record-derived deadline, and a paused rejoin remains asleep without a metered Gemini session. Keep daily allowance rollover independent of this window. Preserve delivery to live calls and keep maintenance batches small enough to yield to interactive work. Memory extraction is already scheduled today; remove the remaining historical scans and deliveries from readiness.

Give call-transcript delivery a durable outbox. Retry the same call ID with a stable delivery payload or retained source reference, using the Bot receiver's existing call-ID deduplication. For chat, durably admit the incoming command and its queue position before resuming the previous Turn's model/tool execution. Retain command idempotency, lane ordering, cancellation, effect fences and the single active Turn. Recovery then reconciles and promotes work under those recorded intentions. Acceptance must not depend on completing unrelated old work; execution may still wait for the reconciliation needed to proceed safely. Combined with the bounded-context plan, admission must avoid full-history reconstruction. Context and transcript reads must not trigger unrelated Turn execution.

Retire completed one-off constructor cleanup after verifying the relevant release receipts. Required cleanup of incompatible state still belongs to its scoped release; do not move unsafe state initialization behind requests or discard unfinished obligations.

Verify during implementation:

- Opening voice and admitting chat do not scan historical backlogs or wait for old cross-Bot deliveries; context remains equivalent under the agreed cache-preservation requirements.
- Eviction around call replacement, job creation, scheduling, delivery and acknowledgement loses neither admitted work nor required wakeups. Duplicate callbacks/deliveries produce one transcript and do not repeat uncertain paid effects.
- Rejoin, replacement, quota checks, live delegation replies, cancellation and lane and queue ordering still hold when recovery races with new input.
- Background jobs make progress without waiting for another user request, preserve unfinished source records, and recover after repeated eviction.

[S3 chat](startup-implementation/context-and-recovery.md#s3-recovery-and-admission) and [S3 voice](startup-implementation/voice.md#s3-voice-recovery) specify indexes, transaction boundaries, crash-safe scheduling and starting batch limits. Follow these directions; report any source/API conflict that would change the agreed behavior instead of silently weakening recovery.
