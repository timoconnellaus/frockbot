# The re-orientation

FrockBot grew a distributed capability operating system around a product that needed a well-built app. Every capability became a Package, the app itself became a 51k-line "plugin", the client split across Vue, Flutter and a third UI language, and the agent loop braided provider I/O together with durable resumption in one 1,785-line function.

This document is the plan to reach the architecture described in [`architecture.md`](architecture.md). It replaces the ADR set, which recorded how the previous shape was reached and is available in git history.

## Target

|                  | Before                                           | After                                   |
| ---------------- | ------------------------------------------------ | --------------------------------------- |
| Packages         | 74, of which 44 plugins                          | ~7 modules                              |
| Clients          | Vue + Flutter + a third UI language              | Flutter, plus web sign-in and marketing |
| Agent loop       | 1,785 lines, provider I/O and durability braided | ~300-line durable loop over the AI SDK  |
| Plugin runtime   | cordis, 158 import sites                         | frock-compose                           |
| Applet authoring | on the User's Computer, via Miniflare            | a cloud build service                   |
| Untrusted code   | every package treated as untrusted               | Bot-authored code and Applets only      |

The seven modules: `core`, `app`, `frock-compose`, `providers`, `computer`, `applets`, `native`.

## Decisions

Settled, and not to be relitigated without a reason that is new:

- **Bot-authored packages stay.** Self-modification is the product, so the loader, generations and grants survive — scoped to untrusted code rather than applied to everything.
- **A tenant is a User.** One Plugin worker per account. A Bot authoring a Plugin installs it for that User; which Bots run it is the Bot's own enable map ([ADR 0026](adr/0026-plugins.md)).
- **The base has no DI container.** Ordinary imports. This is what stops the collapse from quietly undoing itself.
- **The Computer stays, as a Package.** One provider-neutral `ComputerHost` interface with Fly behind it, so another host can be substituted. It leaves the Applet authoring path entirely.
- **Applets follow cloudflare-os.** Source in object storage, built by a cloud service, mounted from an immutable artifact into a Durable Object facet. The runtime is already correct; only authoring moves.
- **Providers go through the AI SDK.** Request translation, streaming, tool-call accumulation and usage reporting are bought, not written, behind one narrow `ModelProvider` interface.
- **At-most-once by idempotency key.** Forensic reconciliation of dispatched effects is removed.
- **Multi-bot stays.** A single default avatar for now; the wearable system is deferred, not deleted.
- **Vue is deleted per surface**, in the same change that lands its Flutter replacement, so `main` always ships a working product.
- **Frock Compose is ours.** `frock-compose/` carries no upstream provenance and is not tracked against another repository. It is free to diverge — which is what makes the Flutter `ViewNode` renderer a first-class part of it rather than a fork.

## Order

Each step leaves `main` shippable.

**1. Documentation reset.** _Done._ One page of principles, one architecture document, this plan. The ADR set, the slice plans and the superseded research are removed.

**2. Cut what is dead.** _Done._ The Electron and WebView shells, their capability packages, the architecture checks and two prototypes: 11 packages, 14,548 lines.

**3. Park the deferred features.** _Done._ MCP and Composio came out first — roughly 11.4k lines, no owned Durable Object class and no owned tables. MCP returns later as a plugin over the `http` grant. Composio came back as first-party app code instead (step 11): it is the deployment's own connection backend, not untrusted code, and the `http` grant is how a plugin reaches an account through it.

The same ruling cleared two leftovers from that cut: Bot templates carried an `mcpServers` field and Routines a connection-trigger kind whose only provider was Composio, both kept only because changing a stored shape looked like a migration. Both are gone, along with the trigger path they served.

`plugin-voice` and `plugin-billing` are out too, in their own tag. Voice owned the `VoiceSession` Durable Object class; a `deleted_classes` migration retires it, because a `new_sqlite_classes` entry is immutable once applied.

**4. Providers onto the AI SDK.** _Done._ Replace the hand-written provider stack with one interface over `ai` + `@ai-sdk/*`. The AI SDK's OpenAI-compatible model now owns SSE framing, tool-call accumulation and the non-streamed body; request mapping, failure classification and the deadlines stayed, because the Frock AI gateway and Ollama's native endpoint reach that seam with a stream and no URL. An Anthropic provider proves the seam is open — the provider set was a hardcoded two-entry map. The 2,526-line Ollama connection file is untouched: it is durable-record ceremony, not transport, and belongs to step 7.

**5. Split the agent loop.** _Done._ `index.ts` is 853 lines beside `model-request.ts`, `resume.ts`, `tool-execution.ts`, `errors.ts` and `runtime.ts`. The extraction changed no test, which is what proved it changed no behaviour.

Forensic reconciliation is gone. Every external effect that matters carries an idempotency key — a model call's `requestId`, a tool call's `occurrenceId` — and is re-issued under that key rather than investigated afterwards. No Turn parks waiting for a person to resolve it. `admitEffect` and supersede fencing survive and now run before every dispatch, re-issues included.

The seam that retrieved a lost response from the provider is deleted outright: `LlmReconciliationCapability`, `ctx.llm.reconcile`, and all four provider implementations. It was declared, implemented everywhere and called by nobody.

**6. Frock Compose replaces cordis.** _In progress, in three cuts that each leave `main` shippable._ Wire the extension points named in `AGENTS.md` — and only those — and delete `kernel-composition`, the manifest system, `plugin-authoring`, `plugin-package-catalog` and `plugin-package-publisher`.

- _6a, done._ The three packages, with the seams that existed only for them: the Bot authoring quota and artifact store, the Catalog install path, the publisher's User revisions, and `apps/cloudflare-bundler`, whose one caller was authoring. 14,900 lines. Authoring returns with the step 8 build service; nothing else produces an artifact-bearing member now, so the only isolate member is the Applets Package.
- _6b, done._ cordis is gone. The registries are plain classes built by ordinary imports; every first-party plugin is a feature function the app lists in order; the loop takes one typed hook list (`LoopHooksV1`) that replaces the waterfall and emit bus, and the isolate host appends a Bot-authored package's hooks to the same list after the app's. The resident runtime, the desktop shell contracts and the two `@cordisjs/plugin-webui` entries went with it: none had a live caller. The manifests stay until 6c.
- _6c, done._ Frock Compose hosts the untrusted layer only. The Package Catalog went first: first-party code ships with the deploy, so it had nothing to distribute. The Applets tools became an ordinary first-party feature with first-party iframe pages, and the Worker Loader host moved into Frock Compose. Then the manifests went: a first-party plugin is a `PackageDefinitionV1` the foundation lists, and an untrusted member carries a `PluginDescriptorV1` naming its tools, the loop seams it wraps, the grants, the slots and the three context keys — nothing else. Generations list untrusted members only and live in `core/durable`; `kernel-composition` is deleted. Nothing produces an untrusted member until the step 8 build service exists, so tests are the narrowed contract's only caller for now.

**7. Collapse the plugins into the app.** _Done._ The 21 first-party plugins are directories under `app/`, and the seven modules are what is on disk: `core`, `app`, `frock-compose`, `providers`, `computer`, `applets` and `native`. `applications/` is gone, and the eight per-plugin vite builds went with it — nothing read their output, and the app's own build bundles the clients from source.

The shell backend is now a state object and feature modules: `ShellBotStateV1` is what every feature function takes as its first argument, and each group — Subagents, isolate grants, the Applets host, settings, notifications, routines, approvals, the machine seam, run reads, debug, Skills, the Turn and its Composition mount — is an ordinary exported function the Bot Durable Object calls directly. `app/shell/backend.ts` went from 6,111 lines to 204: the state construction, a hook table of one-line lambdas, and the forwards the recovery tests still drive.

Frock Compose was the last module to be cut. `frock-compose/` is one flat workspace holding the isolate host and its wrapper, and the framework-agnostic Compose kernel beside it — which nothing had imported since cordis went — is deleted. The core-to-compose cycle went with it: what an untrusted member declares about itself is a contract, so `PluginDescriptorV1` and the four vocabularies it names are `core/contracts/plugin-descriptor.ts` and the failure phases are `core/durable/composition/failure.ts`, beside the activation that records them. `core` now imports `@frockbot/core/` and nothing else; the app builds the host `activateCompositionV1` mounts through (`app/shell/backend-composition.ts`), and `packages/` holds only the two client libraries step 9 deletes.

**8. Applets off the Computer.** _Done._ `apps/applet-build` is a fifth deployable: no routes, an `APPLET_BUILD` service binding, a `node:24-slim` container with no egress running the SDK's own five-stage pipeline over source posted inline, answering with diagnostics or with a content-addressed artifact the app Worker hash-verifies and stores. The Bot authors with four tools — `applet_files`, `applet_read_file`, `applet_write_file` and `applet_check`, whose preview URL is the existing anonymous artifact route — and `applet_publish` builds from the Workspace prefix rather than from a Sprite.

The Computer is out of the loop entirely. Applets declares no durable root to it, so nothing is mirrored onto a Sprite; the `applets` provisioning phase, the `applet` PATH shim, the unpinned `@frockbot/applet-sdk@latest` install, the two doctor checks and the `applet dev` preview-tab branch are gone, and provisioning is five phases. The SDK lost its CLI and its `bin` with them — the service is the only thing that builds an Applet — and the end-to-end Workspace seed door went the same way, its last caller having been the `dist/` seeding a publish no longer reads. The last cut was 488 insertions against 1,807 deletions; the step as a whole is 7,354 insertions against 2,543 deletions, and what it bought was a build service and a Computer with no Applet-shaped operation left in it.

**9. Flutter to parity, Vue out.** _Done._ The long pole. One Flutter client, on the phone and on the web — `bot.frockbot.com` is an app behind sign-in, so Flutter Web's first-load cost buys one codebase instead of two. Each surface ported, then its Vue original deleted in the same change. Includes the ViewNode renderer — six node types — which replaces the third UI language as the way a plugin renders.

The flip served the Flutter web build at `/` and took the Vue client out in the same change: 216 files and 42,949 lines, `packages/` with them, so the repository holds one client and no client libraries beside it. What a plugin renders is the ViewNode document the server projects, not a second UI language, and the app Worker's own document is the Flutter bootstrap carrying the identity attributes the Vue shell used to read. The one thing the browser cost is the app origin's Content-Security-Policy: `script-src` gains `'wasm-unsafe-eval'` and `style-src` gains `'unsafe-inline'`, which is what CanvasKit and the engine's injected styles need. The artifact origin's policy is untouched, which is the one that matters — it is where untrusted code runs.

- _PR 1, done._ The Flutter app compiles for the web. `dart:io` leaves `lib/` except inside `*_io.dart`, and a test keeps it there; four seams pick an implementation by conditional import — HTTP and the socket, the credential, the sign-in door and the durable store. The phone's behaviour and the transport's public API are unchanged, and CI builds `flutter build web`.
- _PR 3, done._ The shell. `apps/native/lib/shell/` is the Bot list, the conversation and the right panel: three responsive tiers at the stylesheet's own two widths, a slot registry — `right-panel`, `overlays`, `header-actions` — that is the Flutter analogue of `<k-slot>`, and `lib/main.dart` reduced to the app entry and the sign-in door. The Vue shell's rules are ported with its tests: transcript ordering by Turn, the supersede drain, the composer draft and the two questions Send and Try again each ask. Tool receipts leave the thread for a Work view opened from the message. Every interactive widget carries a `Semantics(identifier:)` from one file, which is what a Playwright spec can select on a canvas. No Vue is deleted yet: Flutter Web is not what the site serves until the flip.
- _PR 4, done._ `ViewNode` and `ViewDocument` are in the client wire schema and rendered by `apps/native/lib/view/` — six node types, the budgets checked before a widget is built, and `embed` naming a host-owned region rather than shipping markup. `PluginDescriptorV1` gains account-scoped `views`. The third UI language went out in the same change: its two Flutter packages, the vendored `0.9.1` spec, the catalog adapter, `FormPreview`, its three wire types and the qualification-form route beneath them — 2,065 lines. Nothing produces a document until the surfaces that use it land, so the renderer's callers are its tests and a development-only sample page.

- _PRs 5 and 6, done._ Settings. The server projects the `SettingsFrame` it already produces as a `ViewDocument` (`app/settings/settings-document.ts`, reached with `?as=document` on the two settings routes), so the Flutter settings page is a host over `ViewDocumentView` rather than a second renderer of typed fields — `lib/settings/page.dart` went from 522 lines to 300 and the generic frame renderer inside it is gone. This is where `ViewController.dispatch` got its real route: an action's declared input names the section, and the page turns it back into the `SettingsChangeCommand` the route already takes. Bot settings is a new surface — the GrokBot order, extras under Advanced, in the `right-panel` slot at wide widths and a page on the phone — and the sidebar footer's sheet is the Vue profile trigger's menu. The model picker writes. No Vue is deleted: the frame is unchanged and `bot-settings.e2e.ts` still passes against it.

- _PR 7, done._ Connectors and Plugins. Two more projections in the settings-document family: `connectionsDocumentV1` over a widened `ConnectionsFrame`, and `pluginsDocumentV1` over a new `PluginsFrame`, both reached with `?as=document`. The frames carry what the Vue surfaces had assembled client-side from the catalog and the User's settings — a provider's accounts, whether another may be connected, the Connection settings a type declares, and the "Model in use" line, which is now written where the settings live. Connectors and Plugins are hosts over `ViewDocumentView`; `lib/view/surface.dart` is the chrome and the per-revision controller both share, so a page is a controller and a title. The Flutter client authorizes and revokes in the app rather than handing off to a browser, and opens one only for a provider whose door is a web flow. `SettingField` gains a `secret` kind: the document seeds it null, the widget never shows a value, and the typed characters go out on the action input to the credential route and are dropped from the controller the moment it is answered. Admin is a small surface of its own over `/api/admin/policy` — the deployment's signups switch — offered in the profile sheet only to an account `/api/identity` calls an admin. No Vue is deleted: both frames are additive and `connect-ollama.e2e.ts` and `defaults.e2e.ts` still pass against the web app.

- _PR 8, done._ Routines, Audit, Search and conversations. Two more projections in the document family, both reached with `?as=document`: `routinesDocumentV1` over a `RoutinesFrame` — one Bot's Routines and its completion inbox in one read, because a client that had to ask twice could show a list and a badge that disagreed — and `auditDocumentV1` over an `AuditFrame`. Neither frame carries a shared revision counter, because a Routine is its own durable record and an audit page is a projection: each projection derives one from its own bytes, so the host adopts a fresh controller exactly when what it is showing has changed. `lib/routines/` and `lib/audit/` are hosts over `ViewDocumentView`; Routines is the second entry in the `right-panel` slot beside Bot settings, which the region now shows one at a time rather than stacking, and a page on the phone. A Routine's firings are a run log, and one firing opens on the same Work view a message in the thread opens. The completions badge is in workspace navigation and matches `RoutineInboxBadge.vue`: a count, and "Mark all read" that means the entries the reader could see rather than the wire's "acknowledge everything". Search is the backend index rather than the Bot-list `SearchDelegate` the shell cut left — `lib/search/`, debounced, every state named, and a chosen hit opens its Bot and brings its Turn into view. The Bot has one continuous, automatically compacting chat; the Session's announcements — a rename, a compaction — are `LineRole.system` lines in the thread, which the `/turns` projection already carried and no client read. No Vue is deleted: both new projections are additive, and `routines.e2e.ts` and `continuous-chat.e2e.ts` still pass against the web app.

- _PR 9, done._ Flock, templates, machines and the Routine editor. Creating a Bot is the sidebar's own gesture rather than a handoff to Manage Bots: a sheet with a sheep, a name and the first thing to say to it, whose command is written to the durable store before it is sent and re-fenced on the directory revision a conflict reported, so a lost reply finishes the Bot that was asked for rather than making a second one. The avatar is the Flock's art — the background layer and the canonical sheep, seven WebPs the app bundles — and the same sheep is drawn wherever a Bot is: the sidebar row, its pinned tile, the thread, the working row and Bot settings. Within the single-default-avatar rule the background is the whole of the choice — made when the Bot is created and changed later from its own settings, which is all that survives of the Vue wardrobe's edit half; the recipe's three wearable bands stay at the catalogue's neutral roots, so a Bot this app makes is still one the wardrobe can dress when wearables return. Archiving, restoring and deleting are `BotDangerZone` inside Bot settings' Advanced, which is the seam `FlockDangerZone.vue` draws — the Flock owns the directory the change is to, so it contributes the control rather than the settings surface rebuilding it — over one retained lifecycle command per account, which Manage Bots now shares rather than keeping a second copy of.

  Three more projections in the document family. `machinesDocumentV1` over the registry (`GET /api/machines?as=document`); `templateSharesDocumentV1` and `templateImportsDocumentV1` over the two template routes, two documents because they are two surfaces — what this Bot is packed into is per-Bot and what this account has imported is not. Which Bot a pack is of is never in a document: the host is showing one, and names it when it turns the press into a command, the same way the Routines host does. The Routines document grows an editor — one form, seeded by the read, for a new Routine or for the one `?edit=` names, because a form per Routine would be a second copy of every prompt and would spend one of the thirty-two declared actions on each of them. Which form is open is navigation, so it is asked for on the read and written nowhere.

  One rule arrived with all three: **a secret the authority minted once is never in a document.** A webhook key and a pairing code exist on a receipt and nowhere else — the Bot keeps only a digest — and a document can be read twice, so the host holds each in `ViewSurfacePage`'s banner for as long as the person is looking at it. That is the same reasoning `SettingField.secret` already carried, from the other direction.

  Creating a Bot and its danger zone are host chrome rather than projections, and deliberately: the sheep is bundled art rather than an `embed`'s https image, the create command fences on a directory revision that `ViewController` has no way to express, and the lifecycle route answers `pending` for a saga that has not settled. No Vue is deleted: the three new projections are additive, and `delete-bot.e2e.ts`, `bot-info.e2e.ts` and `admin.e2e.ts` still pass against the web app.

- _PR 10a, done._ Applets, the Computer and Package pages. The Applet canvas is `apps/native/lib/applets/` on the routes `applets-client.ts` reads — the directory and the Session's focus, the source as the Bot writes it, the progress line projected from the thread, the four failure states with the retry each deserves, and the live Applet over the code once a generation is active. The Computer is `lib/computer/`: the card's presence, its live-while-working stream and snapshot settling, and the full-window viewer with Take control behind a confirmation. Package entries are `lib/packages/`: the entry projection, and the postMessage bridge a first-party or Bot-authored page speaks, reached from the Bot header and from Bot settings. All three are framed web pages through one seam, `lib/view/host_frame.dart` — a platform view over a sandboxed `<iframe>` on the web, a hardened WebView on the phone — and all three are host chrome rather than projections, because each holds a credential minted per reader and a document can be read twice. `embed`'s two reserved frame names now resolve to those widgets through a `HostViewFrames` scope, so a plugin naming a region gets whatever host surface is above it and the reserved region everywhere else. The `/native-fallback` path is gone whole: `lib/extensions/fallback.dart`, `apps/cloudflare/src/native-fallback.ts` and its gateway route, the `/api/native/applets/:id/bootstrap` route and the RPC behind it, and `FallbackBootstrap` from the wire schema — nothing else reached any of them. Two things the local stack needed to prove any of it: `native-dev` mints an `APPLET_VIEWER_SECRET` the way it already mints the build token — without one the token route answers a definitive 503 and the canvas is right to say Applets do not work here — and `AppletViewerToken.socketUrl` accepts a loopback `ws://` beside `wss://`, the same allowance `AuthorizationUrl` already carries, because the native decoder otherwise refuses every token a local stack can mint. No Vue is deleted: the four specs it would touch still pass against the web app.

**11. Connected apps.** _In progress, in three cuts that each leave `main` shippable._ One integration layer for the services a User connects FrockBot to, as `app/connect` (architecture §8): the provider behind it is invisible plumbing, each app is its own Connectors row, and connecting once gives every Bot the app.

- _Cut 1, done._ Connections. A `connect` Package with one hosted-grant Connection Type per curated app (Gmail, Google Calendar, Google Drive, GitHub, Slack, Notion). - _Cut 1b, done._ Connectors, designed. The generic document renderer gave the page text and buttons; Tim wanted one Connectors page that reads well for every kind of connector. **12. Plugins.** _In progress, in nine steps that each leave `main` shippable ([ADR 0026](adr/0026-plugins.md))._ A User customises a Bot by talking to it, and the way a Bot changes is by adding Plugins. Two layers: the deploy holds the loop, the first-party features behind per-Bot flags, the loopbacks and the hook contract; one Dynamic Worker per User holds every Plugin the deployment seeded or a Bot wrote, keyed by the hash of its artifacts and the contract version so a release never reloads it. Six hooks answer with plain patches. Storage, network, model and settings are loopback capabilities masked per Bot per Turn; declared hosts and open network access are approved by the User on the Plugin's card. The User Durable Object owns the generation; the Bot owns its enable map, approvals, settings and quarantine. Seeded Plugins are locked, default-on, default-off or admin-gated. The Bot authors through a `plugin_*` Tool Namespace and a managed Skill, builds through the Applet build service, and activates through an Approval card. Plugins can be Routine trigger sources behind an app-owned `/hooks/<token>` route. The page is "Plugins".

- _Step 1, done._ The ADR, the terms in `CONTEXT.md`, and the amendments to `AGENTS.md`: the sixth hook, the shape of the `http` grant, provides and consumes, triggers, settings, the per-Bot exception to account-shaped configuration, and the one path by which a Plugin gains reach.

- _Step 2, done._ The descriptor and the Plugin worker contract, decoders and tests only. `PluginDescriptorV1` names loop hooks directly — the action vocabulary and the action-to-hook map are deleted — carries the `contractVersion` it was built against, and gains `network` (declared hosts or open access, present exactly when the `http` grant is), a bounded settings schema, typed `provides` and `consumes`, and `triggers`. `servedPluginContractVersionsV1()` is the current-and-previous pair. The sixth hook opens to Plugins: `agent/request` is an isolate hook, its `LoopHooksV1` signature is widened with turn and step like `agent/tool-exposure`, and a replacement may shape the request but never change `requestId`, `provider`, `model` or the model binding the credential lease hangs off. `core/contracts/plugin-worker.ts` is the boundary of the per-User worker step 3 implements: module-set hash and loader id, per-plugin health, hook invocations carrying the Bot's enabled list, results naming the Plugins the index skipped, tool invocations by Plugin, and trigger receipt. No host speaks it yet and nothing produces a Plugin, so tests are its only caller.
