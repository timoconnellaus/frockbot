# Hermes compaction persistence and recovery

## Scope

Inspected NousResearch/Hermes Agent at commit [`524041b9d0437cd4424a524af4b9e26145e69ab0`](https://github.com/NousResearch/hermes-agent/tree/524041b9d0437cd4424a524af4b9e26145e69ab0), retrieved 2026-09-22. This note covers the main summary path and what persists across compaction, restart, and repeated compactions. It reports no new measurements.

## Default persistence model

The default `ContextCompressor` performs **in-place compaction under one stable session ID**. It replaces the live prompt transcript with protected head messages, one structured summary/handoff, and a recent tail. In the same SQLite transaction, `archive_and_compact()` marks the old active rows inactive and inserts the compacted view as the new active generation. Rows genuinely summarized away become `active=0, compacted=1`; originals of verbatim tail rows carried into the new generation become `active=0, compacted=0` so search does not return the same tail once per compaction ([documented default](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/developer-guide/context-compression-and-caching.md#L273-L282), [`archive_and_compact`](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/hermes_state_messages.py#L665-L725)).

The rewrite is non-destructive for summarized content: archived rows stay in `state.db` and its FTS indexes. Only the new active rows are loaded into the model context. A protected message can legitimately exist in both an archived and active generation; this is intentional rather than a duplicate-write defect ([generation semantics](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/developer-guide/session-storage.md#L56-L77)).

Commit safety is stronger than a best-effort transcript rewrite:

- A watermark captured before the slow summary call preserves messages appended concurrently; they are cloned byte-for-byte after the compacted generation rather than summarized away.
- The compression lease is verified inside the transaction so a stale worker cannot overwrite a newer winner.
- If the atomic commit raises, Hermes restores the pre-compression in-memory list and leaves the old database rows active. It does not publish a half-compacted transcript ([atomic commit and rollback](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/conversation_compression.py#L3616-L3697)).

## Repeated-compaction continuity

Hermes maintains a rolling `_previous_summary`. On a later compaction, the summarizer receives that prior checkpoint plus only the new middle turns and is instructed to update state: preserve still-relevant information, add new completions, move work between active/completed sections, and remove clearly obsolete material ([iterative prompt](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/context_compressor.py#L3603-L3704)).

When the normal threshold is crossed, Hermes first prunes eligible old tool results, then chooses the protected head and recent tail and makes one auxiliary request to summarize the middle. Default `lean` mode bounds that tail from the model context size, adds bounded verbatim user excerpts and a mechanically extracted identifier index, and appends recovery instructions ([main compression phases](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/context_compressor.py#L5036-L5094), [summary request](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/context_compressor.py#L3603-L3664), [lean assembly](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/context_compressor.py#L838-L1002)).

That continuity does not rely only on process memory. Before compacting, Hermes scans the full live transcript for prior compaction handoffs and rehydrates `_previous_summary` from them. It deliberately scans beyond the new compression window, excludes old handoff rows from the new summarizer input, and folds their content into the replacement summary. If there is no handoff in the transcript, a leftover `_previous_summary` is treated as cross-session contamination and discarded ([handoff rehydration](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/context_compressor.py#L4688-L4728)). This is what lets repeated compaction continue after an agent/gateway restart.

The live checkpoint itself is still lossy. In the default lean mode Hermes reduces that risk with:

- a structured narrative and detailed chronological log from one summarizer call;
- recent real user messages quoted verbatim under a character budget;
- a mechanically extracted exact-identifier index for paths, SHAs, errors, URLs, and similar anchors;
- a deterministic `session_search` recovery instruction naming the current session ID.

The recovery footer explicitly says the compacted rows remain preserved and directs the model to retrieve exact commands, file contents, errors, or earlier reasoning instead of guessing ([verbatim user and recovery sections](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/context_compressor.py#L838-L925), [lean-mode description](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/developer-guide/context-compression-and-caching.md#L255-L264)).

## How archived evidence is recovered

`session_search` deliberately distinguishes compaction archives from undo/rewind history. An inactive row is discoverable from the current session only when `compacted=1`; inactive rewind rows with `compacted=0` remain hidden. Discovery normally suppresses hits from the current live session, but permits a hit on an archived row under that same session ID because it is no longer in the model's active context ([storage-state predicate](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/tools/session_search_tool.py#L214-L233), [current-session exception](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/tools/session_search_tool.py#L388-L415)). A returned match carries its message ID; the model can scroll around that exact archived row for surrounding evidence.

This makes the compacted summary a retrieval map, not the sole record. Recovery is nevertheless **query-driven rather than automatic**: the summary and anchor index must preserve enough clues for the model to formulate an FTS5 query, or the user/model must otherwise know what to search for. Details absent from the summary are durable but not guaranteed to be recalled without a useful query.

## Legacy rotation and retention caveats

Setting `compression.in_place: false` selects the legacy model: the old session ends with reason `compression`, a child continuation is created with `parent_session_id`, and repeated compactions form a lineage chain. `session_search` resolves that chain to its root for deduplication while retaining the raw owning session ID needed to pair a hit with its message ID ([legacy option](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/developer-guide/context-compression-and-caching.md#L273-L282), [lineage resolution](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/tools/session_search_tool.py#L102-L123)). This mode remains supported but is not the default.

Archived compaction rows are durable SQLite state, not immutable archival storage. Ended inactive sessions are pruned after `sessions.retention_days` (90 days by default) unless auto-pruning is disabled or retention is raised. Active sessions are not pruned by that startup sweep, so a continuously active in-place session retains its compacted rows; after it ends, normal retention policy applies ([retention policy](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/user-guide/sessions.md#L1073-L1088)). Resume/export also have configurable 20,000-message guards. Desktop cold resume pages only the active tip, whereas plain interactive resume can materialize the whole compression lineage and may be refused if the configured limit is exceeded ([resume guards](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/user-guide/sessions.md#L1045-L1071)).

## Optional modes are different contracts

- **Context-engine plugins:** one explicitly selected engine can replace the built-in compressor and own selection, compaction, and persistence policy. Plugins are never auto-activated, so claims above apply to the default `context.engine: compressor`, not to an arbitrary engine such as an LCM plugin ([context-engine selection](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/developer-guide/context-engine-plugin.md#L9-L24)).
- **Codex app-server runtime:** the remote Codex thread owns context. Hermes asks the app-server to compact and records boundary/counter events, but does not rewrite its local transcript; the visible `state.db` transcript remains intact ([app-server behavior](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/developer-guide/context-compression-and-caching.md#L396-L416)).
- **Native OpenAI Responses compaction:** opt-in supported routes return an opaque encrypted compaction item. Hermes stores it in the assistant replay sidecar and replays the newest checkpoint; bounded user messages and whole local summaries are retained around it because the server ignores everything preceding a replayed checkpoint. The local compressor remains armed as fallback, and changing issuer/endpoint drops incompatible checkpoints ([native mode](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/developer-guide/context-compression-and-caching.md#L418-L451), [checkpoint replay rules](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/native_compaction.py#L196-L230)). The checkpoint is cumulative provider-owned state, not a human-readable replacement for Hermes' archived SQLite transcript.
- **Micro-compaction:** this built-in option is off by default. When enabled, it incrementally absorbs the oldest unabsorbed exchange into a rolling summary after completed turns at a configurable cadence. Each pass is an additional model call and rewrites already-sent history, so frequent passes invalidate the provider prompt-cache prefix; Hermes documents this as the main opt-in tradeoff ([behavior and cost](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/developer-guide/micro-compaction.md#L17-L33), [configuration and cache effect](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/developer-guide/micro-compaction.md#L176-L225)).

Hermes' default compaction is a transactional, generational view over a durable transcript: SQLite keeps original summarized rows searchable; the active generation carries a rolling handoff plus recent evidence; repeated passes rehydrate and update that handoff; exact recovery comes through FTS5. Its continuity guarantee is therefore “summary plus retrievable originals while retention keeps them,” not “the summary is lossless.”
