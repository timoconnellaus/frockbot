# Chat model dispatch assessment

Inspected 2026-09-22 at `4a1bdd9ea7b0c74e60cfced0ae6e4d7fd98b8a8a`, after rebasing onto `origin/main`. Scope: the path from prepared chat context through provider dispatch to the first committed `send_to_user`. This is a source assessment and recommendations for discussion, not newly agreed decisions or runtime implementation. No model calls, startup measurements, dependency changes or deployments were made. The checkout's identity with production was not established.

The existing [startup assessment](chat-voice-startup.md), [preparation plan](../plan.md#planned-reusable-runtime-preparation-and-persistent-tool-catalogs) and [delivery plan](../plan.md#planned-direct-delivery-of-committed-chat-updates) cover adjacent stages. This note identifies additional work inside model dispatch and commitment; it does not reopen those decisions.

## Main findings

- **Ordinary chat does not make a compulsory preliminary Jev or routing-model call.** Turn supervision has contracts and an adapter but is not wired into the loop. Even that adapter's `startTurn` returns a local default. Frock AI's Auto choice is deterministic request routing to a configured Gateway route or concrete model, not an application-owned inference to select a model. Gateway-side route configuration was not inspected, so this is not a claim about its internal upstream behavior. Sources: [unwired supervision milestone](../jev-supervision-plan.md#L386), [Jev adapter](../../app/supervision/jev.ts#L96), [model selection](../../providers/frock-ai/catalog.ts#L92), [gateway dispatch](../../apps/cloudflare/src/frock-ai.ts#L184).
- **A complete model step is currently required before any tool executes.** The loop consumes the whole stream, records the assistant response, flushes it and settles held model resources before calling `send_to_user`. OpenAI-compatible and catalog decoders also withhold tool calls until the terminal response. This is separate from the notification/REST delay after a send commits. Sources: [stream consumption](../../core/agent-loop/model-request.ts#L234), [assistant commitment and tool execution](../../core/agent-loop/index.ts#L555), [OpenAI-compatible completion](../../providers/openai-compatible/index.ts#L944), [catalog completion](../../providers/catalog/runtime.ts#L118).
- **The clearest additional simplifications are bounded active-effect state and less fragmented persistence.** Dispatch admission reads the current run's event range to check one intent. Every private text chunk queues persistence, and every persistence transaction reads the current run again. These are structural dependencies, not measured claims about their elapsed cost. Sources: [effect admission](../../app/shell/turn.ts#L587), [append queue](../../core/contracts/session.ts#L281), [event persistence](../../core/durable/authority.ts#L1719).
- **Provider startup differs materially by adapter.** Frock AI uses deployment credentials; connected providers lease credentials from the User authority. Most compiled catalogs are local, while Radius reloads remote gateway configuration during each dispatch. Optional OAuth refresh or unknown-model resolution can add network work before inference. Sources: [Frock AI host](../../apps/cloudflare/src/frock-ai.ts#L120), [catalog dispatch](../../providers/catalog/runtime.ts#L193), [catalog loading](../../providers/catalog/models.ts#L18), [credential admission](../../providers/model-connections/user.ts#L2206), [OAuth refresh](../../providers/catalog/user.ts#L119).

## Prepared context to provider dispatch

The runtime already has a selected provider/model and Connection generation when this stage begins. Mounting validates unavailable bindings and refuses an admitted request whose provider, model or Connection generation differs from the mounted binding. A Plugin-served provider must come from the account's installed, pinned deployment artifact. This selection is configuration resolution, not a model judgment. Sources: [binding validation](../../app/shell/runtime-mount.ts#L680), [provider Plugin selection](../../app/shell/runtime-mount.ts#L102), [agent options](../../app/agent-runtime.ts#L195).

The remaining common path is ordered as follows:

### Provider-specific work

**Frock AI.** The adapter checks its Connection identity/generation, translates the request and maps Auto to `dynamic/<route>` when the compat Gateway transport is configured, or to the compiled concrete model when it is not. Schema requests have a separate deterministic Auto mapping. The host makes one Gateway POST, or calls the native Gateway binding. It uses deployment-owned credentials, so this path does not request a per-User credential lease. Sources: [provider](../../providers/frock-ai/runtime.ts#L142), [mapping](../../providers/frock-ai/catalog.ts#L92), [host](../../apps/cloudflare/src/frock-ai.ts#L120).

**Compiled catalog providers.** The adapter awaits a Connection credential lease, validates its effect/generation/expiry, opens the sealed credential, loads its provider catalog and selects the requested model. Builtin catalog lookup is local. Radius's alternative branch awaits `loadRadiusGatewayConfig`; the runtime calls that branch for every model dispatch. Then the adapter starts the provider stream with SDK retries disabled and a request-ID idempotency header; Bedrock has a separate transport branch. Sources: [dispatch](../../providers/catalog/runtime.ts#L193), [catalog source](../../providers/catalog/models.ts#L18), [stream options](../../providers/catalog/runtime.ts#L274).

**Ollama Cloud.** It awaits the same kind of lease and secret opening, caches that authorization only for the request, and then opens its OpenAI-compatible stream. A separate native structured-output path is conditional on the endpoint and requested format. It does not perform a second conversational inference to select a model. Source: [authorization and dispatch](../../providers/ollama-cloud/runtime.ts#L122).

**Provider Plugins, including the seeded DeepSeek adapter.** The host checks the already-selected binding and creates a one-use dispatch ticket. The Plugin composes the body and calls the host's model transport. The host validates ticket scope, durable intent, active authority, duplicate/uncertain dispatch history and body limits; reads current account configuration; leases and opens the credential; then sends the one fixed-route upstream request. The Plugin never receives the credential or chooses an unrestricted destination. These isolation and authority checks are not equivalent to the first-party application-routing layer discussed elsewhere. Sources: [provider boundary](../../app/shell/plugin-model-provider.ts#L507), [DeepSeek transport call](../../app/plugins/seeded/deepseek/plugin.ts#L207), [transport checks](../../app/isolates/model-transport.ts#L354), [live configuration and dispatch](../../app/isolates/model-transport.ts#L509).

**Connection lease work.** The common connected-provider lease path expires leases, checks replay, validates current Package/Connection authority, invokes the optional OAuth refresh hook, and resolves an unknown model through the provider before finally leasing its secret. Model metadata already present in the Connection avoids that resolution. OAuth refresh is conditional on expiry; neither refresh nor catalog discovery is an inference. Sources: [lease path](../../providers/model-connections/user.ts#L2206), [unknown-model resolution](../../providers/model-connections/user.ts#L2292), [final authority check](../../providers/model-connections/user.ts#L2339), [OAuth expiry policy](../../providers/catalog/user.ts#L121).

### Jev, compaction and extra requests

The loop constructs an `AgentLoop` from prompt, model, tools, Session and hooks; it has no `TurnSupervisor` dependency. A repository search of non-test TypeScript found no invocations of the hosted supervisor chooser, `startTurn` or `reviewStep`. The plan explicitly marks this wiring as pending. The existing `reviewStep` adapter would call Jev sequentially for mutating calls and allow reads locally, but describing those calls as current chat startup work would be incorrect. Sources: [runtime composition](../../app/agent-runtime.ts#L131), [loop](../../core/agent-loop/index.ts#L479), [adapter](../../app/supervision/jev.ts#L102), [delivery sequence](../jev-supervision-plan.md#L386).

Compaction can make a real model call, but its hook starts detached work after `turn/end`. It does not deliberately insert a summarizer ahead of the first chat request. A previous compaction can still make the next admission await its abort/unwind to preserve one Session writer; the await is for relinquishing that writer, not for obtaining a new summary. Sources: [compaction hook](../../app/shell/agent.ts#L674), [yield](../../app/shell/compaction-scheduler.ts#L67), [admission](../../app/shell/turn.ts#L103).

A subsequent model call can be legitimate work after tools, a delivery-repair call when the model wrote private text instead of sending, or a classified retry/fallback. None is an obligatory preliminary inference for an ordinary greeting. The existing greeting integration test asserts one provider request, one send and a completed Turn; it was read, not rerun here, and it establishes no elapsed-time result. Sources: [delivery repair](../../app/shell/delivery.ts#L97), [retry/fallback](../../core/agent-loop/model-request.ts#L168), [greeting assertion](../../apps/cloudflare/test/integration/reply-latency.integration.ts#L15). Account-installed Plugin hooks may intentionally do extra work under their grants; the compiled path cannot promise that arbitrary extensions add none.

## Provider output to the first committed send

1. **Accumulate the complete model step.** Text deltas become private `assistant/chunk` events; tool-call events are accumulated in memory. The OpenAI-compatible decoder additionally waits for a valid terminal stream before emitting its accumulated calls, and the compiled catalog decoder emits them only from `done`. The SDK `doStream` used by the former is supplied a local response-body fetcher; it is decoding the existing response, not issuing a second upstream inference. Sources: [loop accumulation](../../core/agent-loop/model-request.ts#L250), [private chunks](../../core/agent-loop/model-request.ts#L351), [terminal decoder](../../providers/openai-compatible/index.ts#L944), [local SDK fetcher](../../providers/openai-compatible/index.ts#L798), [catalog decoder](../../providers/catalog/runtime.ts#L118).
2. **Finish provider accounting and commit the response.** With billing enabled, the provider wrapper awaits successful usage settlement in its generator's `finally` before iteration finishes. The loop then appends usage and the complete `assistant/message`, awaits all pending persistence, checks cancellation, and awaits `modelOutcomeCommitted` hooks, including connected-provider credential settlement. Only then does it execute tools. Sources: [billing settlement](../../app/billing/model.ts#L224), [usage](../../core/agent-loop/model-request.ts#L300), [response commitment](../../core/agent-loop/index.ts#L567), [catalog credential settlement](../../providers/catalog/runtime.ts#L333), [Plugin credential settlement](../../app/shell/backend-composition.ts#L705).
3. **Prepare, journal and admit the send occurrence.** Top-level tools execute serially in provider order. For each, the registry prepares/validates the call; the loop persists `tool/call`, awaits the effect fence, then executes. Thus a slow tool placed before a send delays that send. Sources: [tool sequence](../../core/agent-loop/tool-execution.ts#L27), [occurrence](../../core/agent-loop/tool-execution.ts#L124).
4. **Commit the explicit message.** `send_to_user` validates the complete disposition/payload, deduplicates by occurrence ID, appends `send/to-user` and flushes it. This flush is the first committed-send milestone. Card drawing, post-tool hooks, `tool/result`, later calls, step completion and Turn completion can follow it. Rich payload rendering may have further card work, but the durable send already exists. Sources: [send validation](../../app/shell/agent.ts#L480), [send commitment](../../app/shell/agent.ts#L84), [post-tool hooks](../../core/tools/tools.ts#L758), [result commitment](../../core/agent-loop/tool-execution.ts#L91).

`batch` does not remove model composition time: its full arguments still arrive as one completed model proposal. Once executing, it journals every child intent in declared order, then overlaps unordered calls with one ordered chain. Sends are ordered effects; the first send can commit while independent batch work continues. The batch waits for all dispatched children before returning its aggregate result, but that wait is not a condition for a send already committed to appear. Sources: [batch intent writes](../../core/agent-loop/tool-execution.ts#L323), [parallel/ordered execution](../../core/agent-loop/tool-execution.ts#L337), [send ordering declaration](../../app/shell/agent.ts#L492).

The agreed socket-delivery redesign begins at that committed-send milestone. It cannot reveal a reply before the current loop executes and commits the tool. A concise first acknowledgement can be produced by the model as its own first step, followed by work, under the existing prompt contract; automatically inventing acknowledgements or exposing private text would change that contract. Source: [conversation instructions](../../app/shell/agent.ts#L258).

## Recommended simplifications, subject to design

**Use bounded active-effect state for dispatch and persistence.** Keep an indexed, durable summary of the open request/step, tool occurrences and effect admissions with the run header, derived atomically from journal changes. Admission should check that small state plus current Stop/supersede authority, loading exact payloads by reference only when execution/recovery needs them. Today `admitRunEffect` reads the active event range; `persistRunEvents` rehydrates it again, even for a private chunk. This is a current-run counterpart to the already agreed bounded-history work. Keep the original exact journal, contiguity checks and reconstruction path; a projection is not a second source of truth. Sources: [admission hydration](../../app/shell/turn.ts#L602), [persistence](../../core/durable/authority.ts#L1719), [run hydration](../../core/durable/authority.ts#L1095).

**Batch private stream persistence, preserving durable barriers.** `Session.append` schedules one persistence callback per append; `assistant/chunk` uses it for every text delta. Each callback opens a transaction, updates the log/run, evaluates record hooks and refreshes the recovery alarm. Coalesce pending private chunks into bounded event batches without changing their content/order, and make `flush` drain them at every existing consequential boundary. Keep partial-output buffering explicitly bounded and its recovery semantics explicit rather than silently assuming volatile data is durable. Maintain one alarm owner and avoid recomputing unrelated scheduling state per chunk when an already-durable wakeup still covers the obligation. This is more focused than removing required request/send commits. Sources: [append and flush](../../core/contracts/session.ts#L281), [persistence transaction](../../core/durable/authority.ts#L1719), [alarm refresh](../../core/durable/authority.ts#L1335).

**Keep model metadata preparation outside normal dispatch.** Reuse a revisioned provider descriptor/catalog for Radius rather than downloading its configuration every model step. Prepare known model metadata on selection/refresh, retaining bounded first-use discovery for a genuinely unknown model. Current live Connection authority and credential expiry checks must remain; cached metadata cannot authorize use of a revoked Connection. The Plugin transport's full configuration read followed by lease RPC is a candidate for one narrow host-authorized dispatch preparation operation that returns coherent route metadata and a scoped lease. Do not merge away the Plugin isolate or expose its secret. Sources: [Radius lookup](../../providers/catalog/models.ts#L18), [lease authority](../../providers/model-connections/user.ts#L2417), [Plugin configuration/lease sequence](../../app/isolates/model-transport.ts#L509).

**Separate response commitment from recoverable settlement work where warranted.** Spend reservation must precede inference. Final usage settlement and credential release are currently awaited before any send, even when a complete provider result is available. A durable obligation containing the exact usage/outcome could allow response commitment and sends to proceed while idempotent settlement is completed by the existing scheduler. This requires explicit recovery, retained reservations until settlement, quota correctness for subsequent work and durable cleanup; replacing the awaits with detached promises is not safe. It is a larger accounting change than batching local writes and should not be presented as an already approved optimization. Sources: [reservation](../../app/billing/model.ts#L163), [settlement](../../app/billing/model.ts#L224), [settlement failure behavior](../../core/agent-loop/index.ts#L624).

**Keep whole-response completion for now.** Executing an early-looking `send_to_user` while the provider is still emitting is not a safe local shortcut. Calls need complete validated arguments; the current journal derives occurrences from a complete `assistant/message`; retries must not re-send visible effects; batch order, provider terminal failures and replay metadata need defined semantics. The planned Jev enforcement also reviews complete proposals. Incremental committed calls would therefore be a separate loop/protocol design, not part of the already agreed direct socket delivery. Sources: [journal occurrence creation](../../core/contracts/session.ts#L97), [decoder terminal validation](../../providers/openai-compatible/index.ts#L988), [planned review boundary](../jev-supervision-plan.md#L415).

Retain the essential guards throughout: exact durable model/tool intent before dispatch, atomic Stop/supersede fencing, current identity/grant/Connection checks, spend admission, provider-specific idempotency and uncertain-outcome handling, complete argument validation, ordered/deduplicated sends, and commitment before publication. A shared request key alone does not establish that every upstream provider deduplicates; preserve the actual transport and billing defenses rather than relying on the generic model-request comment. Sources: [effect fence](../../app/shell/turn.ts#L587), [billing duplicate refusal](../../app/billing/model.ts#L194), [Plugin uncertainty](../../app/shell/plugin-model-provider.ts#L638), [send deduplication](../../app/shell/agent.ts#L121).
