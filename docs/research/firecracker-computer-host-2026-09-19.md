# Firecracker as FrockBot's Computer host

**Recommendation: keep Firecracker as the preferred isolation substrate for a later bare-metal host, not the implementation for the five-User DigitalOcean pilot.** It fits `ComputerHostV1` well and gives each User a real VM boundary with unusually little VMM overhead. It does not, however, replace the Kubernetes/Agent Sandbox control plane: FrockBot would have to build the guest image and agent, VM supervisor, networking, storage, snapshots, viewer routing, host hardening and recovery machinery itself.

Sources checked 19 September 2026. Facts below come from the Firecracker project and Linux KVM documentation; FrockBot conclusions are marked **[D]** for design inference and **[U]** for an unknown that needs a prototype.

## What Firecracker gives us

Firecracker is a Linux/KVM virtual machine monitor, with exactly one microVM per Firecracker process. It deliberately exposes a small device model and a host-side HTTP API over a Unix socket. The API configures vCPUs, memory, a kernel, file-backed block devices, TAP-backed network interfaces, vsock and rate limiters, then starts the guest ([design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md), [API schema](https://github.com/firecracker-microvm/firecracker/blob/main/src/firecracker/swagger/firecracker.yaml)).

That is an attractive boundary for untrusted Computer workloads. KVM provides the hardware-virtualization boundary; default per-thread seccomp filters, the Firecracker jailer, namespaces, cgroups, chroot/pivot-root and privilege dropping add defence in depth. The production guidance says to use the jailer or stronger equivalent constraints, allocate a distinct unprivileged UID/GID per VM, bound resources, patch host/guest kernels and microcode, disable KSM, and consider disabling SMT for stronger tenant separation ([sandboxing design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md#sandboxing), [jailer](https://github.com/firecracker-microvm/firecracker/blob/main/docs/jailer.md), [production host setup](https://github.com/firecracker-microvm/firecracker/blob/main/docs/prod-host-setup.md)).

Its published, tightly conditioned specification is also promising: for a tuned 1-vCPU, 128 MiB minimal guest, VMM threads add at most 5 MiB and `InstanceStart` reaches `/sbin/init` within 125 ms. Guest memory and the real workload are additional, and vsock/configuration can raise overhead, so these are not end-to-end desktop figures ([specification](https://github.com/firecracker-microvm/firecracker/blob/main/SPECIFICATION.md#supported-container-workload-platforms)). **[D]** Chromium, Xvfb and the profile dominate FrockBot's memory budget; Firecracker improves isolation without making five active desktops fit comfortably in 8 GiB.

## What FrockBot would still own

Firecracker is not a sandbox service or fleet manager.

- **Host eligibility.** It needs x86_64 or aarch64 Linux with read/write `/dev/kvm`; Firecracker recommends checking with `tools/devtool checkenv`, and its published test matrix is AWS bare metal ([getting started](https://github.com/firecracker-microvm/firecracker/blob/main/docs/getting-started.md), [tested platforms](https://github.com/firecracker-microvm/firecracker/blob/main/README.md#tested-platforms)). KVM itself is accessed through `/dev/kvm` ioctls ([Linux KVM API](https://docs.kernel.org/virt/kvm/api.html)). Current validated host kernels are 5.10, 6.1 and 6.18 with 4K pages ([kernel policy](https://github.com/firecracker-microvm/firecracker/blob/main/docs/kernel-policy.md)). **[D]** The planned DigitalOcean Droplet must not be assumed suitable merely because it is Linux: `/dev/kvm`, nested-virtualization behaviour and production support must be proven on the exact SKU. A bare-metal worker is the clean target.
- **Guest image and control.** A VM needs a separately built/versioned guest kernel and root filesystem containing an init system ([rootfs and kernel setup](https://github.com/firecracker-microvm/firecracker/blob/main/docs/rootfs-and-kernel-setup.md)). Firecracker ships no FrockBot guest agent. Virtio-vsock is the natural transport: Firecracker bridges host Unix sockets to guest AF_VSOCK sockets, provided the relevant host and guest kernel options are enabled ([vsock](https://github.com/firecracker-microvm/firecracker/blob/main/docs/vsock.md)). **[D]** The agent would implement exec, file transfer, browser actions, screenshots, process inspection, doctor, leases and graceful shutdown; the host gateway would translate the existing v1 protocol to it.
- **Networking and policy.** Each virtio-net device terminates in a host TAP. The operator supplies addressing, routing/NAT and namespaces. Firecracker does no traffic filtering; its own production guide requires host firewalls for restricted destinations ([network design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md#host-networking-integration), [network setup](https://github.com/firecracker-microvm/firecracker/blob/main/docs/network-setup.md), [egress guidance](https://github.com/firecracker-microvm/firecracker/blob/main/docs/prod-host-setup.md#filtering-guest-egress-network-traffic)). **[D]** FrockBot therefore still needs per-User network namespaces, deny rules for host/private/control-plane ranges, controlled Internet egress, and a gateway for HTTPS/WebSocket viewer traffic. Xvfb/noVNC can remain inside the guest; Firecracker need not emulate a GPU.
- **Fleet operations.** **[D]** FrockBot must own admission, placement, process supervision, image rollout, jail creation and cleanup, per-VM UID/GID allocation, TAP/IPAM, health, logs, disk quotas, backup and teardown. The small Firecracker API makes that supervisor tractable, but it is a new infrastructure product, not an adapter.

`firecracker-containerd` is not a shortcut I would choose for this slice. Its official project adds a custom containerd, runtime, rootfs builder and in-guest agent, while explicitly saying multi-tenant use is at the user's own risk and retaining substantial packaging/orchestration roadmap work ([project README](https://github.com/firecracker-microvm/firecracker-containerd/blob/main/README.md), [agent design](https://github.com/firecracker-microvm/firecracker-containerd/blob/main/docs/agent.md)). **[D]** It solves a general container-runtime problem that FrockBot does not need; a narrow FrockBot agent over vsock is easier to audit.

## Persistence and hibernation

Normal persistence is straightforward: Firecracker block devices are host files, so each User can have a durable ext4 data disk while the immutable kernel/rootfs comes from the shipped image ([storage design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md#storage)). That is a good match for the current per-User Computer and its browser profile.

Full snapshots can preserve guest memory plus KVM/device state, which could retain open browser tabs and processes across hibernation. Restores use a private, demand-paged mapping of the memory file with copy-on-write pages, enabling fast load, but the memory file must remain available for the lifetime of the resumed VM. Firecracker does not package or manage snapshots, and block-device files are separate artifacts the operator must copy and protect ([snapshot support](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)). Diff snapshots remain Developer Preview.

Snapshots are less portable than they first appear. Cross-host-kernel restore is considered unstable; CPU features must remain invariant, snapshots cannot cross CPU architectures or Intel/AMD, and the original block paths, TAP names and vsock resources must be recreated or explicitly overridden. Network continuity is not guaranteed and open vsock connections close on resume ([snapshot versioning](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/versioning.md), [snapshot limitations](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md#limitations)). Snapshot files are trusted inputs and need authentication, encryption and lifecycle management.

**[D]** Treat a Firecracker snapshot as a same-host hibernation cache, never FrockBot's durable source of truth. Durable turns stay in the Bot Durable Object; the data disk is backed up independently to R2; a missing or incompatible snapshot falls back to booting the guest and restoring its disk. The viewer and guest-agent channels always reconnect after resume. This preserves the repository's current recovery contract while allowing a later optimization that can keep live browser state.

There are two materially different ways to buy this: rent an ordinary VM that exposes nested KVM and operate Firecracker ourselves, or buy a managed Firecracker-backed sandbox. The second is much closer to the Computer product FrockBot needs, but replaces direct Firecracker control with the provider's API.

### Managed Firecracker-backed platforms

1. **E2B is the closest product match.** Its managed service gives each sandbox its own Firecracker microVM and kernel, exposes shell/files/processes/network, advertises a full streamed desktop for Computer Use, and preserves filesystem and memory across pause/resume. It is available managed in US/EU/APAC and as BYOC on AWS or GCP ([E2B platform](https://e2b.dev/), [security model](https://e2b.dev/security)). The trade is accepting E2B's sandbox contract instead of owning Firecracker: normal active sessions cap at 24 hours on Pro, pause/resume is still labelled beta in the SDK, and FrockBot must verify durable-volume semantics, egress enforcement, viewer integration, regional data handling and pricing ([SDK lifecycle](https://e2b.dev/docs/sdk-reference/js-sdk/v2.6.2/sandbox)). **[D]** This deserves a proof before building any nested-Firecracker control plane.
2. **Fly Machines is the strongest general managed microVM primitive.** Fly explicitly describes Machines as Firecracker VMs, supports create/start/stop/suspend/delete through a REST API, accepts container images, and offers host-local persistent NVMe volumes and volume snapshots ([Firecracker workload guide](https://fly.io/docs/machines/guides-examples/functions-with-machines/), [Machines API](https://fly.io/docs/machines/api/), [Volumes](https://fly.io/docs/volumes/)). It does not expose the raw Firecracker API, guest kernel, vsock setup or Firecracker snapshot format; a Machine can mount only one volume and that volume is tied to a physical host ([Machine resource](https://fly.io/docs/machines/api/machines-resource/)). **[D]** It could host the guest agent and desktop, but its storage/placement and trust-control fit need a prototype.

AWS Lambda and Fargate use Firecracker internally, but do not expose a persistent general-purpose microVM lifecycle suitable for `ComputerHostV1`; they are not alternatives here. **[D]** The actionable shortlist is therefore: E2B first if a managed dependency is acceptable; Fly Machines second; otherwise Vultr VX1 for a Sydney self-operated proof, or AWS/GCE when their more explicit KVM contract is worth the price. None of the generic nested-VM choices should be called production-supported Firecracker without FrockBot's own qualification and an explicit support answer from the provider.

## Cursor's Grok Bot precedent (checked 19 September 2026)

Cursor explicitly says that Grok Bot uses **one persistent Firecracker microVM per User**, with its own kernel, memory and virtual devices; every Bot belonging to that User shares the same Computer ([Grok Bot security FAQ](https://prod.cursor.com/docs/grok-bot/security-faq), [Teams architecture](https://prod.cursor.com/docs/grok-bot/teams)). Cursor hosts and operates those Computers in the United States today and does not support on-premises or bring-your-own-image deployment ([security FAQ](https://prod.cursor.com/docs/grok-bot/security-faq)). This is direct confirmation that Firecracker is the isolation substrate, not evidence that Cursor buys E2B, Fly Machines or another managed Firecracker service. Cursor does not publicly identify Grok Bot's underlying host provider or say whether Firecracker runs on bare metal or nested virtualization.

Cursor's Composer 2 paper separately describes **Anyrun**, the internal compute platform used for Cloud Agents and Automations, as a multi-cluster scheduler whose pods are dedicated Firecracker VMs with browser/GUI support, filesystem and memory snapshots, live migration and controlled egress ([Composer 2 paper, section 6.2](https://cursor.com/resources/Composer2.pdf)). The Grok Bot reference files observed in this repository call its default runtime a "brokered anyrun pod" ([parity evidence](../grokbot-parity.md#the-two-shipped-reference-docs)), so the best-supported reconstruction is a Cursor-operated Anyrun control plane around Firecracker. **[D]** The public Composer paper does not itself name Grok Bot as an Anyrun consumer, so that control-plane link is strong corroboration rather than a separate public product guarantee.

## Fixed-price servers for self-operated Firecracker (checked 19 September 2026)

For five continuously running Computers, fixed-price bare metal is the natural way to make Firecracker's live memory resizing economically useful. Firecracker can return hot-unplugged guest memory to the host and idle guests consume little CPU, allowing the fixed host to be packed more densely; neither operation reduces the host's monthly price ([memory hotplug](https://github.com/firecracker-microvm/firecracker/blob/main/docs/memory-hotplug.md)). Firecracker requires a Linux host with KVM and read/write `/dev/kvm`, which a root-controlled x86 bare-metal server can provide when CPU virtualization is enabled ([host requirements](https://github.com/firecracker-microvm/firecracker/blob/main/docs/getting-started.md)).

**[D]** Five 2.5 GiB guest envelopes need 12.5 GiB before the host, filesystem cache and burst headroom. A 32 GiB server is a workable minimum when only one or two browsers are busy; 64 GiB is the much safer production-pilot shape. Four physical cores can oversubscribe mostly idle guests, while six to eight cores gives better protection against coincident browser work.

Hetzner Cloud is not an alternative: Hetzner explicitly disables nested virtualization there ([Cloud FAQ](https://docs.hetzner.com/cloud/servers/faq/)).

**[D] Recommendation:** for an EU-hosted proof, use Scaleway `EM-A610R-NVMe` if 32 GiB is enough in the load test, or Hetzner AX41 limited/Auction for 64 GiB and more burst headroom. Choose OVH or Leaseweb only when Sydney placement is worth the premium; of those, OVH currently has the clearest publicly verified 32 GiB configuration. Confidence is **high** that dedicated x86 hosts from all four providers can expose native KVM and run Firecracker, **high** in the cited list prices at the check date, and **medium** in stock availability and the exact Leaseweb Australian configuration. A single server remains a physical failure domain with no managed live migration, so use mirrored local disks, off-host R2 backups, monitoring and a tested cold restore; adding a second host for availability approximately doubles the compute line item.

## Cost of a genuinely always-running Computer (checked 19 September 2026)

The important requirement is stronger than “the Computer remains addressable”: a User may leave a process running and it must continue to execute. A stopped, suspended, paused or cold Computer does not meet that requirement, even if its disk or RAM can later be restored. There is consequently no legitimate scale-to-zero saving in this comparison. Dynamic downsizing is not a substitute either: EC2 and GCE machine-type changes require a stop/start, Daytona requires a stop before reducing CPU or memory, and a cold Sprite restarts rather than continuously executing the old process ([EC2 stop/start](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/how-ec2-instance-stop-start-works.html), [GCE stop/start](https://cloud.google.com/compute/docs/instances/stop-start-instance), [Daytona scaling](https://www.daytona.io/docs/en/scale/), [Sprites lifecycle](https://docs.sprites.dev/concepts/lifecycle/)).

The shared-host estimates use 4 vCPU/16 GiB: enough memory for five 2.5 GiB envelopes plus a small host margin, with CPU oversubscribed on the expectation that no more than two Users are busy at once. Managed services are priced per User at the smallest published allocation that meets or exceeds 1 vCPU/2.5 GiB. These are infrastructure prices, not total product cost.

If managed Firecracker isolation is wanted now, prototype Fly Machines first at roughly $81/month for five; if raw Firecracker control is required, GCE is marginally cheaper than AWS for a continuously running 4 vCPU/16 GiB nested host after its automatic sustained-use discount. The nested-host price difference is nowhere near enough to pay for building and operating FrockBot's own Firecracker control plane. Firecracker is principally an isolation decision, not a five-User cost optimization.

## Is Firecracker the right technology?

**[D] Firecracker is the right long-term isolation primitive if FrockBot values maximum density and a deliberately small VM device surface more than transparent cross-host mobility. It is not obviously the right first fleet manager for a small team.** The strict requirement—a real, always-running Linux Computer per User, executing untrusted code—rules out scale-to-zero products and makes an independent guest kernel valuable. The remaining choice is therefore less “VM or container?” than “build a narrow Firecracker control plane, or adopt a more complete VM manager with a somewhat heavier VMM?”

The QEMU comparison should not be dismissed merely because QEMU is larger. Its own security model explicitly treats the guest, disk images and migration stream as untrusted and requires the management layer to run it unprivileged and apply SELinux/AppArmor, namespaces, cgroups and seccomp. Firecracker makes that attack surface much smaller; Incus makes the surrounding operational surface much smaller. Those are different optimisations.

Incus changes the storage conclusion as well. With direct Firecracker, one Vultr volume per host is useful mostly for whole-host replacement, while a per-User move needs a bespoke disk copy plus memory snapshot/restore. Incus/QEMU can migrate a running VM whose root disk is on non-shared storage, so local NVMe becomes viable without giving up planned rebalancing. This does not make a Vultr host failure recoverable: local disks still need off-host backups, and automatic Incus healing requires shared storage and fencing to avoid split-brain/data corruption ([Incus storage in clusters](https://linuxcontainers.org/incus/docs/main/howto/cluster_config_storage/), [cluster healing](https://linuxcontainers.org/incus/docs/main/howto/cluster_manage/)).

### VX1 local NVMe versus NVMe Block Storage

At the same 240 GB capacity, **price does not decide this choice**. Vultr's public Plans API returned $87.60/month for `vx1-g-4c-16g` and $116.80/month for `vx1-m-4c-32gb`; adding 240 GB of NVMe Block at Vultr's $0.10/GB-month rate produces $111.60 and $140.80. The corresponding local-NVMe plans were $111.69 and $140.89—only $0.09/month more in either case ([public Plans API](https://api.vultr.com/v2/plans), [NVMe Block price and limits](https://blogs.vultr.com/block-storage-upgraded); checked 2026-09-19).

The performance trade is much larger. Vultr's own NVMe Block tests used `fio`, direct asynchronous I/O, queue depth 4 and four jobs, although its example replication job confusingly says `numjobs=16`. The published sustained ceiling is 10,000 IOPS or 400 MB/s per volume, with a credit-based burst of up to 15,000 IOPS or 600 MB/s for up to 60 seconds. Its measured means were approximately 10,000 IOPS/40 MiB/s/2.7–3.2 ms at 4 KiB and 6,000 IOPS/381 MiB/s/4–5 ms at 64 KiB. Those are ceilings rather than an SLA because the redundant network backend is shared ([Vultr Block benchmark and method](https://docs.vultr.com/products/storage/block-storage/storage-performance-block-storage), [performance caveat](https://docs.vultr.com/support/products/storage/what-are-the-performance-expectations-for-block-storage)).

The best independent VX1 result found is one VPSBenchmarks run of a 4 vCPU/16 GiB/240 GB local-NVMe instance in New Jersey on 2025-10-21. Its YABS `fio` used two libaio workers, direct I/O and a 50/50 random read/write workload:

| Block size | Local NVMe observed, read + write | NVMe Block published mean | Local/block ratio |
| ---------- | --------------------------------: | ------------------------: | ----------------: |
| 4 KiB      |        327,065 IOPS; 1,308.3 MB/s |   ~10,000 IOPS; ~40 MiB/s |       ~32.7× IOPS |
| 64 KiB     |         46,544 IOPS; 2,978.9 MB/s |    ~6,000 IOPS; 381 MiB/s |         ~7.5–7.8× |
| 512 KiB    |          7,301 IOPS; 3,738.2 MB/s |      ~750 IOPS; 381 MiB/s |         ~9.4–9.7× |
| 1 MiB      |          4,324 IOPS; 4,429.0 MB/s |      ~380 IOPS; 381 MiB/s |       ~11.1–11.4× |

The same independent run's buffered, synchronous Sysbench tests reported 4 KiB average latency of 0.09 ms for reads, 0.03 ms for writes and 0.05 ms for mixed I/O, with p95 of 0.10, 0.07 and 0.11 ms respectively. That indicates a large latency advantage over network block storage, but it is **not an apples-to-apples latency ratio**: the local figures are buffered Sysbench results, while Vultr's 2.7–3.2 ms Block figure is direct asynchronous `fio` under queue depth. The throughput comparison is also one local sample in a different region and month against Vultr's cross-plan Block mean, and YABS reports the sum of simultaneous reads and writes. It is useful as an order-of-magnitude bound, not a purchase guarantee ([independent YABS result](https://www.vpsbenchmarks.com/yabs/vultr-4c-16gb-20251021-tg8483), [independent Sysbench result](https://www.vpsbenchmarks.com/trials/vultr_performance_trial_21Oct2025/sysbench)).

**[D] Incus implication:** if every User VM's disk image shares one host Block volume, all package installs, Git operations, browser-profile writes and builds share that volume's 10,000-IOPS/400-MB/s envelope. Six light Users may still feel fine, but two or three concurrent disk-heavy operations can expose the 3 ms-class small-I/O latency and shared cap. Incus per-VM I/O limits can stop one noisy User taking the whole allowance, but cannot increase it. Local NVMe is therefore the better UX default for an oversubscribed Incus host; use off-host backups and Incus non-shared-storage migration for durability and planned moves. A mixed design—durable Block for host/control-plane state and local NVMe for User VM disks—buys recovery flexibility without putting every interactive filesystem operation on network storage. Validate this with the real Computer image in Sydney because neither source measures nested QEMU guests or multi-tenant contention: run identical direct-I/O `fio` tests at queue depths 1 and 16, record synchronous-write p50/p95/p99 latency, then repeat while two guest VMs perform package installs.

### Recommended decision path

1. **Keep the current gVisor pilot path** while FrockBot has five known Users, but make compatibility an explicit test rather than an assumption. It gives the most honest memory overcommit and does not depend on nested virtualization.
2. **On one VX1 proof host, run the real Computer workload in both a jailed Firecracker VM and an Incus VM.** Measure idle resident memory, Chromium interaction latency, package/build I/O, two noisy Users, reclaim behaviour and failure recovery. Verify `/dev/kvm` first; Vultr's “customer virtualization” statement is not a Firecracker or Incus certification.
3. **Before buying a five-host pool, perform one Incus non-shared-storage live migration between two VX1 hosts.** Confirm the User's process, browser session, agent and viewer connection survive; measure migration traffic, pause time and the spare headroom required on the destination. Also test the current Incus rebalancer with conservative thresholds and cooldowns.
4. **Choose Incus VMs unless Firecracker demonstrates a material density or security advantage that pays for a custom control plane.** Choose direct Firecracker when a reconnect during rare moves is acceptable and its measured density win is important. Add Cloud Hypervisor to the proof only if Incus/QEMU is too heavy but transparent live migration remains non-negotiable.
5. Keep `ComputerHostV1` above all three. The guest agent and durable-data contract should remain VMM-neutral, with VM memory treated as continuity state rather than the authoritative backup.

**[D] Crisp recommendation:** for the newly stated five-host, deliberately oversubscribed and telemetry-rebalanced design, start with **Incus VMs on VX1**, not direct Firecracker. Firecracker is still the better end-state candidate if measurements show that Incus/QEMU's extra footprint materially hurts per-User cost, but direct Firecracker would make FrockBot build the very scheduler and migration machinery that Incus now supplies. If relocation becomes rare after applying CPU, memory and I/O limits, the decision can flip back to Firecracker.

## Recommendation and proof gate

Do not replace the chosen DigitalOcean Kubernetes/gVisor pilot with Firecracker now. Keep the `ComputerHostV1` and guest runtime shaped so a Firecracker implementation remains possible, then revisit it when either (a) the threat model requires a hardware VM boundary, (b) a bare-metal Hetzner fleet is justified, or (c) snapshot-backed desktop continuity becomes a product requirement.

Before choosing it, run one bounded bare-metal prototype that proves:

1. the exact host passes Firecracker's environment check and the intended kernel/CPU template supports repeatable snapshot restore;
2. one jailed VM boots the real Chromium/Xvfb/noVNC image and a minimal vsock agent satisfies exec, files, browser, screenshot and viewer paths;
3. per-VM netns/TAP rules block other Users, host services, metadata and private/control-plane ranges while permitted egress still works;
4. five idle and two concurrently active desktops fit the intended node without unacceptable pressure or viewer latency;
5. persistent-disk backup/restore works independently of snapshots; and
6. snapshot resume reconnects the agent and viewer, while an incompatible snapshot safely falls back to a normal boot.

If that succeeds, Firecracker is a credible `computer/firecracker` Package and likely the cleanest long-term self-hosted isolation boundary. Until then, it is a promising substrate—not a shorter path to shipping the Computer.
