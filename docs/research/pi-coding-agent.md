# Research: pi coding agent — bare-minimum core and extension model, for FrockBot

## Summary

Pi is a local Node/Bun terminal harness whose published kernel is three packages — a provider-neutral LLM layer (`pi-ai`), a tool-calling agent loop with an event stream (`pi-agent-core`), and a CLI/harness (`pi-coding-agent`) that owns sessions, resources, and modes. Almost everything a comparable agent bakes in — sub-agents, plan mode, MCP, permission prompts, to-dos, background bash, sandboxing — is deliberately absent and delegated to TypeScript **extensions**, **skills**, **prompt templates**, **themes**, and installable **pi packages**. FrockBot should copy pi's four-tool floor, its single extension factory contract (`(pi: ExtensionAPI) => void | Promise<void>`), its append-only tree-structured session log with self-contained compaction checkpoints, its state-in-`details` reconstruction rule, its progressive-disclosure skill loading, its trust-gated project-resource split, and its explicit "not a sandbox" honesty. It should **not** copy pi's `jiti`-based arbitrary-TypeScript loading, its in-process `/reload` semantics, its per-user filesystem as the resource authority, or its assumption that a process outlives a session.

Everything below marked **[local-process]** is true because pi is a Node process with a user-writable filesystem and full user permissions. Everything marked **[transferable]** is a principle that survives translation to an evictable Durable Object + Dynamic Worker + Sprite design.

## Findings

1. **The published kernel is three packages, and the loop package is genuinely small (positive, high).** The monorepo root README names three primary components: `packages/ai` "Unified multi-provider LLM API", `packages/agent` "Agent runtime with tool calling and state management", `packages/coding-agent` "Interactive coding agent CLI". `pi-agent-core`'s own README describes itself as "Stateful agent with tool execution and event streaming" and documents the entire loop as a fixed event sequence — `agent_start → turn_start → message_start/update/end → tool_execution_start/update/end → turn_end → agent_end`. Its only structural seams are `transformContext()` (prune/inject), `convertToLlm()` (required; maps `AgentMessage` to what a provider accepts), `beforeToolCall`/`afterToolCall` hooks, `shouldStopAfterTurn`, and a `toolExecution` mode of `parallel` (default) or `sequential`. There is no persistence, no compaction, no UI, no provider auth, and no resource discovery in the loop package. For FrockBot: make the Durable Object's Agent loop exactly this — call model, run tools, emit events, repeat — with context transformation, LLM conversion, tool pre/post hooks, and a stop predicate as its only extension points. [Root README](https://github.com/earendil-works/pi-mono/blob/main/README.md) · local `node_modules/@earendil-works/pi-agent-core/README.md`

2. **The default tool floor is four tools, not eight (positive, medium).** The README's Quick Start says "By default, pi gives the model four tools: `read`, `write`, `edit`, and `bash`", while the CLI reference lists eight _available_ built-ins: `read`, `bash`, `powershell` (Windows), `edit`, `write`, `grep`, `find`, `ls`. `settings.md` documents `defaultTools` as "Built-in tools enabled initially. When omitted, Pi uses its standard defaults", without enumerating that default set — so the exact shipped default list is **not documented** in one authoritative place. The four-tool claim is the load-bearing one: a `read`/`write`/`edit`/`bash` floor is sufficient for a self-modifying agent, because `bash` subsumes search and `write` subsumes capability authoring. For FrockBot: pick the smallest kernel tool set that makes the agent able to author its own Plugins, and treat everything richer (search, structured file listing) as a Plugin-contributed tool rather than a kernel obligation. [README CLI reference and Quick Start](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/README.md) · local `docs/settings.md` §Tools

3. **Every capability layer is a file on disk with a documented global/project split, and the split is trust-gated (positive, high).** Extensions load from `~/.pi/agent/extensions/*.ts` or `*/index.ts` (global) and `.pi/extensions/...` (project); skills from `~/.pi/agent/skills/`, `~/.agents/skills/`, `.pi/skills/`, and `.agents/skills/` walked from cwd up to the git root; prompt templates from `~/.pi/agent/prompts/*.md` and `.pi/prompts/*.md`; themes analogously. Project-local resources load **only after the project is trusted**. `docs/security.md` is explicit about the ordering: "Before trust is resolved, pi only loads context files, user/global extensions, and CLI `-e` extensions", and a global extension can own the trust decision by handling the `project_trust` event — "the first extension that returns a yes/no decision owns the decision". Decisions persist by canonical directory in `~/.pi/agent/trust.json`; the closest ancestor decision wins. The user's local `~/.pi/agent/trust.json` shows exactly this — a blanket `"/Users/tim/repos": true` covering descendants. For FrockBot: **[transferable]** the two-tier authority split (operator-owned vs. workspace-owned Contributions, with workspace Contributions inert until an explicit durable trust grant, and one trust-decider Contribution that runs before the untrusted tier) is a directly reusable admission model. **[local-process]** the specific `~/.pi` vs `.pi` filesystem layout and ancestor-directory trust inheritance are not. Local: `/Users/tim/.pi/agent/trust.json`, `/Users/tim/.pi/agent/settings.json` · [docs/security.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/security.md)

4. **One extension contract gives access to tools, commands, UI, events, providers, and session writes (positive, high).** An extension is a default-exported factory, sync or async, receiving one `ExtensionAPI`: `pi.on(event, handler)`, `pi.registerTool()`, `pi.registerCommand()`, `pi.registerShortcut()`, `pi.registerFlag()`, `pi.registerProvider()`/`unregisterProvider()`, `pi.registerMessageRenderer()`/`registerEntryRenderer()`/`registerMarkdownTransformer()`, `pi.appendEntry()`, `pi.sendMessage()`/`sendUserMessage()`, `pi.setActiveTools()`/`getAllTools()`/`getActiveTools()`, `pi.setModel()`, `pi.setThinkingLevel()`, `pi.exec()`, `pi.events` (an inter-extension bus), and session-name/label writers. The handler-side `ExtensionContext` adds `ctx.ui`, `ctx.mode`, `ctx.hasUI`, `ctx.cwd`, `ctx.isProjectTrusted()`, `ctx.sessionManager`, `ctx.signal`, `ctx.compact()`, `ctx.getSystemPrompt()`, `ctx.getContextUsage()`, `ctx.abort()`, `ctx.shutdown()`; the command-only `ExtensionCommandContext` adds `ctx.newSession()`, `ctx.fork()`, `ctx.navigateTree()`, `ctx.switchSession()`, and `ctx.reload()`. So yes: an extension can add tools, UI, commands, keybindings, CLI flags, **and model providers**. `pi.registerProvider()` covers OpenAI/Anthropic/Google-shaped endpoints declaratively (base URL, API key, `api` kind, model list), and `docs/custom-provider.md` covers bespoke APIs and OAuth. For FrockBot: this is the closest analogue to a Package Contribution manifest — one narrow object handed to a Plugin at mount, exposing registration verbs plus a per-invocation context. Copy the _shape_; do not copy the breadth (UI component factories and shortcut registration belong in a hosted-client Contribution, not the backend runtime one). [docs/extensions.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/extensions.md)

5. **Async extension factories are awaited before startup proceeds — a clean initialization barrier (positive, medium).** "If the factory returns a `Promise`, pi awaits it before continuing startup. That means async initialization completes before `session_start`, before `resources_discover`, and before provider registrations queued via `pi.registerProvider()` are flushed." Paired with a hard rule: "Extension factories may run in invocations that never start a session. Do not start background resources such as processes, sockets, file watchers, or timers from the factory. Defer background resource startup until `session_start` … Register an idempotent `session_shutdown` handler." For FrockBot: **[transferable]** separate _declaration_ (cheap, always runs, awaited, safe in an invocation that does no work) from _activation_ (session-scoped, disposable, idempotent shutdown). This maps almost exactly onto DO construction vs. first-command activation, and it is the discipline that makes a Contribution safe to mount in an evictable object. [docs/extensions.md §Async factory functions, §Long-lived resources and shutdown](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/extensions.md)

6. **Extension state must round-trip through the session log, not memory (positive, critical).** `docs/extensions.md` §State Management is unambiguous: "Extensions with state should store it in tool result `details` for proper branching support", and the worked example rebuilds in-memory state on `session_start` by walking `ctx.sessionManager.getBranch()` for its own tool results. Two additional durable channels exist: `appendEntry(customType, data)` writes a `custom` entry that is persisted and renderable but explicitly "does NOT participate in LLM context", and `appendCustomMessageEntry(...)` writes a `custom_message` entry that **does** enter LLM context. For FrockBot: this is the pi finding that transfers most cleanly and most urgently. **[transferable]** a Plugin holds no authoritative state; every Plugin-owned fact is an entry in the Bot's durable event log, tagged by owner, with an explicit flag for whether it is model-visible; the Plugin's in-memory state is a fold over that log, rebuilt on every mount. That is precisely the "ephemeral projections of durable state" rule already in `AGENTS.md`, and pi demonstrates it works in practice under branching. [docs/extensions.md §State Management](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/extensions.md) · [docs/session-format.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/session-format.md)

7. **The session log is an append-only tree, and modern compaction entries are self-contained checkpoints (positive, critical).** Sessions are JSONL at `~/.pi/agent/sessions/--<slugified-cwd>--/<timestamp>_<uuid>.jsonl`. The first line is a `session` header (`version: 3`, id, timestamp, cwd, optional `parentSession`); every subsequent line is an entry with an 8-hex `id` and a `parentId`, forming a tree. Entry types: `message`, `model_change`, `thinking_level_change`, `compaction`, `branch_summary`, `custom`, `custom_message`, `label`, `session_info`. Branching is in-place — `/tree` moves the leaf, `/fork` and `/clone` create new files with a `parentSession` backlink. Context is rebuilt by `buildContextEntries()` walking leaf→root, then `buildSessionContext()` converting entries to messages. Critically, newer `compaction` entries embed a materialized `retainedTail: AgentMessage[]` **on the entry**, so "we can rebuild context from this checkpoint without walking older entries before the compaction entry"; `firstKeptEntryId` survives only for backward compatibility. Versions 1→2→3 auto-migrate on load. For FrockBot: **[transferable]** adopt the id/parentId tree over a linear log (branching without file copies, and `/tree`-style navigation for free), the typed non-model-visible entry class, and above all the self-contained compaction checkpoint — a DO that must resume after eviction should be able to reconstruct the next model request from a bounded suffix of storage, not an unbounded replay. FrockBot's constitution already demands reconstructing "every exact normalized model request"; pi's `retainedTail` is the mechanism that makes that cheap. [docs/session-format.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/session-format.md) · [docs/compaction.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/compaction.md)

8. **Compaction is lossy-by-design with the full history preserved beside it (positive, medium).** Auto-compaction fires when `contextTokens > contextWindow - reserveTokens` (`reserveTokens` default 16384); it walks backwards accumulating until `keepRecentTokens` (default 20000), summarizes the older span with an LLM call, and appends a `CompactionEntry` whose `usage` is folded into session cost totals. Repeat compactions re-summarize from the previous kept boundary, not from the previous compaction entry, so surviving messages are carried forward. Mid-turn cuts ("split turns") are handled explicitly. Branch summarization is a parallel mechanism triggered by `/tree` navigation, producing `branch_summary` entries with a `fromId`. Both disable prompt-cache writes where the provider supports it, since one-off summarization prompts will not be reused. `session_before_compact` lets an extension replace the summary entirely. The README states plainly: "Compaction is lossy. The full history remains in the JSONL file; use `/tree` to revisit." For FrockBot: keep compaction a Plugin-owned policy behind a narrow interface, always append rather than truncate, always attribute the summarizer's own token cost, and never let a compaction be the only record of what happened. [docs/compaction.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/compaction.md)

9. **Self-modification is a first-class, documented workflow — with an explicit in-session reload path (positive, high).** Three of pi's doc pages open with a one-line banner: "pi can create extensions. Ask it to build one for your use case." (`extensions.md`), "pi can create skills." (`skills.md`), "pi can create prompt templates." (`prompt-templates.md`), and packages.md offers to bundle them. The actual loop is: the agent uses `write` to create `~/.pi/agent/extensions/foo.ts` or `~/.pi/agent/skills/foo/SKILL.md`, then the runtime must reload. `/reload` "Reload keybindings, extensions, skills, prompts, themes, and context files" — and `docs/extensions.md` ships a worked example (`reload-runtime.ts`) of an extension that exposes a `reload_runtime` **tool the model can call**, which works around a real constraint: "Tools run with `ExtensionContext`, so they cannot call `ctx.reload()` directly. Use a command as the reload entrypoint, then expose a tool that queues that command as a follow-up user message." The tool body is literally `pi.sendUserMessage("/reload-runtime", { deliverAs: "followUp" })`. Reload semantics are spelled out and are footgun-heavy: `await ctx.reload()` emits `session_shutdown`, reloads resources, then emits `session_start { reason: "reload" }` and `resources_discover { reason: "reload" }`, **but** "the currently running command handler still continues in the old call frame" and "code after `await ctx.reload()` still runs from the pre-reload version". Guidance: "treat reload as terminal for that handler". Only themes hot-reload without `/reload` ("When you edit the currently active custom theme file, pi reloads it automatically"). Placement matters: "Extensions in auto-discovered locations can be hot-reloaded with `/reload`"; `pi -e ./path.ts` is "only for quick tests". For FrockBot: **[transferable]** the self-modification loop needs (a) an authoring surface the agent already has, (b) an explicit, agent-invocable reload command, and (c) a documented rule that the reload is terminal for the frame that triggered it. **[local-process]** in-place module re-evaluation via `jiti` in a live process has no DO analogue; FrockBot's equivalent is publishing a new Contribution version and re-mounting the Cordis root — which is _cleaner_, because a DO re-mount has no "old call frame" problem if the reload is expressed as a durable command that completes the current turn first. [docs/extensions.md §ctx.reload()](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/extensions.md) · [docs/themes.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/themes.md)

10. **There are no self-modification guardrails, no provenance, and no rollback (risk, critical).** This is the sharpest gap. Nothing in the docs describes review, signing, provenance, or version history for an agent-authored extension or skill. The only gate is project trust, and `docs/security.md` is candid that it is not one: "Project trust is only an input-loading guard. It prevents a repository from silently changing pi's settings or extensions before you approve it. It does not make untrusted code, untrusted prompts, or untrusted model output safe." Global extensions in `~/.pi/agent/extensions/` are never trust-gated at all — an agent writing there self-modifies with no approval step. Packages carry a blunt warning ("Pi packages run with full system access… Review source code before installing third-party packages") but no enforcement. Rollback is whatever the user's VCS provides; there is no extension version history, no `pi revert`, and no record in the session log of which extension version produced a given tool result. Supply-chain hardening exists but is aimed at pi's _own_ npm dependencies (exact pins, `min-release-age=2`, shrinkwrap, lifecycle-script allowlist, `--ignore-scripts` everywhere), not at agent-authored code. For FrockBot: this is the one place to deliberately diverge. A self-modifying Bot needs the capability _and_ the ledger — Contribution versions as durable, addressable, immutable artifacts; a durable record on each Turn of which Contribution versions were mounted; an explicit human-or-policy admission step before a newly authored Contribution becomes active; and rollback as re-mounting a prior version, not as filesystem archaeology. [docs/security.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/security.md) · [docs/packages.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/packages.md) · [Root README §Supply-chain hardening](https://github.com/earendil-works/pi-mono/blob/main/README.md)

11. **Pi ships no sandbox and says so, loudly (risk, high — but honest).** "Pi does not include a built-in sandbox. Built-in tools can read files, write files, edit files, and run shell commands with the permissions of the pi process. Extensions are TypeScript modules that run with the same permissions." The rationale is worth quoting because it is an architectural argument, not an excuse: "A partial in-process sandbox would be easy to misunderstand as a security boundary while still depending on the host shell, filesystem, package managers, credentials, and extension code. Real isolation needs to come from the operating system or a virtualization/container boundary." Isolation is therefore an extension concern — `docs/containerization.md` documents three patterns, and `examples/extensions/gondolin/` routes built-in tools and `!` commands into a Linux micro-VM while pi and provider auth stay on the host. The `BashOperations` interface (`exec(command, cwd, { onData, signal, timeout, env })`) is the seam that makes this possible: the bash tool's execution backend is pluggable, so an extension can redirect it to SSH, a container, or a micro-VM without reimplementing the tool. For FrockBot: **[transferable]** the _seam_ is the lesson — define tool execution as a narrow provider-neutral operations interface so the execution target (in-DO, Sprite, Dynamic Worker) is a Contribution choice, exactly as the constitution's Computer interface already requires. **[local-process]** pi's "just run it as the user" default is the opposite of a Cloudflare deployment, where the isolate boundary is the default and _expanding_ capability is the deliberate act. FrockBot inherits a better starting position here and should not import pi's permissiveness. [docs/security.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/security.md) · local `dist/core/tools/bash.d.ts`

12. **Tools are a small typed contract with cooperative cancellation and a file-mutation queue (positive, high).** A tool is `{ name, label, description, parameters (typebox), promptSnippet?, promptGuidelines?, prepareArguments?, execute(toolCallId, params, signal, onUpdate, ctx), renderCall?, renderResult? }`. Cancellation is a cooperative `AbortSignal` threaded into `execute` and onward into `pi.exec()`. Progress streams via `onUpdate`. `content` goes to the LLM; `details` is for rendering and state reconstruction; optional `usage` accounts for nested LLM calls made _by_ the tool and is folded into session totals; `terminate: true` skips the follow-up model call, but "only takes effect when every finalized tool result in that batch is terminating". Errors must be **thrown** — "Returning a value never sets the error flag regardless of what properties you include in the return object." Two details are worth stealing outright. First, `prepareArguments(args)` runs before schema validation specifically so a _resumed old session_ whose stored tool-call arguments no longer match the current schema can be migrated forward, with an explicit instruction to keep the public schema strict rather than accreting deprecated fields. Second, because tools run in parallel by default, any tool that mutates files must wrap its whole read-modify-write window in `withFileMutationQueue(absolutePath, fn)` — which canonicalizes through `realpath()` so symlink aliases share one queue — or lose writes to a concurrent built-in `edit`. Extensions may override built-ins by registering the same name, and renderer inheritance resolves per slot (omit `renderCall` and the built-in renderer is used), which makes logging/gating wrappers cheap. For FrockBot: **[transferable]** all of it — the signal-threaded contract, content/details separation, nested-usage accounting, throw-to-error, per-resource mutation serialization, and especially `prepareArguments` as a **schema-version migration seam on replay**, which a DO that reconstructs historical model requests will need. [docs/extensions.md §Custom Tools, §Tool Definition, §Overriding Built-in Tools](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/extensions.md)

13. **Dynamic tool loading keeps the prompt prefix stable while the tool set grows mid-session (positive, medium).** Register every tool, keep only a loader active, and have the loader call `pi.setActiveTools([...current, ...matches])`. "Pi detects purely additive changes, records the newly available tool names on that tool result, and applies the updated active set before the next model request." On providers with native support this uses Anthropic `defer_loading`/`tool_reference` or OpenAI client `tool_search_call`/`tool_search_output` items anchored at the load point, preserving the cached prefix; otherwise it falls back to sending the full active list. Removals work but always take the fallback path. A caveat the docs flag: activating a tool that carries `promptSnippet` or `promptGuidelines` rebuilds the system prompt and can invalidate the prefix anyway, "so lazily loaded tools should usually rely on their tool `description`". For FrockBot: this is the mechanism that lets a Bot mount many Plugin-contributed tools without paying context cost for all of them, and the additive-only constraint plus "the active-tool change is the signal" is a clean, provider-neutral design worth copying into the Plugin/tool seam. [docs/extensions.md §Dynamic Tool Loading](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/extensions.md)

14. **Skills are progressive disclosure with a documented standard and near-zero kernel cost (positive, high).** Pi implements the Agent Skills standard (agentskills.io) "warning about most violations but remaining lenient" — notably relaxing the standard's requirement that a skill's `name` match its parent directory, because "that requirement is suboptimal for shared skill directories used by multiple tools". The mechanism is four steps: scan locations at startup for name+description; inject only those into the system prompt as XML; let the model `read` the full `SKILL.md` when a task matches; follow the instructions using paths relative to the skill directory. Frontmatter is `name` (≤64 chars, lowercase/digits/hyphens) and `description` (≤1024 chars) required; `license`, `compatibility`, `metadata`, `allowed-tools` (experimental), `disable-model-invocation` optional. Skills also register as `/skill:name` commands with trailing args appended as `User: <args>`. The docs admit the weak link: "models don't always do this; use prompting or `/skill:name` to force it". Name collisions warn and keep the first found. Crucially, pi can consume _other harnesses'_ skill directories by adding `~/.claude/skills` or `~/.codex/skills` to `settings.skills` — the user's local install has 39 skills in `~/.pi/agent/skills/` that are clearly shared with their Claude Code setup. For FrockBot: **[transferable]** skills are the cheapest possible extension layer — pure Markdown, no code, no execution surface of their own, costing only a description in the system prompt — and standards-compatibility means a FrockBot skill directory is portable. This is the right shape for the majority of Bot behavior customization; reserve code Plugins for what genuinely needs execution. Local: `/Users/tim/.pi/agent/skills/` (39 skills) · [docs/skills.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/skills.md)

15. **Four modes share one core, and the mode differences are a two-flag abstraction (positive, high).** Interactive TUI (`ctx.mode: "tui"`, `hasUI: true`), RPC (`--mode rpc`, `"rpc"`, `hasUI: true` — dialogs and notifications marshalled over JSON, but `ui.custom()` returns `undefined`), JSON (`--mode json`, `"json"`, `hasUI: false` — UI methods are no-ops), and print (`-p`, `"print"`, `hasUI: false` — "extensions run but can't prompt"). Plus an in-process SDK (`createAgentSession()` / `createAgentSessionRuntime()`) that is the recommended path for Node consumers over spawning an RPC subprocess. Extensions load and run in _all_ modes; they simply query `ctx.mode` and `ctx.hasUI` before reaching for UI. Behavioral divergences are documented rather than emergent: non-interactive modes never show a trust prompt and fall back to `defaultProjectTrust`, and RPC's framing is deliberately strict — "strict JSONL semantics with LF (`\n`) as the only record delimiter… Node `readline` is not protocol-compliant for RPC mode because it also splits on `U+2028` and `U+2029`, which are valid inside JSON strings." RPC `prompt` responses mean _accepted/queued_, not _completed_: "Failures after acceptance are reported through the normal event and message stream, not as a second `response` for the same request id." For FrockBot: **[transferable]** two booleans (`hasUI`, plus a mode discriminant) are enough for a Plugin to behave correctly across every entry point — that is a far smaller seam than per-mode Plugin variants, and it directly serves the one-production-path rule. Also copy the accept/complete split: an admitted command acknowledges admission, and outcomes arrive on the event stream. [docs/extensions.md §Mode Behavior](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/extensions.md) · [docs/rpc.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/rpc.md) · [docs/sdk.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/sdk.md)

16. **Instruction files follow the AGENTS.md convention with a documented override escape hatch (positive, medium).** Pi loads `AGENTS.md` (or `CLAUDE.md`) from `~/.pi/agent/AGENTS.md`, then every parent directory walking up from cwd, then the current directory, concatenating all matches. "If a directory contains `AGENTS.override.md`, Pi loads it instead of `AGENTS.md` or `CLAUDE.md` from that directory. Context files from other directories are still concatenated." Context files load **regardless of project trust** (unless `--no-context-files`/`-nc`) — a deliberate and slightly uncomfortable choice, since a hostile repo's `AGENTS.md` reaches the model before any trust decision; `security.md` names this as accepted risk: "Prompt injection from repository files, comments, documentation, context files, or build output is expected local-agent risk and cannot be reliably prevented by pi." Separately, the _system prompt_ itself is replaceable via `.pi/SYSTEM.md` (project) or `~/.pi/agent/SYSTEM.md` (global), or appendable via `APPEND_SYSTEM.md`; CLI equivalents are `--system-prompt` and `--append-system-prompt`. There is no long-term memory store — no `memory.md`, no vector index, no cross-session recall beyond session files and context files. That absence is consistent with the philosophy but is **not documented** as an explicit decision. For FrockBot: keep the concatenating hierarchy and the override file, but do _not_ copy trust-free loading of workspace-authored context — a Bot whose durable instructions can be shaped by an untrusted workspace file is a policy problem, not just an injection problem. [README §Context Files](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/README.md) · [docs/security.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/security.md)

17. **The "no X" list is the actual design document (positive, critical).** Pi's Philosophy section enumerates deliberate absences with reasons: **No MCP** ("Build CLI tools with READMEs… or build an extension that adds MCP support"); **No sub-agents** ("There's many ways to do this. Spawn pi instances via tmux, or build your own with extensions"); **No permission popups** ("Run in a container, or build your own confirmation flow with extensions inline with your environment and security requirements"); **No plan mode**; **No built-in to-dos** ("They confuse models"); **No background bash** ("Use tmux. Full observability, direct interaction"). The README frames the whole product this way: "Pi ships with powerful defaults but skips features like sub agents and plan mode. Instead, you can ask pi to build what you want or install a third party pi package that matches your workflow." The user's own install proves the model works: `settings.json` lists 13 installed packages supplying exactly the omitted features — `pi-subagents` (delegation and multi-agent workflows), `pi-mcp-adapter` (MCP, the explicitly-refused feature), `pi-background-tasks`, `@juicesharp/rpiv-todo` (to-dos), `pi-web-access`, `pi-codex-image-gen`, `@llblab/pi-telegram`, plus local extensions and symlinked ones from a personal `pi-setup` repo. For FrockBot: **[transferable]** write the "not in the host bootstrap" list explicitly and treat it as a constitutional artifact, the way `AGENTS.md` already treats plugin composition. Pi's list is a good template — orchestration patterns, approval flows, planning, task tracking, and protocol adapters are all Plugin territory. Local: `/Users/tim/.pi/agent/settings.json` · [README §Philosophy](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/README.md)

18. **Packages are a thin distribution layer over the same on-disk conventions (positive, medium).** A pi package is any npm/git/local directory with a `pi` key in `package.json` (`{"extensions": [...], "skills": [...], "prompts": [...], "themes": [...]}`) — or nothing at all, since "Without a `pi` manifest, pi auto-discovers from conventional directories". Sources are `npm:@scope/pkg@1.2.3`, `git:host/user/repo@ref`, protocol URLs, or absolute/relative local paths (added to settings without copying). Versioned npm specs and pinned git refs are skipped by `pi update`. Installs land in `~/.pi/agent/npm/` and `~/.pi/agent/git/<host>/<path>`, or `.pi/…` with `-l`; project packages install automatically on startup **after trust**. `pi config` toggles individual resources on or off. `pi -e npm:@foo/bar` installs to a temp dir for one run. For FrockBot: **[transferable]** the manifest-or-convention duality (an explicit declaration wins; a conventional layout is the fallback) lowers the cost of authoring a Contribution to near zero, which matters a great deal for a self-modifying Bot writing its own Plugins. **[local-process]** npm/git as the transport and per-user directories as the install target do not survive; FrockBot's equivalent is durable cloud configuration scoped to User or Bot, which the constitution already requires. [docs/packages.md](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/packages.md)

19. **Session switching from inside an extension is documented as a footgun (risk, medium).** `ExtensionCommandContext` exposes `newSession()`, `fork()`, `navigateTree()`, and `switchSession()`, and `docs/extensions.md` devotes a section titled "Session replacement lifecycle and footguns" to them — mirroring the `ctx.reload()` warnings: the calling frame survives the replacement it triggered. `session_before_switch` can cancel. For FrockBot: **[transferable]** any Plugin-triggered operation that replaces the runtime around the calling frame must be modelled as a durable command that the current Turn completes _into_, never as an in-frame await. A DO makes this easier to get right than a live Node process does, and FrockBot should encode it as a rule rather than a warning. [docs/extensions.md §Session replacement lifecycle and footguns, §ctx.reload()](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/extensions.md)

20. **Extension failures degrade rather than halt, with one fail-safe inversion (positive, medium).** "Extension errors are logged, agent continues"; "`tool_call` errors block the tool (fail-safe)"; tool `execute` errors are caught, reported to the LLM with `isError: true`, and execution continues. So the one place pi fails _closed_ is the permission-gate path — an extension that throws while deciding whether a tool may run blocks the tool. For FrockBot: copy the asymmetry exactly. A Plugin that fails while decorating, rendering, or observing must not take down a Turn; a Plugin that fails while _admitting_ an action must deny it. [docs/extensions.md §Error Handling](https://github.com/earendil-works/pi-mono/blob/main/packages/coding-agent/docs/extensions.md)

## Bare-minimum core (answer)

**In the kernel** (irreducible, per pi's own package boundaries and the loop package's documented surface):

1. **Provider-neutral model invocation** — `@earendil-works/pi-ai`: one API over ~30 providers, streaming normalization, model catalogs, thinking levels, transport selection (SSE / WebSocket).
2. **The agent loop** — `@earendil-works/pi-agent-core`: `agent_start → turn_start → message_* → tool_execution_* → turn_end → agent_end`, plus `prompt()`/`continue()`, parallel-or-sequential tool execution, `beforeToolCall`/`afterToolCall`, `shouldStopAfterTurn`, `transformContext`, `convertToLlm`, cooperative abort.
3. **Message and session model** — the `AgentMessage` union and the id/parentId entry tree, with `SessionManager` as the append/navigate/rebuild surface.
4. **Four tools** — `read`, `write`, `edit`, `bash`. (Four more ship as available built-ins: `grep`, `find`, `ls`, `powershell`.)
5. **A tool contract** — typebox parameters, `AbortSignal`, `onUpdate` streaming, `content` vs `details`, nested `usage`, throw-to-error, `prepareArguments` replay migration, per-file mutation queue.
6. **Resource discovery and loading** — the `ResourceLoader` that finds extensions, skills, prompt templates, themes, and context files across global/project/package/settings/CLI, gated by project trust.
7. **One extension seam** — `(pi: ExtensionAPI) => void | Promise<void>`, awaited before startup completes.
8. **Session persistence, compaction, and branching** — JSONL log, self-contained compaction checkpoints, `/tree`, `/fork`, `/clone`.
9. **Mode adapters** — TUI, print, JSON, RPC, SDK, differing only by `ctx.mode` and `ctx.hasUI`.
10. **Auth and settings storage** — provider credentials, `settings.json` layering, `trust.json`.

**Deliberately NOT in the kernel** (each is a documented refusal or an extension-only capability): sub-agents · plan mode · MCP · permission prompts/approval UI · to-do lists · background bash · sandboxing or any permission system · git checkpointing · custom compaction strategies · status lines, headers, footers, widgets, overlays, custom editors · alternative model providers beyond the built-in catalog · remote/SSH/container tool execution · session sharing beyond `/share` · long-term memory.

**The shape of the trade:** pi's kernel is "call a model, run four tools, keep an append-only tree, discover files, hand everything else one factory function." Every refused feature exists in the ecosystem — the user's own install pulls back sub-agents, MCP, to-dos, background tasks, and image generation as packages. The kernel stayed small _and_ the feature set is complete, which is the entire proof of the model.

## Recommended FrockBot shape

- **Kernel = loop + tools + log + mount.** The Bot Durable Object's host bootstrap does what pi's does: initialize the runtime, mount declared Contributions, report fatal startup failure, dispose. The Agent loop itself is "call model, run tools, emit events, repeat" with exactly pi's four seams — context transform, LLM conversion, tool pre/post hooks, stop predicate. No provider branching, no product policy.
- **Four tools, then Plugins.** Ship `read`/`write`/`edit`/`bash`-equivalents as the kernel floor — enough for a Bot to author its own Contributions — and contribute everything richer as Plugins.
- **One Contribution factory, awaited.** Mirror `(pi: ExtensionAPI) => void | Promise<void>`: cheap declaration awaited at mount, activation deferred to first session event, idempotent disposal. This is what makes a Contribution safe in an evictable object.
- **No Plugin holds authority.** Every Plugin fact is a durable log entry tagged by owner, with an explicit model-visible flag (pi's `custom` vs `custom_message`). In-memory Plugin state is a fold rebuilt on mount. Already constitutional; pi shows it working under branching.
- **id/parentId tree, self-contained checkpoints.** Adopt pi's entry tree over a linear log, and make every compaction embed its `retainedTail` so a cold DO can rebuild the next model request from a bounded storage suffix. Persist the normalized request envelope alongside, per FrockBot's existing rule.
- **Two-tier trust, decided before the untrusted tier loads.** Operator-scoped Contributions mount first and may include the one that decides workspace trust; workspace-scoped Contributions stay inert until a durable grant exists. Unlike pi, gate workspace-authored _instruction_ files too.
- **Self-modification with a ledger.** Give the Bot the authoring surface and an agent-invocable reload command — expressed as a durable command that completes the current Turn first, not an in-frame await. Then add what pi lacks: immutable versioned Contribution artifacts, a per-Turn record of mounted versions, an explicit admission step before a newly authored Contribution activates, and rollback as re-mount.
- **Skills before code.** Make Markdown skills (Agent Skills standard, progressive disclosure, description-only in the system prompt) the default customization layer. Reserve code Contributions for what needs execution.
- **`prepareArguments` as a replay migration seam.** A DO that reconstructs historical model requests will hit schema drift. Copy pi's answer: keep published schemas strict, migrate stored arguments in a dedicated pre-validation hook.
- **Serialize per-resource mutation.** Copy `withFileMutationQueue`'s canonicalize-then-queue pattern for any parallel-executing tool touching shared state.
- **Fail open on decoration, closed on admission.** Observer/renderer/decorator Plugin failures log and continue; admission-gate failures deny.
- **Two flags for mode.** `hasUI` plus a mode discriminant is enough for a Contribution to behave correctly across hosted UI, one-shot, and protocol entry points — no per-mode variants. Acknowledge admission; report outcomes on the event stream.

## Gaps and residual risks

- **Agent-authored code has no provenance, approval, or rollback story.** Nothing in the docs covers reviewing, signing, versioning, or reverting an extension or skill the agent wrote. Global `~/.pi/agent/extensions/` is not trust-gated at all. This is the single largest gap between pi and what a self-modifying FrockBot needs, and the recommendations above are FrockBot-specific design, not observed pi behavior.
- **The exact default built-in tool set is ambiguous.** The README says four (`read`, `write`, `edit`, `bash`); eight are listed as available; `settings.defaultTools` says "when omitted, Pi uses its standard defaults" without enumerating them. Not resolved from the installed docs; would require reading `dist/core/defaults.js` or upstream `src/`.
- **Long-term memory is absent and the absence is undocumented.** There is no memory file, store, or cross-session recall beyond session JSONL and `AGENTS.md`. Consistent with the philosophy, but pi never states it as a decision, so it is unclear whether this is refusal or omission.
- **No durability guarantees are documented.** Session JSONL append timing, fsync behavior, crash-mid-turn recovery, and whether an interrupted turn is resumable or merely reopened are all **not documented**. Pi assumes a process that outlives its session; FrockBot cannot. Every durable-admission, alarm-resume, and idempotency requirement in FrockBot's constitution is unaddressed by pi and must be designed independently.
- **Cancellation is cooperative and in-process.** `AbortSignal` threading is well documented, but there is no durable cancellation record — a killed pi process leaves no cancellation event. FrockBot's "only an explicit authenticated command cancels work" rule has no pi analogue.
- **Extension isolation is nil.** Extensions share the pi process, the event bus (`pi.events`), the tool namespace (later registrations override built-ins by name), and full user permissions. There is no capability declaration, no manifest-declared authority, and no per-extension resource accounting. FrockBot's manifest-declared Contribution authority is a deliberate divergence with no pi precedent to validate it.
- **`main`-branch URLs are mutable.** Every GitHub link above points at `main`. Pin to the reviewed commit before citing this note in an ADR. The installed local copy (`0.84.3`) is the stable artifact and is the source actually read.
- **Not verified by execution.** No pi session was run, no extension was authored and reloaded, and no session JSONL was parsed end-to-end. All behavioral claims come from official docs, installed type definitions, and on-disk configuration artifacts — not from observed runtime behavior.
