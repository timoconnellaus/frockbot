# Hermes memory alternatives

## Scope

Inspected NousResearch/Hermes Agent at commit [`524041b9d0437cd4424a524af4b9e26145e69ab0`](https://github.com/NousResearch/hermes-agent/tree/524041b9d0437cd4424a524af4b9e26145e69ab0), retrieved 2026-09-22. This note describes Hermes's integration behavior for its eight bundled optional memory providers. Integration claims use pinned Hermes sources; the architectural comparison also uses linked first-party provider documentation retrieved on the same date. Those provider pages are not pinned versions. This is not an implementation audit or benchmark of each service.

## The common Hermes seam

**Decision from the walkthrough:** use Hindsight as the reference design and implement the shared long-term Memory engine on FrockBot's Cloudflare architecture. The [agreed plan](../plan.md#planned-shared-long-term-memory-following-hindsight) covers User, Bot and Group Chat scopes, separate from working context, compaction and transcript history. Implementation remains deferred. The comparison below records the evidence behind that choice.

These are opt-in plugins, not replacements for `MEMORY.md` and `USER.md`. Hermes activates at most one external provider and keeps the built-in provider beside it ([provider overview](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/user-guide/features/memory-providers.md#L7-L39)). The common interface admits static prompt instructions, prefetched context, completed-turn sync, session-end extraction, built-in-write mirroring, and provider tools ([interface](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/memory_provider.py#L75-L185)). Provider tools can also be removed by the memory-toolset gate.

The eight below ship in this revision. Hermes also documents **Memori** as a separately installed `hermes-memori` catalog plugin with completed-turn capture and explicit structured-recall tools; it is an example of the open provider seam rather than a ninth bundled implementation ([Memori installation](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/user-guide/features/memory-providers.md#L651-L670)).

The generic fast path is deliberately fail-open. External prefetch is bounded by an eight-second host timeout; a timed-out call contributes no context, continues on a daemon thread, and causes later prefetches for that provider to be skipped until it exits. Successful context is attached to the current user turn and therefore remains in later prompt prefixes ([prefetch manager](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/memory_manager.py#L394-L448)). The interface's intended default is prior-turn prewarming: `queue_prefetch()` runs after a turn and `prefetch()` consumes the cached result on the next turn ([contract](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/memory_provider.py#L107-L129)). Individual adapters depart from that contract, so “automatic recall” does not always mean current-query recall.

Completed turns and session-boundary work run on a serialized background worker. Session-end extraction runs before rebinding the provider to a new session, avoiding both user-visible blocking and attribution races ([boundary ordering](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/memory_manager.py#L610-L645)). Successful built-in `add`, `replace`, and `remove` operations may be announced to the external provider, but each adapter decides which actions it can actually mirror ([write seam](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/memory_manager.py#L720-L749)). This is asynchronous replication, not a cross-store transaction.

## What is strongest prior art for FrockBot

Three designs deserve deeper comparison; none is established as universally best by the evidence above.

1. **Hindsight's evidence-to-observation retrieval** is the strongest match for reliable, token-bounded recall. It separates raw evidence from consolidated observations, supports query-time semantic, keyword, graph, and temporal retrieval, and exposes both retrieval effort and output-token budgets. Its provider-level knowledge pages are generated topic/wiki projections over those observations, retain provenance, and can be rendered as Markdown; they are derived views rather than a second authored source ([knowledge pages](https://hindsight.vectorize.io/developer/knowledge-pages), [observations](https://hindsight.vectorize.io/developer/observations)). That is useful prior art for combining FrockBot's authoritative records, SQLite exact/history search, and Vectorize candidates without duplicating editable memory files. Hermes exposes the bank recall/retain/reflect seam, but its adapter does not itself implement those consolidation rules. This also does not prove that Hindsight's storage model maps directly to Durable Objects or that its latency meets voice startup needs.
2. **OpenViking's hierarchical context and read-after-search workflow** is strong prior art for large project/group knowledge. Its L0 abstracts, L1 directory overviews, and L2 originals let recall return small navigation material before expanding exact sources ([OpenViking context layers](https://github.com/volcengine/OpenViking/blob/main/docs/en/concepts/03-context-layers.md)). The useful idea is progressive disclosure with stable source URIs. Generated sidecars can lag source updates and sampled summaries can omit details, so authoritative reads and freshness checks remain necessary.
3. **Honcho's peer identity model** best matches shared-user plus distinct-bot memory. One workspace can hold a common human identity while each bot has its own representation, and Hermes already isolates bot-authored traffic from human-profile mutation. Its dialectic layer and query rewrite add model calls, and its default cached/prewarmed path can lag the current request; current-query mode trades latency for relevance.

Mem0 is a useful simple extracted-fact baseline, Holographic a useful local explicit-control baseline, and Supermemory a useful container/document-capture example. RetainDB and ByteRover demonstrate prewarming and hierarchy but expose weaker deletion/mirroring guarantees in Hermes. None directly supplies FrockBot's required user, bot, project, and future group scopes with Cloudflare Vectorize. Reproducing any pattern over Durable Objects, SQLite, R2, and Vectorize would be a new FrockBot implementation and would need its own freshness, tombstone, authority, token-budget, and latency validation.

## Adoption and evidence

Hindsight has published author-run evaluations on LongMemEval and LoCoMo ([paper](https://arxiv.org/abs/2512.12818)). That is useful evidence to inspect when selecting a system; it does not establish a universal winner, validate every newer feature, or demonstrate FrockBot voice startup performance. Its retrieval design combines several search methods and separately controls search depth and returned tokens ([recall architecture](https://hindsight.vectorize.io/developer/retrieval)). Ordinary recall uses embeddings and a reranker without a generative LLM call; `reflect` adds generative reasoning ([recall versus reflect](https://hindsight.vectorize.io/blog/2026/07/24/recall-vs-reflect)).

Adopting that implementation is a different decision from borrowing its design. Hindsight's primary backend is PostgreSQL with pgvector, full-text indexes and relational graph queries; it also documents an Oracle alternative ([storage](https://hindsight.vectorize.io/developer/storage)). It is not a ready-made implementation inside FrockBot's SQLite Durable Object and Cloudflare Vectorize. The selected direction is to implement the design on FrockBot's architecture; the per-User Memory DO topology and canonical-record schema remain provisional. Hindsight's publisher, Vectorize, Inc., is distinct from Cloudflare's Vectorize product.
