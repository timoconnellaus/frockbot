# Hermes Agent memory: current implementation and lessons for FrockBot startup

## Scope and revision

This note inspects NousResearch/Hermes Agent at commit [`524041b9d0437cd4424a524af4b9e26145e69ab0`](https://github.com/NousResearch/hermes-agent/tree/524041b9d0437cd4424a524af4b9e26145e69ab0), committed 2026-09-21 19:56:16 -04:00 and retrieved on 2026-09-22. Claims below come from that pinned source and its first-party documentation. Provider internals outside the Hermes integration adapters were not audited, and no latency benchmarks were run.

## Executive assessment

Hermes does not have one memory subsystem. It has four related layers:

1. **Built-in curated memory:** two small, profile-scoped Markdown files, `memories/MEMORY.md` and `memories/USER.md`. Their contents are read once when an `AIAgent` is constructed and injected as a frozen system-prompt snapshot. Writes are explicit tool operations, except for a periodic post-response review that may decide to call the same tool in a background model run.
2. **Durable conversation history:** the full transcript is stored in `state.db`; SQLite FTS5 powers an explicit `session_search` tool. History is not automatically retrieved for every prompt.
3. **Context compaction:** a long live session is summarized while its original messages remain recoverable through `session_search`. This is active-session continuity, not durable fact memory.
4. **One optional external memory provider:** eight adapters ship in-tree. A provider supplements the built-in files with semantic/structured recall, automatic turn capture or extraction, and provider-specific tools. It does not replace the built-in store. Some providers prewarm recall after the prior turn; others perform current-query retrieval on the next turn's critical path.

For FrockBot's startup problem, the strongest prior art is architectural rather than provider-specific: keep a small prepared prompt view local; do not rebuild it by enumerating all source objects on every turn; invalidate it deliberately; keep full transcript search on demand; and let richer semantic retrieval miss or arrive later rather than block a reply indefinitely. Hermes also demonstrates the consistency cost of this choice: its built-in view is intentionally stale until the `AIAgent` is rebuilt, normally at a real session boundary.

## Default built-in memory

### Scope, storage, and prompt injection

`MEMORY.md` holds agent/environment notes and defaults to 2,200 characters; `USER.md` holds user identity and preferences and defaults to 1,375 characters. Both live under the active Hermes profile's `memories/` directory. The code resolves that directory through `get_hermes_home()`, so separate profiles do not share the files unless an external provider is configured to do so ([memory tool paths](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/tools/memory_tool.py#L38-L60), [documented shape and limits](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/user-guide/features/memory.md#L13-L23)).

Both stores default to enabled, but each can be disabled with `memory.memory_enabled` or `memory.user_profile_enabled`; specialized agents can also be constructed with `skip_memory`. Thus “built-in memory is always active alongside a provider” describes the ordinary configured product path, not an unconditional runtime invariant ([flag resolution](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/tools/memory_tool.py#L215-L253), [agent initialization](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/agent_init.py#L1254-L1299)).

At agent construction, `MemoryStore.load_from_disk()` reads and deduplicates both files, warns rather than truncating if an external writer has exceeded a limit, scans entries for prompt-injection/exfiltration patterns, and renders a frozen prompt block. The live entry lists may subsequently change, but `format_for_system_prompt()` continues to return the load-time snapshot ([load and snapshot](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/tools/memory_tool_store.py#L122-L153), [frozen accessor](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/tools/memory_tool_store.py#L403-L406)). The system-prompt assembler inserts those blocks and then any external-provider static block ([prompt assembly](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/system_prompt.py#L514-L539)).

This is a prepared view, but it is process/session-local rather than a durable cache with fine-grained invalidation. In a gateway, an `AIAgent` can remain warm across many messages; LRU, idle, configuration, or memory-pressure eviction rebuilds it later from durable state ([cache bounds and idle eviction](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/gateway/run_agent_cache.py#L804-L830), [eviction path](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/gateway/run_agent_cache.py#L923-L983)). A messaging chat may remain one logical session across process restarts, while any new agent instance re-reads the files. A deliberate `/new` is the clear semantic boundary at which new file contents become part of a fresh prompt ([session-boundary explanation](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/user-guide/features/memory.md#L57-L65)).

### Writing, updating, and forgetting

The ordinary write path is explicit. The model calls `memory` with `add`, `replace`, or `remove`, or submits an atomic batch. Entries are separated by `§`. Replace/remove use an exact match first and otherwise require a unique substring. Duplicate adds are idempotent. A write that would exceed the target's character budget fails and returns enough live state for the model to consolidate; the store never silently evicts or summarizes entries ([add/overflow behavior](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/tools/memory_tool_store.py#L263-L325), [atomic batches](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/tools/memory_tool_store.py#L355-L401)). Writes lock a sidecar lock file, re-read before mutation, atomically replace the Markdown file, and reject edits that would overwrite unroundtrippable external changes ([locked mutation](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/tools/memory_tool_store.py#L155-L201), [drift-safe mutation](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/tools/memory_tool_store.py#L234-L261)). Optional write approval can stage a mutation rather than apply it immediately ([write gate](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/tools/memory_tool.py#L64-L111)).

There is no general automatic fact extractor on every built-in turn. Instead, a configurable nudge interval defaults to 10 turns. After a successful response, Hermes can launch a separate background review over a transcript snapshot; that reviewer decides whether anything warrants a `memory` tool call. It runs after delivery so it does not delay the user's response, and cron/specialized paths can suppress it ([nudge initialization](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/agent_init.py#L1254-L1289), [post-response launch](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/turn_finalizer.py#L632-L664), [review routing prompt](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/background_review.py#L334-L357)). This is best-effort model curation, not deterministic extraction.

### Token and cache behavior

The built-in limits total 3,575 characters, documented as roughly 1,300 tokens. The complete blocks cost tokens on every turn, regardless of relevance. The advantage is that no file listing, search, embedding, model call, or network request is needed at turn start after agent construction. Freezing the blocks preserves the model provider's prefix cache and avoids mid-session prompt churn; the cost is that a successful memory write is not injected into later turns of the same warm agent ([frozen-snapshot rationale](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/user-guide/features/memory.md#L36-L63)). That prompt budget is not the whole memory cost: periodic background review starts another model run over a full same-model transcript snapshot or a routed digest, while some providers add extraction, synthesis, or query-rewrite calls ([review input choice](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/background_review.py#L1171-L1179)). Their cost depends on cadence, routing, provider, and transcript size; no universal measured figure is established here.

## Conversation recall and compaction are separate

Hermes persists full sessions and messages in `state.db`. `session_search` performs explicit FTS5 discovery, scrolling, whole-session reads, or recent-session browsing. It returns stored messages without an LLM call; it is prompted for references such as “last time,” but it is not run automatically at conversation startup or before every turn ([session-search implementation contract](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/user-guide/sessions.md#L776-L853)). Ended inactive sessions are auto-pruned after 90 days by default, so “all history” is bounded by retention configuration ([retention](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/user-guide/sessions.md#L1087-L1088)).

Long active sessions use a context compressor. In the default in-place mode, old rows are soft-archived under the same session ID, a summary plus recent tail remains in the prompt, and recovery pointers direct the model back to `session_search`. The source messages remain queryable; the summary is active-context management, not the authoritative history or the curated memory files ([compaction design](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/developer-guide/context-compression-and-caching.md#L261-L275)).

This separation is useful prior art for FrockBot: a persistent transcript FTS index and a memory index solve different questions. FrockBot already has persistent UserDO FTS5 conversation-history search, while its hosted `memory_search` builds a separate lexical projection of memory files. A prepared prompt-memory view should not duplicate or replace transcript search.

## External-provider integration seam

The optional seam is `MemoryProvider`. One configured provider is loaded at agent initialization, checked locally for availability, initialized with session/profile/platform/identity context, and allowed to expose tools. The contract includes a static `system_prompt_block`, turn-start `prefetch`, post-response `sync_turn` and `queue_prefetch`, session-boundary extraction, pre-compression checkpointing, explicit tool dispatch, and mirroring of built-in memory writes ([provider contract](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/memory_provider.py#L75-L188), [single-provider registration](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/memory_manager.py#L283-L375)). Setup is opt-in through `hermes memory setup` or `memory.provider`; only one external provider is active at once ([setup and choices](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/user-guide/features/memory-providers.md#L7-L39)).

The host calls provider recall once before the tool loop for nontrivial input. The result is stored in `TurnContext` and reused across all model iterations in that turn. A provider call runs in a daemon thread, but the host joins it for up to eight seconds; timeout/failure yields no injected context and does not fail the turn. An unfinished provider is skipped on following turns until that call returns. Oversized recall can spill out of the prompt ([turn-start call](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/turn_context.py#L834-L862), [timeout and spill](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/memory_manager.py#L394-L448)). “Background, non-blocking prefetch” in the product page therefore needs qualification: the provider may have prepared a prior-turn cache in the background, but the turn-start host still makes a bounded synchronous call to consume it, and some adapters perform real retrieval there.

After a completed, non-interrupted response, `sync_turn` and `queue_prefetch` are submitted to one serialized background worker. The response is already available to the user, turn writes remain ordered, and interrupted/partial outputs are not ingested ([turn finalization](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/run_agent.py#L910-L940), [serialized background work](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/memory_manager.py#L463-L543)). At a real session boundary, extraction and provider rebinding are queued together in FIFO order; shutdown drains queued work for at most five seconds and explicitly records abandonment ([session boundary](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/memory_manager.py#L610-L645), [drain constants](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/memory_manager.py#L26-L32)).

## Voice path

Hermes' ordinary voice modes transcribe audio to text and send that text through the same chat turn. They therefore use the same active `AIAgent`, built-in snapshot, external provider, transcript persistence, compaction, and session search as typed input. Voice mode adds a concise-response note and streams TTS, but it does not define a separate durable voice-memory store.

The desktop's optional GPT-Live mode is a distinct realtime voice model with no Hermes tools. When it needs work, each delegation becomes a normal turn on the open Hermes chat, which then has the full toolset and memory; recent spoken exchange is supplied as a per-turn note. The first-party documentation explicitly describes that delegation boundary ([GPT-Live delegation](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/website/docs/user-guide/features/voice-mode.md#L205-L219)). Thus Hermes offers useful evidence that text and voice can share one memory path, but not prior art for FrockBot's separate voice durable/ongoing/recent store.

## What transfers to FrockBot

### Retrieval design with FrockBot's existing Vectorize and SQLite

Hermes points to a useful split between a compact always-present core and query-driven detail. It does not justify switching FrockBot to one of its vendors. FrockBot already has the main building blocks: authoritative Markdown memory, a per-file generation ledger, persistent SQLite FTS5 conversation history, a lexical memory-search path, and library support for Vectorize embeddings even though the hosted wiring does not currently supply embeddings/Vectorize to `backend-memory.ts`.

A proposal for later design discussion is:

1. **Always-present core:** a small prepared projection of identity, high-value preferences, active commitments, and other facts whose omission would make the Bot behave incorrectly. It should be derived from current authoritative facts/retractions and keyed to source generations.
2. **Current-query memory recall:** search within authorized Bot/User/joined-Project scopes using both Vectorize and lexical/exact lookup. Apply scope filters before `topK`, deduplicate by logical fact/source, verify candidates against the current authoritative file/generation and retraction/supersession rules, then inject only token-bounded excerpts with source references.
3. **Conversation recall:** retain the existing UserDO SQLite FTS5 history index for exact prior-turn recovery. Memory retrieval and transcript retrieval may be invoked together when a query needs both durable facts and the conversation that established them, but they should remain separately attributable.
4. **Write-to-index bridge:** make a newly accepted or retracted fact immediately visible to exact/lexical lookup and to prepared-view invalidation while its vector mutation is pending. Cloudflare documents Vectorize insert/upsert/delete as asynchronous and typically completing within seconds, so a vector-only read-after-write promise would be false ([Vectorize client API, retrieved 2026-09-22](https://developers.cloudflare.com/vectorize/reference/client-api/)). Query metadata should carry stable source/fact IDs and generations; `returnMetadata: "indexed"` avoids the documented overhead of fetching full metadata when indexed fields suffice.
5. **Scoped vector queries:** use namespaces and/or metadata filters for the admitted Bot/User/Project scope; Cloudflare applies filters before `topK`, and additional filter fields require metadata indexes ([Vectorize metadata filtering, retrieved 2026-09-22](https://developers.cloudflare.com/vectorize/reference/metadata-filtering/)). Authorization still belongs in FrockBot: a vector match is a candidate, not authority to read a source.

This needs stronger semantics than the current hosted memory-search path. The current code-path observation is that memory projection resolves shared retractions when reading authoritative memory, while the derived search index chunks raw `MemoryDocument` text and returns chunk snippets; lexical results are used as a fallback only when the vector score set is empty, rather than being fused as a true hybrid ranking. This note does not claim an exercised production bug, but a future retrieval design must ensure that a stale raw chunk cannot resurrect a retracted or superseded fact. Every hit should resolve through current fact identity, authority, and source generation before reaching the model.

Token efficiency should be explicit rather than delegated to vendor defaults. Hermes providers illustrate useful controls—Hindsight passes `max_tokens` to recall, Honcho clamps live context to a configured token-derived character budget, Mem0 caps per-message extraction input, and the host spills oversized provider output—but their guarantees differ by adapter. For FrockBot, retrieval should have a single kernel-owned budget covering the core projection plus recalled excerpts, with deterministic per-scope/per-source caps, deduplication, and auditable omission/truncation. That preserves low prompt cost while still letting exact or semantic recall reach memories outside the core.

### Strong ideas to adopt or adapt

- **A small prepared prompt view with explicit provenance/versioning.** Hermes reduces repeated file-read and prompt-render work by preparing the exact bounded text once and reusing it. FrockBot can apply the same principle to its Bot/User/joined-Project memory projection, but because those scopes have multiple writers and Durable Objects evict, the view should be durable or cheaply reconstructible and keyed by source generations. A merely resident cache would not solve cross-Bot freshness or eviction.
- **Separate source records from the prompt projection.** Hermes' Markdown files remain editable source, while its frozen rendered block is a derived prompt view. FrockBot can preserve authoritative R2 files and audit semantics while materializing the merged facts/retractions/truncation result used by a turn.
- **Move core selection and rendering off the critical path; use source expansion on demand.** FrockBot's current first step lists and reads every Bot/User/Project root, merges facts and retractions, truncates to 12,000 characters, and audits the injection. The analogous fast path would read one prepared core plus enough metadata to prove which source generations it represents, then add query-relevant excerpts. Persistent conversation FTS and explicit source reads remain separate expansion/recovery paths.
- **Fail open with strict latency bounds for semantic recall.** Hermes skips trivial prompts, reuses one recall result across all iterations of a turn, bounds provider waits, avoids concurrent pileups, and performs ingestion after reply. Those techniques transfer directly to FrockBot's current-query Vectorize/lexical retrieval, especially for voice; a recall timeout should degrade to the prepared core and exact/source paths rather than delay the whole turn indefinitely.
- **Record the exact injected view.** Hermes persists an `api_content` sidecar containing the actual external-memory injection sent to the model ([sidecar stamping](https://github.com/NousResearch/hermes-agent/blob/524041b9d0437cd4424a524af4b9e26145e69ab0/agent/turn_context.py#L865-L887)). FrockBot already has an injection audit record; a prepared-view optimization should retain that evidence, including generation/version identifiers.
- **Treat session-boundary/background extraction as asynchronous enrichment.** Hermes' periodic review and most provider ingestion happen after delivery. FrockBot should not put optional extraction, embedding, or provider synchronization ahead of chat or voice readiness.

### Ideas that do not transfer unchanged

- **Frozen-until-`/new` consistency is too weak for shared scopes.** Hermes explicitly accepts that a memory written mid-session is invisible to that session's prompt snapshot. FrockBot's User and Project scopes can be changed by other Bots, so it needs a freshness contract, not indefinite freezing. Generation checks, event-driven invalidation, or bounded-staleness leases are more appropriate than copying Hermes' session rule literally.
- **Injecting the entire store scales only because Hermes caps it at about 3.6K characters.** FrockBot already permits a 12K-character projection across multiple roots. A prepared view removes I/O/merge work but not prompt-token cost; current-query retrieval and tiering are needed to keep relevant recall broad without paying to inject every memory.
- **Provider prewarming often recalls the previous query.** Hindsight, Honcho, and RetainDB trade current-query precision for latency unless synchronous recall is enabled. That can be acceptable enrichment, but it should not be presented as equivalent to retrieval against the user's new utterance.
- **The external host timeout is not a zero-latency design.** Eight seconds is a resilience ceiling. Providers such as OpenViking, ByteRover, Supermemory, and Mem0 can still add noticeable work before the first model call. They are options for richer recall, not evidence that startup will be fast.
- **Hermes' external adapters have heterogeneous durability.** Some queue locally, some rely on cloud acceptance, some retry at least once, and mirror semantics differ. FrockBot's authoritative memory and effect-idempotency invariants should remain in its kernel rather than being delegated to a provider contract.
- **Holographic HRR is interesting but experimental prior art for this decision.** It is shipped code, but the available source and docs do not establish recall quality or startup benefit. Its transferable pieces are local SQLite/FTS, explicit fact IDs, trust/feedback, and structured update/delete—not a demonstrated need for HRR vectors.

## Practical architecture conclusion

For very fast FrockBot chat and voice startup with reliable recall, Hermes supports a proposed three-part direction for discussion:

1. A **durable prepared core projection** per Bot, derived from Bot/User/joined-Project sources and addressed by the source-generation set used to build it. It carries the small set of identity and behavioral facts that must always be present and retains the same injection audit evidence used today.
2. **Current-query hybrid recall on every substantive turn**, using existing Vectorize plus lexical/exact source lookup inside admitted scopes. Results are fused, deduplicated, checked against authoritative current generations/retractions, and packed with the core under a kernel-owned token budget. The model receives source references so it can explicitly expand a promising fact or file when the excerpt is insufficient.
3. **Durable freshness and recovery around asynchronous indexing:** newly accepted changes bridge through exact/lexical retrieval until Vectorize catches up; tombstones and generation checks prevent stale vector hits from resurrecting removed facts; existing SQLite transcript FTS remains the separate path to prior conversation evidence.

Hermes does not supply the invalidation design FrockBot needs. Its sources are mostly one profile's two local files, while FrockBot has shared multi-writer scopes and eviction. The useful borrowing is the prepared-view boundary, query-driven retrieval patterns, and off-critical-path ingestion lifecycle, combined with FrockBot's existing per-file generation ledger, Vectorize, SQLite FTS, and Durable Object coordination. A concrete design still needs to specify who materializes the core projection, how Project/User changes notify or invalidate every affected Bot, how lexical/vector scores are fused, what bounded stale behavior is acceptable during eviction/recovery, and how failed refreshes preserve the last known-good core without hiding its age. This is an architecture proposal for the walkthrough, not implementation approval.
