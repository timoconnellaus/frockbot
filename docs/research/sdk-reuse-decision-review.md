# SDK reuse decision review

Status: recommendations for discussion, **not new agreed plan decisions**. Reviewed against checkout `4a1bdd9ea7b0c74e60cfced0ae6e4d7fd98b8a8a`, the agreed startup sections of [the plan](../plan.md), and [runtime preparation](runtime-preparation-proposal.md). No implementation, model calls, live connections, or startup measurements. None of the recommendations below requires a baseline benchmark.

## Recommended boundary

**Reuse the SDK where it owns generic transport or scheduling. Keep FrockBot's durable authority, product policy and projections. Do not migrate BotState to Agent for this startup work.** Voice already gets the useful Agent facilities. The remaining startup changes concern the amount and ordering of application work, which a new superclass would not remove.

## Scheduling: useful reuse already exists

The pinned SDK distinguishes **stable Agent scheduling methods** from its **experimental standalone `Scheduler` capability**. The latter requires Lifecycle, which owns the physical alarm and job queue; it is not a callback utility that can harmlessly share FrockBot's existing alarm. [Public scheduling exports](https://github.com/cloudflare/agents/blob/agents%400.23.0/packages/agents/src/schedules/index.ts), [scheduler implementation](https://github.com/cloudflare/agents/blob/agents%400.23.0/packages/agents/src/schedules/scheduler.ts#L1).

For voice, use the stable methods already present in [VoiceAssistant](../../apps/cloudflare/src/voice-assistant.ts). The planned durable pending indexes/outboxes say **what work is owed**; an SDK schedule supplies **when to run its drain**. Job creation and wakeup must remain crash-safe, and callbacks must reconcile acknowledged work rather than blindly retry uncertain paid effects. Schedule creation deduplication is only deduplication of schedule rows. [Scheduling documentation](https://developers.cloudflare.com/agents/runtime/execution/schedule-tasks/).

For chat, replacing [alarm selection](../../core/durable/authority.ts) would also require transferring recovery, pending lanes and every contributed deadline. It would leave the important policies in [RoutineScheduler](../../app/routines/scheduler.ts): a deferral retains its original due time; late occurrences coalesce; each Routine has one unsettled firing; a bounded queue records additional obligations. The scheduler also feeds the domain inbox and failure policy. The [cron adapter](../../app/routines/cron.ts) already delegates parsing and IANA timezone handling to `croner`; this is not an entire cron implementation waiting to be replaced.

The concrete recommendation is to keep those small integration seams and domain policies, while removing startup scans through the already agreed indexes. Introducing SDK lifecycle/alarm ownership merely to run those same policies adds an integration migration without eliminating their code. This is a scope and semantic judgment, not a performance claim.

## Connections: distinguish transport from reliable publication

Standalone `agents/websockets` supplies hibernating connections, handlers and optional Cap'n Web RPC. It is explicitly experimental. Its optional Cap'n Web sessions are non-hibernating; they are unnecessary for a server-push observer. [Public exports](https://github.com/cloudflare/agents/blob/agents%400.23.0/packages/agents/src/websockets/index.ts), [connection capability](https://github.com/cloudflare/agents/blob/agents%400.23.0/packages/agents/src/websockets/websockets.ts#L59).

[BotStateChannel](../../apps/cloudflare/src/bot-state-channel.ts) already uses the platform's hibernation API. Most of the work we need to retain or add is durable cursor allocation, committed payload/outbox storage, bounded replay, snapshot consistency, identities and failure handling. Moving its socket enumeration and `send` calls behind Agent would leave that work intact while changing startup and protocol behavior. Keep its simple platform transport. Flutter should continue consuming the server-owned FrockBot protocol; adopting React clients would not remove the required Flutter integration.

This does not recommend copying SDK reconnection code. The voice Agent already uses its connection abstraction. For the Bot observer, the next implementation should change the existing publication contract as agreed, not introduce another framework connection alongside it.

## MCP: the manager's owner is the important constraint

The [preparation proposal](runtime-preparation-proposal.md) correctly identifies reusable discovery, connection and schema-conversion behavior in the pinned SDK. `MCPClientManager` persists registration/session information and restores HTTP connections in the background; its live catalogs do not replace the planned durable schema versions and Turn pins. Do not add `waitForConnections()` as a chat-start prerequisite. [Manager source](https://github.com/cloudflare/agents/blob/agents%400.23.0/packages/agents/src/mcp/client/index.ts), [official client documentation](https://developers.cloudflare.com/agents/model-context-protocol/apis/client-api/).

There are two additional integration constraints:

- The manager is a `LifecycleCapability` using Durable Object storage. Installing it outside `Agent.mcp` is explicitly experimental. A FrockBot Plugin runs in a Dynamic Worker and has granted loopback capabilities, not a Durable Object's storage/lifecycle. `new MCPClientManager(...)` alone does not bridge that difference. [Manager declaration](https://github.com/cloudflare/agents/blob/agents%400.23.0/packages/agents/src/mcp/client/index.ts#L385).
- The manager deliberately persists only a supported subset of transport options; it does **not** persist custom `fetch` functions. A Plugin-grant adapter provided only on initial registration cannot be assumed to survive restoration. Every restore/reconnect must reinstall the authorized transport before I/O. Default SDK OAuth storage also does not replace FrockBot's opaque Connection credentials. [Persisted options](https://github.com/cloudflare/agents/blob/agents%400.23.0/packages/agents/src/mcp/client/storage.ts#L50).

**Recommended implementation direction for the separately planned MCP work:** use a thin Plugin adapter over the official `@modelcontextprotocol/client` protocol and HTTP transport classes, routing its network and credentials through the existing `http`/Connection boundary. Cloudflare's pinned connection implementation already uses those classes, and its older Edge transport wrappers explicitly recommend the upstream classes instead. Do not deep-import its unexported connection internals or copy its state machine. [Cloudflare connection imports](https://github.com/cloudflare/agents/blob/agents%400.23.0/packages/agents/src/mcp/client/connection.ts#L1), [deprecated transport wrappers](https://github.com/cloudflare/agents/blob/agents%400.23.0/packages/agents/src/mcp/client/transports.ts#L1).

The integration must preserve Bot/Session/Turn association, validate current grants at use, keep secrets in the host, pin disclosed schemas, bound first-use discovery, and avoid repeating an action with an uncertain outcome. Background discovery must remain within existing granted authority. This is library reuse, not a new kernel MCP extension point or a Composio conversion.

Use the full Cloudflare manager only if its eventual durable owner can preserve those requirements through **supported** public hooks on initial connection and every restoration. Until that is demonstrated by interface design, treating the manager as the chosen drop-in library would overstate what the pinned SDK offers. The precise adapter/lifecycle owner remains an MCP implementation question; the startup design does not depend on settling it now.

## Skills: the useful abstraction is already in the agreed design

`agents/skills` is framework-agnostic and exported in 0.23.0, but officially experimental. Its useful pattern is a metadata catalog with bodies/resources loaded on demand. That matches the agreed durable-index direction. [Agent Skills documentation](https://developers.cloudflare.com/agents/runtime/execution/agent-skills/), [package exports](https://github.com/cloudflare/agents/blob/agents%400.23.0/packages/agents/package.json#L374).

Its registry keys Skills by name and resolves collisions by first source, emits its own prompt/tools, and delegates bodies to a source's `load(name)` method. Source fingerprints and optional version metadata are useful, but do not by themselves enforce FrockBot's exact-generation reads, reference authority or journal attribution. Recreating all of those around it would preserve most of our loader and add another registry. [Registry](https://github.com/cloudflare/agents/blob/agents%400.23.0/packages/agents/src/skills/registry.ts#L110), [source interface](https://github.com/cloudflare/agents/blob/agents%400.23.0/packages/agents/src/skills/types.ts#L96).

Keep [FrockBot's catalog](../../app/skills/catalog.ts), [Skill contracts](../../core/contracts/skills.ts), explicit load tools and refusal semantics. Refactor their storage/preparation, as already agreed. Do not add SDK script execution: scripts would be a new authority/execution surface, whereas the present Skills contract is instructions and references. A parser-only substitution is also unnecessary for this startup work; the existing bounded grammar should not change incidentally.

## Decision left for the user

There is no unresolved product decision required to implement the agreed startup changes. The recommendation to avoid a Bot superclass migration and to retain the domain machinery above is new advice for this walkthrough. If adopting the experimental modular lifecycle is desired as a separate maintenance project, it should deliberately transfer alarm/transport ownership and identify the custom infrastructure it deletes; it should not be bundled into startup work by default.

This review narrows the earlier [SDK assessment](agents-sdk-startup-assessment.md): **a baseline benchmark is not a prerequisite**. Source and interface analysis are sufficient to choose the boundaries above; correctness and dependency checks belong to implementation.
