# Conversations compact instead of forgetting

ADR 0027 bounded one model request at 150k characters and evicts whole Turns oldest-first when it overflows, leaving a plain notice saying how many are missing and that they are not summarised. That is a correct floor and a poor ceiling: a long conversation silently stops carrying its own beginning, and the only repair on offer is "start a new conversation", which is a different action for a different want. ADR 0027 itself named compaction as "a good thing to have later"; this is later.

The design is deliberately not the one the owner shipped and reverted in `zerobsai` (a per-Turn, in-request-path summariser on a second vendor whose output was never stored, so the same prefix was re-summarised, differently, on every Turn past the threshold). Three of its lessons are load-bearing here and each shows up as a decision below: the summary is a durable event computed once, the summariser is told to preserve identifiers verbatim and to list them, and tool outputs are pruned as a cheap tier before anything is summarised.

## Considered options

- **Summarise inside `turnScopedMessagesV1`, per request.** Rejected. It puts a model round-trip in the user's latency path, recomputes the same summary on every Turn, and makes the model's view of its own past non-deterministic with nothing on the log to say so — exactly the failure `zerobsai` reverted.
- **Summarise only at the "new conversation" boundary and write it to Memory.** Rejected as the _only_ move, for ADR 0027's own reason inverted: it is a good thing to have and a bad thing to have only. It does nothing for the conversation that is overflowing right now, which is the one the owner asked about. Memory at the boundary remains the right separate feature.
- **Delete or rewrite the covered Turns in the durable log.** Rejected. Nothing durable is deleted; the log is the reconstruction surface for the audit view and for every exact normalized model request.
- **Compact at Turn end into an append-only event, replayed thereafter.** Chosen.

## Decision

**A compaction is a durable event, computed once and replayed.** Three new session events, in the house intent/outcome shape: `conversation/compaction-intent` records the effect before the summariser is invoked; `conversation/compacted` carries the summary text, the Turn range it covers, the identifiers the summariser was made to list, and the provider and model that produced it; `conversation/compaction-failed` settles an intent that did not produce one. `deriveMessages()` is untouched — a compaction is not a message — and the narrowing policy reads the events, as it already reads `turn/admission`.

**The trigger is evaluated at Turn end, never before a model call.** The `agent/turn-stopping` hook, which fires after `turn/end` is appended and flushed, estimates what the _next_ Turn's window would carry and schedules nothing else. Compaction therefore never sits in the user's latency path: the cost is paid after the Turn the User was waiting on is already over. The estimate is the same character measure ADR 0027 chose, over the same window, for the same reason — a tokenizer in the loop would be a provider detail leaking out of the provider Package — and the threshold is 70% of the 150k budget. 70%, not 100%, so compaction lands _before_ tier 1 eviction would have had to drop a Turn: the two tiers are ordered by which loses less, and eviction is the thing compaction exists to avoid reaching.

**The summariser runs outside the Turn, and yields to the next one.** _(Amended after the first implementation shipped.)_ Being evaluated at Turn end is not the same as costing nobody anything, and the first implementation only got the ordering right: `agent/turn-stopping` is a hook the agent loop **awaits** inside `#runTurn`'s `finally`, so `whenIdle` — and behind it the run's terminal record, the deletion of `ACTIVE_RUN_KEY`, the `runs` broadcast and the HTTP response — all sat behind the summariser. A 40-second summariser produced a 50-second Turn against 5–9 seconds for its neighbours, with the client's ring spinning throughout, and it held the next message queued behind it too. So the hook now _hands the work off and returns_: the compaction runs detached, on the Composition the Turn mounted, which is disposed when the compaction finishes rather than when the Turn does. The Turn ends, the run settles, and the response goes out while the summariser is still running.

Detached work and a new Turn must not both be writing the session log, and the choice between them is not close: **the compaction yields.** The next admission aborts it and waits only for that abort to unwind, which is the difference between a person waiting a moment and a person waiting a minute. An aborted compaction leaves an intent with no outcome, which is exactly the case above — the next Turn end settles it as a failure and backoff picks the same range up again. Losing a compaction costs one summariser call and a later retry; making somebody wait for one costs the thing this decision exists to avoid.

**Three tiers, cheapest first, and only the third costs a model call.**

1. _Prune old tool outputs_ — a deterministic assembly rule, no durable write, no model. A `tool/result` message belonging to a Turn older than the newest three keeps its role, `callId` and `name` and has its content replaced by a `[pruned]` stub. The message survives, so the call/result pairing every provider validates survives with it; the payload, which is what actually dominates a long conversation, does not. This is `zerobsai`'s one genuinely good middle tier, and it fits FrockBot's model unchanged because a Turn kept with its tool payloads elided is still a well-formed Turn.
2. _Summarise_ — the oldest Turns, when the pruned window is still over threshold.
3. _Evict whole Turns_ — ADR 0027's existing floor, unchanged, still with its notice. It is also the fallback: a summariser that fails changes nothing, and the request that follows is exactly the request ADR 0027 would have assembled.

The trigger measures the _pruned_ size, so a conversation whose weight is tool output pays no summariser at all.

**A compaction always covers a prefix, so a range is a single number.** The covered range is Turns 1 through `throughTurn`, where `throughTurn` is the newest Turn outside the most recent four. Anchoring at the first Turn is what makes a later compaction supersede an earlier one rather than accumulate beside it: assembly reads only the newest `conversation/compacted`, and the _fold_ happens in the prompt — the previous summary is handed to the summariser as the preamble of the range it is extending.

**The last four Turns are verbatim, and Memory is not history.** The four most recent Turns are never covered by a compaction and never pruned; the current Turn is carried whole, as it always was. Nothing the User pinned and nothing Memory injected can be lost to compaction, because neither is in the window: Memory reaches the request as a prompt section rendered fresh on every Turn and recorded in `memory/injected`. That is a property of the seam, not a rule this feature has to keep.

**Injection: the summary is the first message of the window.** For a conversation with a `conversation/compacted` event, assembly emits one `user` message carrying the summary block ahead of everything else, and drops the messages of every Turn it covers. Order is summary, then pruned history, then the current Turn.

**The summariser runs on the Bot's own model, through the ordinary binding.** No second vendor: the Bot's resolved provider and model, invoked through `ctx.llm`, under a bounded 60-second deadline. Its prompt fixes four headings — `## Summary`, `## Decisions`, `## Open items`, `## Identifiers mentioned` — and carries the identifier rule verbatim from the owner's earlier work, because FrockBot's stakes are higher than a chat app's: a summary that paraphrases a Package id, an Applet id, a Session id or a Workspace path produces a Turn that calls a tool with a plausible-looking wrong argument. Forcing the model to _list_ the identifiers it saw is a far stronger constraint than asking it not to mangle them in passing, and the list is stored as its own field so a test can assert on it.

**Failure is non-fatal, recorded, and retried with backoff.** Any failure — deadline, provider error, an empty or unusable summary — appends `conversation/compaction-failed` and returns. The conversation carries on under tier 1. The next attempt is at a later Turn end, spaced `min(2^failures, 8)` Turns from the last failure, counted from the log; there is no permanent give-up, because eviction already keeps the Bot working while compaction keeps missing.

**Idempotency is keyed by the covered range.** Before appending an intent the writer refuses if a `conversation/compacted` already covers `throughTurn` or more. A restart mid-compaction leaves an unsettled intent on the log; the next Turn end settles it as `interrupted` and lets backoff schedule the retry — ADR 0028's shape, for the same reason. Because the Durable Object is single-threaded and the check runs immediately before the append, no range can be compacted twice.

**Compaction does not write Memory, and this slice does not surface a "worth remembering" list.** `zerobsai` ran compaction and Memory as two systems that never spoke and could inject the same fact twice; the fix for that is a deduplicated writer, and Turn end is the wrong place to acquire one — a Memory write is a tool effect with its own intent, provenance and open step, and Turn end has no step. So the line is drawn instead: **Memory is the durable cross-conversation tier, written deliberately through `memory_write` by the Bot inside a Turn; a compaction summary is the within-conversation tier, bounded, superseded, and scoped to one Session's log.** Routing durable facts out of a summary and into Memory without double-injection is deferred, deliberately, and is a follow-up rather than an omission.

**The User is told, quietly, at the boundary.** The transcript renders one subtle system line — "Earlier messages were summarised" — and everything above it stays exactly as readable as before, because nothing was deleted. _At the boundary_ is load-bearing and was got wrong once: a compaction is written at the end of the Turn that crossed the threshold, which is the newest Turn, so dating the marker by when it was written put it under the newest reply — saying the opposite of what it means. The marker is dated by the `turn/end` of `throughTurn` instead, so it sits between the last compacted Turn and the first verbatim one and stays there as newer Turns arrive; where the covered Turns have scrolled out of the page, it sits at the top of what remains. This is the difference between this feature and the one that was reverted: `zerobsai`'s compaction was observable only in a `console.log`, which is why nobody could weigh it. ADR 0027's "they are not summarised" notice still stands where Turns were genuinely evicted, so the two notices never claim each other's ground. The "new conversation" path is untouched.

## Consequences

- A long conversation now keeps its beginning in a compressed, inspectable form instead of losing it silently, and the compression is paid for once per range rather than once per Turn.
- The exact history each Turn ran on stays reconstructable: the summary is on the log, the pruning rule is deterministic from the log, and `model/request` still records the exact normalized request.
- A Bot's model spend gains a bounded new line item — one summariser call per compacted range — which is subject to the same durable per-User quotas as any other model call.
- A summary is model output stored durably and replayed into later prompts. It is bounded in length, it is superseded rather than appended to, and it is visible in the audit view; it is not, and must never become, an authority for anything the Bot does.
