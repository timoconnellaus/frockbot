# Host the Fly Computer adapter in shared Cloudflare Containers

FrockBot will run the Fly Sprites Computer adapter as a shared, non-authoritative backend service in Cloudflare Containers rather than inside each Bot Durable Object. A real Workerd compatibility test proved that bounded command execution works but file I/O through `@fly/sprites` fails because its HTTP exec protocol relies on response chunk boundaries that Workerd does not preserve; a Node-based container retains the Cloudflare operational boundary while providing a general-purpose runtime for the SDK.

## Considered options

- **Per-Bot Durable Object:** keeps the adapter beside orchestration, but cannot reliably support the provider-neutral Computer interface with the current Sprites HTTP protocol.
- **Per-Bot container:** maximizes isolation but duplicates cold starts and cost even though untrusted execution is already isolated in each Bot's Sprite.
- **One permanent global container:** is sufficient for a prototype but creates a bottleneck and broad failure domain.
- **Shared container service:** chosen. One logical service may use a single container initially and shard or scale its containers later without changing the Computer interface.

## Status

Implemented and now the production path, on both sides of the seam. `apps/computer-host` is the host. `packages/computer-host-protocol` is the versioned seam both sides decode, and `packages/computer-host-runtime` holds the Computer's on-Sprite layout and scripts once, shared with `@frockbot/plugin-fly-sprite`.

`@frockbot/plugin-fly-sprite` is now a thin client of that host: `ComputerHostClient` speaks the v1 protocol over the app Worker's `COMPUTER_HOST` service binding, and `FlySpriteComputer` holds no Sprites SDK, no token, and no provisioning sequence. `SPRITES_TOKEN` survives on the app Worker as one thing only — the answer to "has this deployment a Computer at all" — and with it unset the Computer card still reads "Set SPRITES_TOKEN to attach a computer". A viewer session and the human-takeover lease are reachable from a Bot Durable Object for the first time, because both need the Sprite's URL and its `flock` and neither was reachable from workerd.

`apps/fly-host-prototype` is deleted. It ran the provider _inside_ its container against the SDK — the arrangement this ADR replaced — so it could not survive the provider becoming a client. What it proved is recorded below and in `apps/computer-host/live-test.ts`, which drives the same claims against a real disposable Sprite from the production image.

## Consequences

Each Bot Durable Object remains authoritative for admission, ordering, cancellation, durable effect intent, idempotency, and reconciliation. It calls the internal service through narrow versioned DTOs carrying Bot identity, assignment generation, operation data, and an effect identifier. A host-side Durable Object journals intent and normalized outcomes so a retried effect replays or remains explicitly unresolved instead of executing twice. The container resolves `SPRITES_TOKEN` server-side, holds no canonical Bot state, and treats process loss or restart as normal. The production host and its live test cover command execution, streaming, file operations, cancellation, adapter reconstruction, and cleanup without changing the Bot Agent loop.

## What the live measurements changed

Two failures were measured against real infrastructure, and together they decide the shape of the host rather than merely its location.

**HTTP 431, and it is not a Workerd problem.** A live probe with a real token reached `FlySpriteComputer.provisionRuntime` and failed with `APIError: API error (status 431)` — Request Header Fields Too Large. `execFileHTTP` appends every argv element to the request URL as `cmd=`, and the ~1.9 KB provisioning script (~2.7 KB base64-encoded) exceeds Fly's limit. Measured directly against the Sprite with curl: a short `cmd` answers 200, a ~2.5 KB `cmd` answers 200, the provisioning script answers 431. This is a server-side limit and is independent of the runtime making the call, so **the provisioning path could not have worked from any runtime as written** — not from Workerd, not from Node, not from a laptop. The Sprites SDK's WebSocket `spawn` puts the command's environment into the same URL, so environment variables are bounded by the same limit.

The consequence is a rule, not a workaround: **nothing large travels on a command's argv or environment.** Every command the host runs is `bash -s` with a two-element argv, the script arrives on the command's stdin, and a requested `cwd` and `env` are compiled into that script as `cd` and `export` lines. File bytes never pass through a shell at all; they use the Sprites filesystem API. The host's live test sends a 19 KB script over stdin to a real disposable Sprite and asserts exit 0, so the regression has a standing proof.

**The chunk-boundary framing bug is real but was never reached.** `execFileHTTP` parses one `reader.read()` chunk as one protocol frame and throws when a transport coalesces or re-splits the body. It sits one layer behind the 431 and was therefore never exercised by the product. It is also now unreachable: the host uses the SDK's WebSocket `exec`, which is available from Node and not from Workerd, and its own answers are NDJSON, where the frame boundary is a newline the reader finds and a transport chunk means nothing.

## Pins and the standing bill

A third defect in the same 0.x, measured on 2026-08-31 against a real Sprite from the production image: `WSCommand`'s keepalive declares a healthy connection dead after `WS_PONG_WAIT` — 45,000 ms — without an **inbound message**, and its `WS_PING_INTERVAL` timer (15,000 ms) only measures that gap; it never sends a ping, and the code says why ("the server-side handles keepalive; we just track activity"). `ws` is private and no option exposes it, so a command that is merely quiet is indistinguishable from a command whose connection died. `/v1/computer/open` ran the provisioning document in one exec, and its `apt-get` phase is silent for minutes, so a first `open` on a cold Computer failed reproducibly with `provider-unavailable: Computer command failed: WebSocket keepalive timeout`.

**Resolved by never holding a long connection.** Sending pings was impossible, and a heartbeat on stderr would have made the whole install depend on one WebSocket surviving minutes of `apt-get` — a connection this project already assumes will drop ("Connections to the Computer are expected to drop on every pause"). Provisioning is therefore a _detached_ run that the host polls. One short exec installs the document (on stdin, never argv) and starts it under `setsid nohup` behind a `flock`; every later exec is a poll that answers immediately, so no connection is ever quiet for 45 seconds. The document is divided into five declared phases, each guarded by a marker file under the runtime root, so a run that starts again **completes** a half-provisioned Computer rather than repeating it — which is what a container restart, a Sprite pause, or a dropped client looks like. The host restarts a provisioner that has gone away, rides out an unreachable Computer for two minutes at a time, bounds the whole run, and reports the phase it reached in the `open` result and in its own log, so a cold open is progress rather than silence. Two further defects were measured while proving it and are fixed here: a second `flock -n` probe in the launcher raced the provisioner it had just started and killed it silently (the launcher now probes once, before starting anything, and the provisioner waits for the lock), and the SDK emits `error` more than once for a WebSocket that never opens, which reached an emitter with no listener left and **killed the container**, taking every other User's work with it (the host's `error` listener is now permanent).

**And what that uncovered: a cold Computer cannot finish installing.** With the connection no longer the limit, the install itself became measurable for the first time, and it does not fit. Measured on 2026-09-01 against a disposable Sprite (8 CPUs, 8 GB, not resource-starved): `apt-get update` alone takes **262 seconds**, and the `apt-get install` that follows was still downloading its 37th package **25 minutes** in, when the probe gave up. Two live `open` runs agree — each sat healthily in `installing the desktop packages (2/5)` for the full ten-minute bound with no dropped connection and no retry, which is itself the proof that the keepalive defect is gone, because the old code could not survive forty-six seconds of it. The package list was the visible half of it — Ubuntu's `chromium` is a snap transitional package, so it drags in `snapd` (42.6 MB) and `systemd`, and the recommends closure adds `python3-numpy`, `liblapack3`, `poppler-data`, and fonts nobody asked for — and `/v1/computer/open` on a cold Computer ended at its bound with `Computer provisioning exceeded 600000ms during installing the desktop packages (2/5)`, failing the host's `test:live` there. The reading of _why_ was wrong, and the paragraph below corrects it. The ten-minute bound is kept, because a Computer that takes half an hour to open is not a Computer a Bot can use.

**And what it actually was: nothing was holding the Sprite awake.** The reading above — "the cost is the package list" — was wrong, and the way it was caught was a clock. Measured on 2026-09-01 on a disposable Sprite running the detached provisioner: the Sprite's own `/proc/uptime` and `ps` elapsed times advanced about **4 minutes while ~25 minutes of wall time passed**. The install was not slow; it was **suspended**, and it ran only in the moments the host's polls woke it. Sprites define activity as "a command running, a session producing output, an open TCP connection to its URL, a service handling traffic" ([Idle detection](https://docs.sprites.dev/working-with-sprites/#idle-detection)), and a `setsid nohup` background process is **none of those** — which is the sharp edge of the previous fix: making provisioning survive a dropped connection also made it something the platform is entitled to pause. The documented hold is the Tasks API on the Sprite's own management socket `/.sprite/api.sock`: "Register a task; the Sprite stays up. Delete it (or let it expire); the Sprite is free to pause again." ([Keeping a Sprite running](https://docs.sprites.dev/keeping-sprites-running/)). The provisioning document now registers `frockbot-provision` with a five-minute expiry, refreshes it every 60 s from a child process, and releases it on an `EXIT` trap, so a provisioner that dies stops paying for the Sprite within one expiry rather than pinning it awake. With that hold in place the same `apt-get update` that this ADR recorded at **262 s** measured **6 s**.

**A custom image and a shared snapshot were both checked first, and neither exists.** `POST /v1/sprites` accepts `name`, `wait_for_capacity`, and `url_settings` and nothing else — no image, no region, no size ([Sprites API](https://docs.sprites.dev/api/dev-latest/sprites/)); the pinned SDK adds only a `default`/`dev` runtime variant. Checkpoints do persist installed packages, but they are addressed per Sprite (`/v1/sprites/{name}/checkpoints/{id}/restore`) and nothing documents restoring one onto a different Sprite, so they cannot be a prebuilt image for a Computer that does not exist yet ([Checkpoints](https://docs.sprites.dev/concepts/checkpoints/)). So the fix had to be the provisioning run itself, and it is three changes beyond the keepalive. The browser is no longer the distribution's: `chromium` on the base image is a snap transitional package, so the Computer downloads Playwright's own Chromium build instead and `start-desktop.sh` runs it through a stable symlink at `/home/box/bin/chromium`. Playwright 1.55 refuses the base image outright — "Playwright does not support chromium on ubuntu26.04-x64" — so the phase names the newest build it does have, `ubuntu24.04-x64`, which was verified running headful under Xvfb with CDP answering. The remaining packages are installed `--no-install-recommends`, which is what keeps `python3-numpy`, `liblapack3`, `poppler-data`, and a font collection out of a cold Computer. And a PATH preamble puts the real toolchain ahead of `/.sprite/bin`, because `/.sprite/bin/node` is an nvm shim whose last resort for finding the binary is `command -v node` — itself, in the non-login shell a detached run gets — so it re-execs for ever; a detached `node --version` was measured never returning.

**Measured after the fix, on a real cold Sprite from the production image:** three runs completed a first `open` in **166 s**, **135 s**, and **120 s** (the last with `scrot` added to the list by #69), each over a single connection, with no dropped connection and no provisioner restart — `apt-get update` 6 s, the desktop packages 82 s, Playwright's Chromium about a minute, and the rest cold-start first reads. A second `open` adopts the Computer and provisions nothing in **463 ms**, **348 ms**, and **355 ms**. `apps/computer-host/live-test.ts` asserts both with wide margins — eight minutes for a cold open, thirty seconds for a warm one — so the assertion fails on a regression back into the ten-minute bound rather than on a slow archive.

`@fly/sprites` is pinned to exactly `0.1.0` — a 0.x with the framing bug above — and is loaded in exactly two places, `apps/computer-host` and `packages/computer-host-runtime`. Containers require the Workers Paid plan; the host runs `basic` instances with `max_instances: 3`, `sleepAfter: "10m"`, and two warm shards, so a first call after an idle period pays a cold start rather than the account paying for permanent warmth. Requests are routed by **userId** (ADR 0012), so every Bot of one User reaches the one container that holds that Computer's display-slot registry and `flock`-serialized takeover lease. The host Worker must be deployed before the app Worker on every release, or the app's `COMPUTER_HOST` service binding resolves to a stale image.
