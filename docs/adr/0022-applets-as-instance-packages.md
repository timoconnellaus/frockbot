# Applets: Instance Contributions as facets under a kernel-owned Applet Durable Object

Accepted by the owner on 2026-09-03, in conversation, together with the `AGENTS.md` amendment this ADR names. This ADR amends [ADR 0011](0011-minimal-kernel-and-self-modification.md).

FrockBot will let a Bot build **Applets**: small, real-time, account-wide applications a User opens beside the conversation — a todo list, a slide deck, a website builder — each with its own durable state, its own UI, and tools a Bot can call. An Applet's code is a Package; an Applet's state is not. The code is versioned, content-addressed, and reverted exactly like every other Package generation. The state lives in a **Durable Object facet** that the kernel mounts under a kernel-owned `AppletState` Durable Object, survives every code change, and is migrated forward by the Applet itself. The Applets product — the Bot's verbs, the sidebar entry, the list, the canvas beside the chat — is itself a Package built only from the Contribution kinds a Bot can author, and it is loaded through the same path as a Bot-authored Package. Applet source is authored as TypeScript at a durable root on the User's Computer, type-checked, linted, and previewed there through an SDK that embeds workerd, and published as an immutable artifact; the Computer is where an Applet is written, never where it runs.

## What ADR 0011 rejected, and why this is different

ADR 0011 said: "Durable Object facets are not used: a facet owns its own storage, which would make loaded code a second durable authority." That sentence protected the **Composition**: the versioned set of Package code a Bot mounts, which must revert as a set and must never hold state the kernel cannot see, pin, or roll back. Tool Packages hold no state of their own for exactly that reason, and this ADR does not change it.

An Applet instance is not Composition. It is **product state owned by the User**, like Memory files or a Bot's session log: a document, a list, a board. That state must survive a code revert, and a Bot that reverts an Applet's code expects its todos to still be there. cloudflare-os draws the same line — a Blueprint captures a gadget's code and never its storage, and a code change aborts the facet and remounts new code over the same state — and FrockBot copies it. So the amendment is narrow. Facets remain forbidden for Composition Packages. A new Contribution kind, the **Instance Contribution**, mounts as a facet under a kernel-owned Durable Object, and the kernel keeps every authority that matters: the instance directory, creation, deletion, which code generation is mounted, remount on version change, the viewer sessions, tool routing, and every record of those. What the kernel gives up is authority over the _contents_ of the facet's storage, which is the correct trade, because the kernel has no business knowing what a todo is.

## Considered options

- **Kernel-mediated storage capability (a `storage` RPC on `CAPABILITIES`, backed by a kernel-owned table namespace):** keeps one durable authority with no amendment, but every storage feature — SQL, transactions, alarms, WebSocket sessions, hibernation — becomes something the kernel has to build and version, and an Applet with real-time collaborators would be re-implementing a Durable Object over RPC. Rejected: it is the facet, at arm's length, with worse semantics.
- **Applet instance state inside the Bot Durable Object or the User Durable Object:** the fewest new objects, but an Applet is account-wide and the Bot is the wrong owner; the User Durable Object is the hot path for every request and must never be reachable by a future collaborator. Rejected.
- **A facet of a kernel-owned per-Applet Durable Object, with the kernel owning lifecycle and the Applet owning contents:** chosen. It is cloudflare-os's Overseer in FrockBot vocabulary, it gives the Applet a real Durable Object with SQLite, alarms, and hibernating sockets at zero kernel cost, and the kernel's authority over the instance is complete without its authority over the contents.
- **Author Applets by handing source to the bundler service (the `package_author` path):** consistent with Bot-authored tool Packages, but denies the Bot a type checker, a linter, a local run, and a screenshot, which is where an Applet is most likely to be wrong. Rejected as the primary path; the durable root plus the Computer keeps every one of those and reuses the sync ADR 0013 already proved.
- **The Applets product as first-party in-process Contributions:** the fastest build, but it would make the Applets Package the one Package a Bot could not have written, and the owner set "the same Package must be buildable inside a Bot" as a hard requirement precisely because it is the pressure test that kills the last static switch. Rejected.

## Decisions

1. **Instance Contribution.** A Package manifest may declare `contributions.instance`: an immutable server artifact exporting a Durable Object class, an immutable UI artifact, the tools the instance exposes, and the Instance Contract version it speaks. A manifest may carry an Instance Contribution only with a non-first-party or artifact-backed member; the kernel never runs instance code in its own isolate.
2. **`AppletState` Durable Object.** A kernel Durable Object class, keyed `<userId>:<appletId>`, is the authority for one Applet instance: its current code generation, its version history, its viewer sessions, its tool declarations, and its deletion. It loads the Applet's server artifact through the `APPLETS` Worker Loader binding with `globalOutbound: null` and only `CAPABILITIES` and `IDENTITY` in `env`, and mounts the loaded class as a facet named by the artifact hash. A version change aborts the facet and remounts the new class over the same storage. Deletion deletes the facet and its storage, the version records, and the directory entry; artifacts are immutable content and are left to the existing garbage collection.
3. **Applet directory in the User Durable Object.** The User Durable Object owns the account-wide list of Applets: id, display name, the current generation, tool declarations, and creation provenance. Enablement is account-wide by ADR 0019; there is no per-Bot Applet.
4. **Applet tools are Composition members.** Every Bot of the User sees every Applet's declared tools. They enter each Bot's Composition as members of kind `applet`, so every admitted Turn records exactly which Applet generation's tools it ran under, a version change activates at the next admitted Turn, and a tool call routes to the `AppletState` object, which forwards it to the facet. Applet tool descriptions carry the Applet's provenance into the tool catalog.
5. **Real-time by default.** An open Applet holds a hibernatable WebSocket to its facet, minted through a short-lived viewer token the shell obtains with the User's session, because the Applet's page runs in a cookieless sandboxed iframe and can carry no credential. The SDK's client is TanStack DB over that socket: schema-first tables declared once on the server produce the SQLite schema, the typed mutation handlers, and the client collections with live queries and optimistic mutations that roll back on rejection.
6. **Versions, not branches.** Publishing an Applet appends an immutable generation and makes it current; revert is a pointer move that is itself a recorded generation; last known-good is set only by a successful mount. There is no per-chat proposed-changes branch. Preview is a local run on the Computer, opened in the Computer's browser, which the Bot can screenshot.
7. **Authored on the Computer, run in the loader.** Applet source lives under a `package-declared` durable root of the Applets Package, `applets/<appletId>/`, synchronized by the durable-root sync of ADR 0013. The Applets SDK on the Computer type-checks, lints, and bundles it, and embeds Miniflare to run the server class as a plain SQLite Durable Object with capability service bindings. ADR 0011 rejected running Bot-authored _tools_ on the Computer because a Turn would then depend on Computer availability; that objection does not apply here, because the Applet runs in the loader and the Computer is only where it is written. Publishing reads the built artifact from the durable root through the Workspace file surface and records the generation; no credential reaches the Computer for it.
8. **The Applets Package is Bot-shaped.** `@frockbot/plugin-applets` has no in-process code. It is a bot-isolate runtime Contribution (the `applet_*` tools over the kernel's `ctx.applets` capability) and iframe client pages with declarative entries. It ships in the foundation application as an artifact-backed member with first-party provenance, so it loads through the loader path, and an architecture check authors the same Package through `package_author` and proves it mounts and behaves identically.
9. **Declarative entries.** A client Contribution may declare entries — a sidebar action, an overlay surface — that the shell renders from the manifest with no Package JavaScript in the app origin. The Applets entry sits above Connectors in `frockbot.sidebar-actions`. The canvas is an iframe page in `frockbot.right-panel`, shown when the Session has a focused Applet, hidden by the existing phone layout until opened.
10. **Design language.** The SDK ships a small precompiled React component kit on the same semantic tokens `plugin-ui-theme` declares; the host injects token values and theme changes into the frame. The kit is versioned once in the SDK and never copied into an Applet. A custom linter enforces the kit and the SDK's rules and grows from observed failures.

## Consequences

The kernel gains one Durable Object class and one capability, and loses the last static switch: every Contribution kind the Applets Package needs is manifest-resolved from an artifact, so a Bot-authored Package can declare exactly what the first-party one declares. ADR 0011's rejection of facets now reads as a rule about Composition Packages, and `AGENTS.md` says so.

Applet state is the first durable state outside the kernel's records that the kernel does not understand. The kernel still owns its lifecycle, and the Applet owns its migration: the SDK's `migrate` hook runs on remount, and an Applet that cannot read its own old state has failed its health check, which fails the activation closed to the last known-good generation with the old facet still resident.

"Not Cloudflare-specific" has a ceiling and this ADR states it. The SDK hides every binding behind typed capability stubs, but a Durable Object with alarms and hibernating sockets is a Cloudflare programming model; another host would have to reimplement that model, not swap an adapter.

Deferred, deliberately: per-User quotas for Applet storage and count (they join spend tracking), export of an Applet's SQLite, collaborators and cross-User sharing, and public unauthenticated access for a website builder. The instance directory, the viewer-token shape, and the `AppletState` object are designed so each of those is an addition, not a change.
