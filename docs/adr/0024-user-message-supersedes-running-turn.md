# A user message sent mid-Turn supersedes the running Turn

Accepted by the owner on 2026-09-03.

Until now the composer locked while a Turn ran: `isRunning` disabled the textarea and the send button, and the Bot Durable Object refused a second command with `bot already has an active run`. A User who saw the Bot heading the wrong way had one move — Stop — and then had to retype.

GrokBot does not work that way. Its send pipeline interrupts the running Turn with `interrupt("superseded by a new user message")` and enqueues a new exclusive run on the `user` lane; the new message is a **new Turn**, never an injection into the request already in flight. `interrupt()` deliberately does not abort `Task` subagents — only `interruptAll()`, used when an agent is deleted, does — so background work started by the interrupted Turn keeps running, and the harness sets `unfinishedTasksReminderPending` so the next Turn is told about it. This is parity register row 57i (§B, send pipeline).

## Considered options

- **Inject the new text into the running Turn at the next step boundary** ("steering", the Claude Code shape). Cheaper: no second run record, no terminal state, no lane. Rejected: it is not what we are copying. The running Turn's model request would gain a message it was not admitted with, so "the durable session event log reconstructs every exact normalized model request" would need a new event type to stay true; the Turn's recorded input would no longer be the input it was admitted on; and the User's second message would inherit the first Turn's Composition pin rather than being admitted on the current one. A previous attempt down this road is in `~/tmp/frockbot-steer-partial-claudecode-style.patch`; its client-side pieces were reused and its `input/steer-*` events were not.
- **Refuse the second message and keep the composer locked.** The status quo. Rejected: the register row is a capability the product must match, and "wait until it stops talking" is the thing GrokBot Users do not have to do.
- **Queue the second message and let the first Turn finish.** Safe and simple, and wrong: a Bot that has just been told it is doing the wrong thing carries on doing it for another minute. It survives as the behaviour for the one case where interrupting would strand something (below).
- **Supersede: interrupt the running Turn, admit a new one.** Chosen.

## Decision

**A supersede is an explicit authenticated command.** "Client disconnect, refresh, or shutdown detaches an observer; only an explicit authenticated command cancels work," so the intent to interrupt travels with the Turn command: `ClientTurnCommandV1` gains an optional `supersedes: { runId? }`, decoded at the seam exactly as `ClientRunStopCommandV1` is. Without it a second command is refused as it always was, so a reconnecting client can never interrupt a Turn by accident.

**The intent is the field's presence; `runId` is provenance and is optional.** The composer sends `supersedes` on _every_ send, because "replace what you are doing with this" is what a person means by pressing send, and it does not depend on what their client had managed to observe first. Gating the intent on an observed run made the product refuse messages people had every right to send: the composer unlocks the instant a Turn settles, and a fast typist — or an automated client — beats the next poll, so the second message arrived with no intent while the first Turn was still active and the Bot answered "bot already has an active run". That is a race in the client's knowledge, not a difference in what the User asked for. So an empty `supersedes: {}` supersedes exactly as a named one does; a named `runId` records which run the sender had observed, which may already be stale by the time the command lands, and is never the target. The whole field is part of the command fingerprint, so a replayed command replays its own Turn and can never interrupt a second one, and nothing but the composer sends it.

**Admission is durable before acknowledgement.** The new Turn is written in the admission transaction with `phase: "queued"` and recorded in the run index, alongside `pending-run` naming it. Only then is the running Turn's `supersededAt` / `supersededBy` recorded, and only then is the resident Agent signalled. The signal is advisory; the durable intent is what stops the Turn, because `admitRunEffect` fences every new provider call and tool effect from the instant `supersededAt` exists — the same fence Stop uses, for the same reason.

**The superseded Turn reaches a distinct durable terminal state.** Status `superseded`, with `supersededAt` and `supersededBy` on the record, no response text and no failure — the sibling of `cancelled`, not a variant of `failed`. Its `turn/end` carries `outcome: "cancelled"` and `reason: "superseded by a new user message"`, which the Agent loop now records because `cancel()` accepts an opaque detail string it never interprets. A Turn superseded while still queued appended no event and spoke to nobody, so it settles as a record on its own and never touches the session log.

**Stop outranks supersede.** If both intents stand on one run, the settlement is `cancelled`: the User asked for that Turn to stop, and a message that arrived afterwards does not turn their cancellation into something else. Stop targets the Turn that is executing, never the one waiting behind it, so a Stop after a supersede does not discard the message already admitted as the next Turn.

**Lanes.** The run record carries an admission lane, `user` or `background`. A `user`-lane admission carrying supersede intent replaces the active run and any run already waiting behind it; a `background` admission — a Routine firing, a subagent dispatch — never supersedes and is refused exactly as a second command always was, so a firing waits for its own next schedule rather than interrupting a person mid-sentence. The lane is derived from the recorded turn type (`chat` ⇒ `user`, everything else ⇒ `background`) and written explicitly only when it differs, so no stored byte of today's records changes. Issue #151's bot-to-bot messaging adds an `agent` lane by naming it in that field; nothing else moves.

**The queue is one slot, not a backlog.** A second waiting message supersedes the first waiting one exactly as it supersedes a running one, so three messages in quick succession leave three terminal-or-running Turns in admission order and the Bot never works through a queue of things the User has already replaced.

**The not-yet-dispatched exception.** A running Turn that has not journaled a `model/request` has reached no durable checkpoint, so there is nothing to interrupt and nothing to lose. It is left to finish and the new message queues behind it. This is GrokBot's own line and it exists so that no message is stranded before its first durable checkpoint.

**A reconciliation-required run is never superseded.** An uncertain external effect is retrieved, not abandoned: the admission is refused with a message naming the run, and the User resolves it exactly as they do today.

**Background work survives.** Nothing in the supersede path touches the subagent task store: a dispatched `Task` keeps running in its Subagent Durable Object and settles normally. The reminder GrokBot calls `unfinishedTasksReminderPending` is a durable **pending input** here — a fourth `PendingBotInputV1` variant, `superseded-turn` — written in the same transaction that settles the run and drained once by the next conversational Turn, ahead of the person's own words. It says the Turn was cut off, that nothing still in flight may be assumed to have happened, and, when the Turn had dispatched subagents, that they are still running.

**How the superseded Turn appears to the next model request.** Exactly as its durable events describe it, and by no special case: `deriveMessages` walks the log, so the replacement Turn's request contains the superseded Turn's `user/message`, every `assistant/message` it produced, and every `tool/result` — completed ones with their content, and anything unresolved at the interrupt closed as `status: "interrupted"`, `isError: true`, "Interrupted before a durable result was recorded." An in-flight effect is therefore visible as an effect that did not return, never as a success. The interrupted Turn's leftover reasoning is not re-fed because it was never an event. The queued Turn's `previousEventCount` is recomputed when it is promoted, not when it was admitted, so it starts from everything the Turn ahead of it made durable. `deriveMessages` stays deterministic and the log stays the single source of the request.

## Consequences

**A refused admission is 409, not 500.** The Turns route tells an admission the Bot declined — busy without supersede intent, holding an uncertain effect, fenced, or a duplicate command id — apart from a Turn that broke, and answers it with a versioned `{ schemaVersion, status: "refused", reason, error }` body the client shows as its ordinary error state. Answering 500 made the browser log a console error for something that is a normal product answer, and made an end-to-end run fail on a page error rather than on the behaviour under test. `500` stays for a Turn that genuinely failed.

The composer no longer locks. Stop keeps the button only while there is nothing to send; the moment the User has typed something, sending it is what they mean by interrupting. A message sent mid-Turn appears immediately at the bottom of the thread as an ordinary user message at reduced opacity — no label, no icon, no word for the User to learn — and goes to full strength when its own Turn starts. The greyed state is projected from durable run state (`ClientRunV1.queued`), so a reload draws the same thing, and the client's optimistic copy reconciles to it by run id. The superseded Turn's bubble keeps everything it already sent and takes the treatment a stopped Turn already has.

**The client no longer labels the superseded Turn.** It carried "Interrupted by your next message." under its last bubble, which told the reader something the message sitting directly underneath it already said in their own words — the one ending in this product that needs no explaining. The notice is gone from the transcript; the durable run record still carries the sentence, so the debug surface and the API still say why the Turn ended where it did. Stop keeps its notice, and a failure keeps its own, because neither of those has a message underneath explaining it. The working row moved with it: the Bot's avatar and its comet trail are now the thread's last child rather than a part of the running Turn's article, so a message sent mid-Turn lands _above_ the sheep instead of below the Turn it just replaced.

`ClientRunV1` gains `queued?: true` and the `superseded` status with a `superseded` outcome; `ClientRun` follows. `StoredRunV1` gains `supersededAt`, `supersededBy`, the `superseded` status, the `queued` phase, and an optional `admission.lane`. `BotDurableAuthorityHooks` gains two optional hooks — `interruptTurn`, which is advisory and product-neutral, and `supersededRecords`, the sibling of `terminalRecords`. `planStoppedRunRecovery` becomes `planInterruptedRunRecoveryV1` and classifies both intents, because they share the whole question: an effect that may already have run is never assumed not to have.

The accepted trade-off: superseding a Turn whose model call or tool effect was already **admitted** leaves that run `reconciliation-required`, exactly as Stop does today, and the queued Turn waits behind it until the outcome is retrieved. Assuming the effect away to start the new Turn faster would be a silent duplicate, which the register forbids. The failure is visible in durable state and repairable from the banner the User already has.

## Feature rule

1. **Authoritative owner.** The Bot's Durable Object: admission, the lane decision, the supersede intent, the queue slot, and both settlements. The Shell Package owns the pending-input reminder and every projection; the client owns nothing.
2. **Durable state, commands, events.** State: `StoredRunV1.supersededAt` / `supersededBy` / status `superseded` / phase `queued` / `admission.lane`, and the `pending-run` key. Command: `ClientTurnCommandV1.supersedes`, decoded at the HTTP seam and again at the Durable Object's RPC door. Events: the superseded Turn's `turn/end` with `outcome: "cancelled"` and `reason: "superseded by a new user message"`, plus the `interrupted` tool results the interrupt repair writes. Durable input: one `superseded-turn` pending input.
3. **Disconnect, eviction, hibernation.** A client that disconnects detaches an observer; both Turns are durable and continue. Eviction between the superseded Turn terminalizing and the queued one starting is recovered by the object's own alarm — `recoverQueuedRun` promotes and starts it exactly once, and a caller already waiting for it in the resident object is left to do the promoting itself so the two paths cannot both start it. Eviction mid-Turn is unchanged: the fence means the resumed Turn starts no new effect and settles `superseded`. Nothing here wakes the Computer.
4. **Cancellation, retry, idempotency, reconciliation.** The supersede intent is part of the command fingerprint, so a retried POST replays rather than interrupting a second Turn. The interrupt itself is idempotent: an intent already recorded is not rewritten. Effects are reconciled by the existing tool-occurrence journal and `ToolEffectReconciliation` path, unchanged, and nothing is re-run.
5. **Authority, credentials, trust.** No new authority. The command is authenticated on the existing Turn route and validated against the Bot's durable identity in the admission transaction; a supersede can only reach the Bot the caller already owns.
6. **UI projection and control homes.** One surface: the conversation. The composer is the only control, and it gained no new one — the Send button now also means "instead of that". No per-Bot setting, because there is nothing to configure: this is how sending a message behaves.
7. **Observable failure states.** A supersede against a `reconciliation-required` run is refused with a message naming the run. A queued Turn that cannot start after its bounded retries fails with `run "…" could not start` rather than sitting silent. A superseded Turn whose effect was admitted appears as `reconciliation-required` in the existing banner with its Resolve action. Recovery tests cover eviction between the two Turns, the fenced-effect settlement, and the admitted-effect reconciliation.
8. **Parity register.** Row 57i, GrokBot §B send pipeline.
