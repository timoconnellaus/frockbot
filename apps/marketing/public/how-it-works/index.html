Inside FrockBot

Your Bot.
Your rules.
Your frock.

A Bot should fit the person who uses it. Its tools, its behaviour, even the interface around the conversation.

That’s the idea behind FrockBot. A persistent agent in the cloud, native apps on your devices, and plugins that let you dress your Bot however you want.

01 / Native where you are

Feels at home.
Keeps you connected.

The conversation belongs to the Bot. The experience belongs on your device.

FrockBot’s installed apps are built with Flutter and render their interface locally. Native integrations connect that interface to the device’s audio, windows and operating system. The browser client reaches the same cloud state, so you can pick up the conversation from another screen.

Web and macOS are available in early access. Android is in development; iPhone and the other device surfaces in the capability reference are planned. A platform appearing in the architecture does not mean there is a released app for it yet.

The long-term aim is to use what makes each platform useful: a desktop’s files and windows, a phone’s sensors, a watch’s quick interactions. Those capabilities need explicit support in the client and permission from the person using it.

02 / The cloud keeps the thread

Close the laptop.
The Bot stays.

A Bot is a persistent identity, with its own conversation, notes, instructions and routines.

Each Bot is a Cloudflare Durable Object. Each User has a Durable Object too, coordinating account state and installed plugins. Your devices submit commands and render the results; the cloud holds the authoritative state and runs the agent loop.

A Turn is one run of a Bot, started by a message, a schedule or a webhook. It can involve several model requests and tool calls before it finishes or needs your input.

Recording input before acknowledging it means an accepted message is not lost when your connection drops. Recording enough of the Turn lets the system resume after Cloudflare evicts a process. “Always on” means the Bot remains available and its work persists; it does not mean a CPU spins all day.

A little deeper: effects and recovery

Operations that spend money or write to another service need a recorded intent and an idempotency key. Retrying with that key protects against repeating the same operation where the receiving service supports it. Recovery is not a blanket promise that every external system can provide exactly-once execution.

03 / Dress your Bot

Change what it does.
And how it does it.

Plugins can add tools, change the agent’s behaviour, connect services and supply interfaces.

The architecture takes inspiration from dsh / DeepSeek Harness and Pi: make the harness something you can shape. FrockBot brings that idea into a persistent cloud service, with a deliberate boundary between the Bot, its extensions and your devices.

Plugin code runs in a Cloudflare Dynamic Worker, separate from the Bot’s Durable Object. A User’s installed plugins share one worker. You install a plugin for your account, then choose which Bots run it.

Access is granted, not assumed.

A descriptor declares what the plugin contributes and what access it needs. The Bot calls the plugin worker, and plugins call back through host-provided stubs. Every callback is checked against the Bot and Turn it serves.

Network access is limited to approved hosts, or open network access if you approve it. Because the plugins share a worker, network authority must be understood as shared across that worker’s enabled plugins. Credentials are attached by the host at the network boundary; the plugin does not receive the secret.

Descriptor excerpt · current contractJSON 
{
  "id": "research-tools",
  "displayName": "Research tools",
  "version": "1",
  "contractVersion": 6,
  "hooks": ["agent/tool-exposure"],
  "grants": ["storage", "http"],
  "network": { "hosts": ["api.example.com"] }
}

A declared host is a request for access. The User still approves the grant. This excerpt omits contributions such as tools and cards.

Six hooks into the agent loop.

The host exposes specific moments for plugins to participate. For hooks that return a patch, the next plugin sees the previous plugin’s result, in plugin order. A Turn may repeat model and tool steps.

  1. system-prompt/assembleShape the instructions assembled for the model.
  2. agent/tool-exposureChoose which admitted tools the model sees.
  3. agent/requestTransform the permitted fields of a model request.
  4. tools/pre-executeInspect or transform a tool call before execution.
  5. tools/post-executeTransform the result returned to the agent.
  6. agent/turn-stoppingReceive the notification that the Turn is stopping.

Today, the stopping hook is a notification, not a veto. Request hooks cannot change the admitted provider, model or credential binding.

Hook example · JavaScriptTool exposure 
export const hooks = {
  "agent/tool-exposure": ({ tools }) =>
    tools.filter((tool) =>
      tool.name !== "email_send"
    ),
};

This hook removes a tool from the model’s view. Tool visibility is not itself a security boundary; the host still enforces authority.

Your Bot can write a plugin, too.

You can ask for a new capability and have the Bot write the plugin. The resulting artifact is immutable and identified by its content. New code does not grant itself new powers: its requested access must be approved before activation, within the Bot’s existing authority.

  1. WriteThe Bot proposes code.
  2. CheckValidate the artifact.
  3. ApproveYou grant its access.
  4. ActivateMount a new version.

Versions can be replaced or a previous composition restored. Reverting code does not undo an email already sent or another external effect. Plugins may also bundle Skills or offer typed services to other plugins; a missing dependency disables the dependent plugin.

What happens when a plugin fails?

The plugin worker has a hard CPU budget. Ordinary plugin failures can be skipped or quarantined so the Turn can continue. The budget belongs to the worker, and a worker-wide failure can affect several plugins. Failures in required, locked plugins can stop the operation. Isolation limits reach; it is not a promise that every failure is invisible.

04 / The interface is part of the plugin

Give it a place.
Let it take shape.

A slot says where something appears. A renderer says how it is drawn.

Plugins should be able to shape more than the text of a reply. A card in the conversation, a panel beside your work, a settings section or a whole page can give a capability its own useful interface, backed by the plugin’s stored data.

A2UI is a structured description of an interface. The plugin names components, supplies values and declares actions; the host renders components it already knows. It does not download native executable UI code from the plugin.

HTML is the intended option for a custom web interface in a contained surface. That gives a plugin more control over layout without making it native application code. The plugin’s privileged logic still runs in the worker, and device access still passes through the host.

A2UI card message · current formatJSON 
{
  "version": "v1.0",
  "createSurface": {
    "surfaceId": "research-note",
    "catalogId": "https://frockbot.com/a2ui/catalogs/frock/v1.json",
    "components": [{
      "id": "root",
      "component": "Text",
      "text": "Three sources saved."
    }]
  }
}

A small description becomes a locally rendered card. Read the component schemas ↗

Conversation cards and settings sections are the starting point today. Cards use A2UI; settings sections currently use a smaller host-rendered view format. General A2UI/HTML slots, full pages and the broader placements below describe the direction of the platform.

The host keeps ownership of the conversation, audit, undo and trusted approval controls. A plugin can draw its own interface, but it cannot mint an approval identity or replace the parts of the app that let you see and control its work. A new native component or operating-system integration still needs to be shipped in the client.

05 / A much wider canvas

An event here.
A possibility there.

The cloud Bot connects capabilities across devices, services and the interface itself.

A phone event can start a Turn that uses a desktop capability. A webhook can update a conversation card. The plugin combines the pieces; the host decides what is available and allowed.

06 / More than a message history

A little continuity
goes a long way.

A useful Bot needs to remember, know how to work and come back at the right time.

Memory

What it knows

Durable notes hold useful facts beyond the immediate conversation. Bot, User and Project scopes let information live at the right level.

Skills

How to do it

A Skill is an instruction directory: a SKILL.md file and its references. Plugins can bundle Skills for the Bots that run them.

Routines

When to return

Schedules and events start new Turns without an open app. Each run belongs to the Bot’s continuing record.

Conversation history records what happened. Memory keeps the information worth carrying forward. Skills describe a way of working. Routines make that work recur. These are distinct pieces, so a long chat does not have to carry every instruction and every fact forever.

You can give different Bots different jobs, identities, instructions and plugin selections. They share an account’s connections and resources where appropriate, while keeping their own conversations. That lets you build a small team without configuring a separate service for every Bot.

07 / Somewhere to do the work

Your Bot has
a Computer.

A remote browser, filesystem and terminal, with a desktop you can watch or take over.

The current Computer provider uses Fly Sprites: one persistent computer per User, shared by their Bots, with Bot-specific directories and on-demand desktop sessions. Browser logins are shared at the User level. The Workspace gives the work a place to live.

This is where a Bot can browse, use a terminal and work with files. It is also somewhere you can step in when a site needs human attention. Plugins run in their Dynamic Worker, not on this Computer; they reach Computer capabilities through the host’s approved interface.

A connected desktop app is another client on your own machine. Giving a Bot a cloud Computer does not silently give it access to that machine’s filesystem or operating system.

08 / Talk naturally. Choose the engine.

A voice to talk to.
Room to choose.

The interaction can be immediate while the work remains persistent.

Dictation puts spoken words into the composer. Live voice is a conversation: the realtime voice layer can hand work to your Bots while you keep talking. The Bot’s durable Turn remains the place where that work is executed and recorded.

Speak→Live conversation→Bot work→Recorded result

Model choice sits behind an interface too. The provider catalogue contains 40 provider entries, with different authentication and model options. The Turn uses its admitted provider and model; credentials stay in the Worker. Optional model-provider plugins translate requests through host-controlled transport.

Frock AI is the built-in path. On a deployment without model keys or an AI Gateway configuration, it can use the Cloudflare account’s Workers AI binding. You can start with the default and configure another provider when you need it.

09 / Yours to shape

The freedom goes
all the way down.

FrockBot is open source under the MIT licence.

You can inspect the agent loop, see how permissions are enforced, write a plugin, change a client or run a deployment in your own account. The same source lets you move from “I wish it did this” to changing how it works.

Plugins customise the running product. The source lets you change the product itself: add a native integration, extend the component catalogue or contribute a new capability for everyone. Self-hosting means operating the required cloud services and paying their usage costs; the install guide explains the prerequisites.
